## 1. 为什么消灭 Dart 中间层

旧模型（Dart-host）：

```
C++ UI → Dart → [helix_on_ws_frame / helix_on_http_response] → Rust
                  ↑ Dart 持有网络，喂帧给 Rust
```

新模型（C++ 直连）：

```
C++ UI → [helix_command / helix_query] → Rust（持 WS/HTTP/SQLite）
                                          → on_domain_events_batch(buf, len) → C++
```

切换理由：

1. **Dart 是性能瓶颈中间层**：每条 WS 帧 Dart 转发一次，每条 DomainEvent Dart 再转发一次，
   两层序列化/反序列化完全无必要。Rust 直接持网络更高效。
2. **状态所有权更清晰**：网络连接、重连退避、header 注入全在 Rust 管，Dart/C++ 侧零网络状态，
   不存在「Dart 持的连接和 Rust 持的连接谁在 reconnect」的歧义。
3. **批处理对齐 HX-C007**：逐条 `on_domain_event` 变成整步批量 `on_domain_events_batch`，
   FFI 调用次数从 N 次降到 1 次/step，跨边界开销数量级降低。

## 2. 本 crate 的三重身份

`helix-driver-ffi` 同时是：

| 身份 | 内容 |
|---|---|
| **driver**（驱动） | 装配 FFI 特化 ports（FfiEventSink / FfiClock / FfiHttpRequester）|
| **composition root**（装配根） | `pump.rs` 的 `register(ImModule)` 把业务模块注入 ExecutionShell |
| **ABI 边界层** | `api.rs` 导出 `#[no_mangle] extern "C"` 函数族（helix_create / helix_command / helix_destroy / helix_query）|

native 端的「composition root」是独立的 `helix-host-cli` crate；
FFI 端没有独立 app crate（C++ 直接 `helix_create`），所以 `pump.rs` 兼任装配职责。
这是合法的：装配在 driver 层（不在 core），依赖方向单向（adapter → core）不违反三层铁律。

---

## 3. Rust 持 WS：SharedWsClient

`SharedWsClient` 是 `helix-driver-host` 的 WS 管理器，ffi 端直接持用：

- WS 连接生命周期（握手 / 重连 / 退避 / 心跳）全在 Rust。
- `SharedWsClient::with_inbound_tick`：收到 WS 帧 → 直接发 `Tick::Inbound` 进 pump 通道，
  不经过任何外部「帧注入」接口。
- C++ 侧**不见 WS 帧**，只见 DomainEvent（业务级抽象）。

---

## 4. FfiEventSink 批处理：整步一次 vtable 回调

```
step() 内每次 emit(ev)
    → FfiEventSink 内部 Vec<DomainEventBytes> 积累
    → step 结束后 run_engine_loop 调 flush()
    → batch.rs 编码成 len-prefixed 单 buffer
    → CppHostVtable::on_domain_events_batch(buf, len)  ← 一次跨 FFI 调用
```

这是 HX-C007（Effect 跨 FFI 边界批处理）在 FFI 端的具体实现。
「整步攒批」的时机由 host `run_engine_loop` 内的 `BatchSink::flush()` 触发，
`FfiEventSink` 自己不感知泵循环结构。

---

## 5. FFI 边界安全（HX-C006 硬约束）

本 crate 每个导出函数都强制遵守：

1. **opaque ptr 单 owner**：`Box::into_raw` 在 `helix_create` 交出，`Box::from_raw` 在 `helix_destroy` 收回，各一次，null-check 守卫。
2. **panic 策略 = panic="abort"**（生产 cdylib profile）：panic 即进程 abort，不 unwind 跨 `extern "C"`。
3. **C 侧 buffer 立即拷贝**（ACL-3）：payload 指针来自 C++，Rust 立刻 `to_vec()` 拷贝，不持有 C++ 内存。
4. **Storage 只在 pump 执行**（MAJ-4）：同步 SQLite 调用由共享 host executor 放进 `spawn_blocking`；C ABI 查询函数不得绕过 pump 直查 Storage。

---

## 6. helix_query 现状

`helix_query` 只支持 capabilities/version 元信息。IM 业务查询通过 `helix_command` 进入
共享异步状态机，结果由 `on_domain_events_batch` 返回；FFI 不持有业务查询 Storage 句柄。
实现以 [`../../../src/api.rs`](../../../src/api.rs) 和移动端 Query 契约为准。

---

## 7. pump 线程模型

```
std::thread（pump 线程）
    └── tokio current_thread runtime (enable_all)
        └── block_on run_engine_loop(...)
            └── helix-core ExecutionShell::step() ← 单线程，零并发（GOAL §1.3）
```

- pump 线程与 C++ 调用线程完全隔离（`helix_command` = `tick_tx.send`，非阻塞）。
- `helix_destroy` = `drop tick_tx` + `send shutdown` + `join pump_thread`（等泵退出，保证最后一批 `on_domain_events_batch` 在 vtable.ctx 释放前返回）。
- `helix_query` 只读取静态元信息，不创建 runtime，也不访问 Storage。

---

## 8. 总结一句话

`helix-driver-ffi` = 「装配 FFI 特化 ports + composition root（ImModule 注册）+ C-ABI 导出」，
通过 `run_engine_loop`（host 泛型泵核）与 native 端 parity by construction，
通过 `FfiEventSink::flush` + `batch.rs` 实现 HX-C007 整步批处理，
`helix_query` 只承载元信息，业务查询统一复用共享异步 QueryRouter。
