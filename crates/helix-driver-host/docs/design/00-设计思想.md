# helix-driver-host 设计思想

> 本文是 `helix-driver-host` 这个 crate 的架构意图与核心决策备忘，
> 供后来开发者「读完这一篇就知道为什么」，避免边界模糊、重复实现、或因误解而破坏不变量。
> 真源：`src/`；设计图索引：[`README.md`](README.md)；并发正确性规范：[`07-storage-rw-concurrency-spec.md`](07-storage-rw-concurrency-spec.md)。

---

## 1. 北极星：一份实现，两端复用

Helix 的目标是「一份业务内核跑 native（PC/Tauri）和 FFI（Flutter 手机端）两端」。
在 ADR-007（pump 核下沉 host）之前，`helix-driver-native` 是唯一持有完整泵逻辑的 crate：
engine_loop.rs 曾包含存储 ops、HTTP 发射、timer registry、BoundedSpawner 原语——
FFI 端要复用只能整块搬，造成语义分叉风险。

**ADR-007 的一句话**：把「多端公共的 I/O 实现」抽到 `helix-driver-host`，让 native 和 ffi
都变成「装配薄壳 + 调泛型泵核」。

结果：
- `helix-driver-host` = **单一真源**（存储/泵原语/HTTP envelope）。
- `helix-driver-native` engine_loop.rs 现在只保留平台组装与 `run_engine_loop` 调用；行数随接线与观测能力演进，不再作为合同。
- `helix-driver-ffi` pump.rs 同样约 ~80 行（FFI 特化 ports 装配 + 调 `run_engine_loop`）。
- 任何泵/存储 bug fix 或性能优化，**改一处两端同时受益**。

## 2. 泵核下沉 = parity by construction

「parity by construction」是本 crate 最核心的设计哲学：不靠测试对比两端行为是否一致，
而是让两端**物理上共用同一份代码**，一致性由结构保证，而不是靠「检查」。

实现形式：

```rust
// helix-driver-host/src/engine.rs
pub async fn run_engine_loop<S, H, E, T, C>(
    shell: ExecutionShell,
    storage: S,
    http: H,
    event_sink: E,
    transports: Vec<T>,
    clock: C,
    tick_rx: Receiver<Tick>,
    reply_tx: UnboundedSender<PortReply>,
) where E: BatchSink, ...
```

- native 调它，FFI 也调它。`E: BatchSink` 让 native（`NativeEventSink`）和 ffi（`FfiEventSink`）
  在「egress 批处理」上有差异化行为，但泵循环本身（biased select / step / dispatch effects）
  完全相同。
- `BatchSink` supertrait 是在 host 层（不在 core）定义的，因为「一步一 flush」是运行时概念
  （core 的 EventSink 不认识批边界——HX-C001 边界守护）。

## 3. C++ 直连模型的转折（Dart-host → 无中间层）

本 crate 的另一个背景：FFI 端原本设计为「Dart 持有网络，喂帧给 Rust」（Dart-host 模型）。
转向「C++ 直连」后，**Rust 持有 SharedWsClient + SharedHttpClient**，Dart/C++ 只需要：

1. `helix_create_with_network(vtable)` —— 启动 Rust 泵
2. `helix_command(json)` —— 注入 Tick::AppCommand
3. `on_domain_events_batch(buf, len)` —— 接收批量 DomainEvent 回调

原来 `helix_on_ws_frame` / `helix_on_http_response` 两个「帧注入」接口已废弃（Dart-host 遗物）。
这意味着 WS 管理、HTTP 管理、连接生命周期全在 host 层，C++ 侧**零网络状态**。

`helix-driver-host` 的 `network.rs` 是这个模型的 I/O 支柱：
`SharedWsClient` / `SharedHttpClient` / `HostNetworkConfig` / `HostHeaderRegistry`（运行时 token 注入）
全在这里，两端共用。

## 4. BatchSink flush hook：在 host 不在 core

为什么 `flush()` 在 host 定义而非 core？

- `core::EventSink::emit` 是逐事件推送，core 在 step() 内调它，语义是「吐出一个 DomainEvent」。
- 「整步攒批后统一 flush」是运行时决策：FFI 需要批处理（HX-C007，跨 FFI 边界每条调用有开销），
  native 不需要（broadcast 即时送，`flush` = no-op）。
- 如果 `flush` 进 core，则 core 的 `EventSink` trait 就带上了「批边界」的运行时概念，
  破坏 HX-C001（core 零运行时依赖 / 零 driver 语义）。

host 层的 `BatchSink: EventSink` 是核心 EventSink 的**自然扩展**：不改 core，
只在 host 里加一个 supertrait，让泵核在 `dispatch_effects` 之后多调一次 `flush()`。
native 的 no-op 编译期消解（零代价），ffi 的 flush 触发真实批传输（HX-C007 合规）。

## 5. 读写并发模型：WAL + 三池

`HostStorage` 内部有三池（见 `07-storage-rw-concurrency-spec.md §1`）：

- **写连接（N=1）**：`Arc<Mutex<Connection>>`，WAL 单写者，BoundedSpawner N=1 保序。
- **sync 写连接（N=1）**：sync pull（批量 upsert channel/message）专用，避免与增量写争锁。
- **读连接池（N=4）**：`ReadPool`（Semaphore(4) + Vec<Connection>），WAL 快照并发读，读读不互斥。

所有 rusqlite 同步 C 调用全包 `spawn_blocking`（HX-C006），不阻塞 tokio worker。
FFI 端（current_thread runtime）读路径在 `helix_query` 的 `block_on` 线程上跑 `spawn_blocking`，
不占用泵单线程。

本 crate 的成型过程沉淀了以下反模式教训：

## 7. 不变量守护

五个跑不掉的不变量（破坏 = 双端泵语义漂移）：

1. **回灌必达**：PortReply 走独立 unbounded reply_tx。改有界 → Block 死锁环。
2. **主循环不等 I/O**：Persist/Http 入队即返回；HttpFire DropNewest（满即丢当前条目）。
3. **同 key 写顺序**：Persist BoundedSpawner N=1 单消费者保序。
4. **回灌优先**：biased select reply_rx 在前，防 PortReply 饥饿。
5. **graceful drain**：`run_engine_loop` 返回 = 全部 Persist 已落地；必达 Http 与 `UploadFile` 在最长 3 秒窗口内 drain，超时则 abort 在途网络任务，发送可靠性由已持久化的 Sending 状态与重连重发对账承担。
