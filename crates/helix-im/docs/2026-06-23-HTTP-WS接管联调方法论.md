## 1. 核心命题：每个写 HTTP 必有对应 WS 回声，读 HTTP 无 WS

接管一个「HTTP 改状态 → 服务端 WS 广播变更」的实时系统，验证的**第一性原理**是：

```
写命令（mutation HTTP）  ──触发──▶  服务端状态变更  ──广播──▶  WS 推送事件  ──▶  客户端投影渲染
读命令（query HTTP）     ──────────────────────  仅 HTTP 响应回灌，无 WS  ──▶  await 返回值渲染
```

**因果不变量（验证的锚）**：

1. **每个写 HTTP 命令必有 ≥1 个确定的 WS 回声事件**（一对一或一对多）。若发了写命令却没收到对应 WS → 接管断裂（body 不对 / 端点错 / 服务端没推）。
2. **每个读 HTTP 命令必无 WS**——纯请求/响应，响应直接回灌发起的语义 invoke。若读命令意外触发 WS → 命令分类错（读写混淆）。
3. **WS 事件 ↔ 写命令是多对多但可枚举**：一个 WS event（如 `update_channel`）可由多个写命令触发（高频复用）；一个写命令（如建群）可触发多个 WS event（`channel_created`+`channel_member_update`+`post`）。**必须穷举这张映射表**——它是测试矩阵的骨架。

> **实战教训**：cses-client 接管中「发消息无回声」的真因不是 Pulsar 配置，而是 **HTTP body 字段不对**（`真机curl真源.md`）——服务端收到坏 body 静默拒绝，不推 WS。所以**写命令的 body 对齐真抓包 > 源码推断**，是因果链第一环。

### 1.1 建因果映射表的方法（双向核对）

- **正向**：从 outbound 命令清单（registry / 源码）逐条标注「触发哪个 WS event」——锚 WS 推送侧真源（服务端 app 层 `a.Publish` 站点）。
- **反向**：从 WS event 清单逐条反查「由哪些命令触发」——堵「某 event 没有任何命令触发」（= 该 event 只能服务端造数 / 其他用户触发，无 outbound 测试行）的缺口。
- **两向核对必须闭合**：正向有的反向能找到，反向独有的标为「无 outbound 缺口」。cses 实战中 `post_pin`/`change_channel_approval` 两 event 无对应 outbound（toggle 端点未接管）——反向核对才暴露，纯正向会漏。

## 2. 三铁律断言（接管联调最易翻车的 wire 契约点）

接管 = **透传现网 wire 行为，非重新设计**。最易在三处「字段形态」上翻车，每条写命令的期望帧都要过这三关：

### 铁律① cursor 字段顶层注入（离线对账命脉）

实时 + 离线双轨系统，**sync cursor 字段必须在 WS `data` 顶层**（不是嵌在 props 里）。
- cses 实战：`post`/`posts_update`/`post_update`(编辑) 三事件顶层注入 `event_seq`(int64)，客户端 pts gate 直接读 `data.event_seq`，**不**解 `data.props.channel_event_seq`。
- 缺顶层 → cursor gate 收不到 → 离线重连补齐断裂。
- **断言**：写命令的 WS 回声帧，`data.event_seq` 是顶层 int64。

### 铁律② 复合字段的序列化形态（map vs JSON string）

会话列表类聚合字段（如 `lastPost`）在某些路径是 **JSON 字符串**而非嵌套 object——客户端 VO 声明 `String`。
- cses 实战：`update_channel`/`increment_channel` 的 `lastPost` 必须是序列化后的 JSON string。推 map → 客户端反序列化报 `invalid type: map, expected a string`（2026-05-29 撤回路径踩坑）→ 会话 lastPost 不刷。
- **断言**：跨所有推 `lastPost` 的路径，字段值类型一致为 string。

### 铁律③ casing / 命名陷阱（透传保真，禁「统一」）

接管时**禁止**把现网的「不规则命名」统一成规整形态——现网消费侧就认那个不规则名。
- cses 实战陷阱词典：
  - `change_channel_approval` wire action **无 Status 后缀**（常量名带 Status，wire 值不带）。
  - 时间字段 `createAt`（**非** `createdAt`/`created_at`，camelCase 漏 d）；DB 列才是 `created_at`，两边都对，别统一。
  - `top20` body 用 **snake_case** `channel_id`（唯一 snake 读端）；`getUpdatedPosts` 用 **`timeStamp` 大写 S**；`getPostsAfterIndex` 的 `postIds` 是**单 id string 非数组**。
  - 投影信号类用 `channel_id`(snake)，透传类用 `channelId`(camel)——逐 channel 不同。
- **断言**：每条命令的 body 键名 / WS action 字符串逐字对齐真源（真抓包 > 源码字段名）。

> **方法论要点**：三铁律不是「写代码时注意」，而是「**测试矩阵里每条期望帧的固定断言列**」——把口头约定降级为机器可勾选判据。

## 3. 按依赖链状态机式排序测试（编排范式）

接管联调**不能随机点测**——命令间有状态依赖链，必须按状态机推进顺序编排，前一阶段产出是后一阶段前置依赖。

### 3.1 通用阶段骨架（连接 → 列表 → 历史 → 实时 → 变更 → 读 → 扩展）

```
① 连接层      connect → 握手 → 拿连接标识(connectionId)        ← 一切的根；红则停
② 列表冷启动  增量推送 → 落库会话列表 + 每会话 cursor 锚点
③ 历史补齐    按 cursor 拉离线增量 → 落库消息 + too_long 兜底
④ 实时收发    发消息 → 乐观上屏 → WS 回声 → echo 对账
⑤ mutation    已读/编辑/撤回 → 各自 WS 回声 → 投影
⑥ 容器写族    建群/成员/角色/属性变更 → 多 WS 回声
⑦ 纯读族      query 命令 → 无 WS → 响应回灌（可与①后任意并行）
⑧ 扩展域      bot/agent/webhook → 部分 WS 回声 + 纯读
```

### 3.2 状态机门（gate）原则

- **每阶段有「前置依赖」**：明确写出本阶段依赖前面哪个阶段的产出（如 ③ 依赖 ② 的「每 channel cursor 锚点」）。
- **关键阶段「红则停」**：① 连接拿不到 connectionId → 后续所有 outbound 身份头缺失 → 全链路阻塞。这类阶段失败必须停止，不往下测（避免一堆下游假阳/假阴）。
- **每阶段四要素**：前置依赖 / 操作步骤 / 期望结果 / 判据（勾选框）。判据必须是**可证伪的具体断言**（字段值 / SQL count / WS action），不是「应该正常」。
- **纯读阶段可旁路并行**：⑦ 纯读族只依赖 ①（连接 + 身份头），与 ②-⑥ 的状态推进无耦合，可任意时刻并行测。

### 3.3 落库 + 投影双重验证点

接管引擎的正确性有**两个观察面**，每个状态变更都要双验：

1. **落库面**：状态权威写进本地 DB（SQLite `channel`/`message` 表，列对齐 wire→column 映射）。验 `SELECT` 行数/列值。
2. **投影面**：引擎 emit 出 `im:__bus__` 信封 → 前端纯渲染。验 emit 的 channel + `data` 键集对齐冻结契约（projection-schema）。

> **「纯渲染」证伪标准**：前端退化为纯渲染——不算 unread/lastPost/readBits/cursor。**信号类事件只携 `channel_id`+`event_seq`+`msg_id` 三字段**（权威行已落 DB，前端按 id 回读）。若某信号事件塞了「半份聚合行」（如只给 unreadCount 不给 lastPost）→ 前端用半份覆盖整份 → 渲染破功。故信号类冻结集**严格 = 三字段，多一个都算漂移**，逼字段走 DB 列而非 emit。

## 4. 接管联调 vs 普通端到端测试的差异

| 维度 | 普通 e2e | 接管联调（本方法论）|
|---|---|---|
| 验证目标 | 功能对不对 | **新引擎产出 == 旧行为**（wire 逐字对齐）|
| 真源 | 需求文档 | **现网真抓包 > 源码推断**（旧系统实际 wire）|
| 断言粒度 | 用户可见结果 | **HTTP body 字段 + WS action 字符串 + 投影键集**（机器可勾选）|
| 编排 | 用例独立 | **状态机依赖链顺序**（前阶段产出=后阶段前置）|
| 覆盖核对 | 用例数 | **命令计数核对 + WS event 双向反查闭合** |
| 缺口处理 | —— | **无 outbound 的 WS event 显式标注**（不能假装覆盖）|

## 5. 复用 checklist（下次接管别的实时系统时）

- `[ ]` 建 **命令 ↔ WS event 因果映射表**（正向标注 + 反向反查闭合）
- `[ ]` 每个写命令的 body **对齐真抓包**（非源码字段名推断）
- `[ ]` 抽出本系统的 **三铁律**（cursor 顶层 / 复合字段序列化形态 / casing 陷阱），落成测试矩阵固定断言列
- `[ ]` 按 **状态机依赖链**排 8 个左右阶段，每阶段四要素（前置/操作/期望/判据）
- `[ ]` 关键阶段标 **「红则停」**（连接层、cursor 锚点）
- `[ ]` 每状态变更 **落库面 + 投影面双验**
- `[ ]` **命令计数核对**（机器断言总数）+ **WS event 双向反查**（堵无 outbound 缺口）
- `[ ]` 缺口（无 outbound 的 event / 不推 cursor 的特例）**显式标注**，不掩盖

## 6. 与已有方法论的边界

- **`gated-phase-migration`（全局 skill）**：管「怎么把旧系统分阶段、灰度、可逆地换成新引擎」（CI-1~CI-3 地基/薄壳/接线 + 灰度白名单→10%→全量）。本篇**不重复**那套。
- **本篇（HTTP+WS 接管联调方法论）**：管「换完之后，怎么系统性验证新引擎行为 == 旧行为」（CI-4 联调）。是 gated 迁移的**验收闸门方法论**，挂在灰度上线之前。
- 两者接力：gated migration 产出可灰度的接入 → 本方法论验证联调通过 → 才允许灰度上线（白名单→10%→全量）。
