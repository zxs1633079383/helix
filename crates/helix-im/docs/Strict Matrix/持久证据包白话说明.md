# 持久证据包白话说明

## 一句话解释

“持久证据包”就是：每次真实验收结束后，把能够证明这次 UC 确实跑通的全部材料放进一个不可混用、可校验、以后还能重新检查的目录，而不是只留下一个 `PASS`、几张散落截图或 `/tmp` 日志。

## 以 G-01 发送文本为例

用户 444 给用户 678 发送一条消息后，不能只说“界面上屏了，所以通过”。证据包至少要保存：

| 平面 | 要保存的事实 |
| --- | --- |
| UI | 444 的 sending/sent DOM、678 的 received DOM、稳定 selector 与双视角截图 |
| Helix | `im_send_message` command、Effect、乐观投影、回声对账后的权威投影 |
| HTTP | 创建消息的 request/response、状态码、`req_id` |
| WS | 678 收到的事件、发送方回声、`event_seq` |
| Storage | 本地消息/会话投影，以及 Go 端 post、channel_event 等权威事实 |
| Native | 真实 Tauri/FFI 进程、账号 profile、启动信息和驱动日志 |
| Trace | 上述材料共同使用的 `run_id + gate_id + operation_id + req_id + channel_id` |

目录中再放一个 `manifest.json`，列出每个文件的相对路径、类型、关联键、哈希和采集时间。验证器按 manifest 重新计算哈希，并拒绝目录外路径、符号链接、缺文件和重复认领。

## 它解决什么问题

- 防止拿昨天 G-01 的截图证明今天 G-02 已通过。
- 防止 UI 上屏但后端没落库，或者后端返回 200 但另一端没收到。
- 防止 reducer 自己写一句 Green，却找不到原始证据。
- 防止 `/tmp` 被清理后，再也无法复盘当时为什么判定通过。
- 防止多个并发 Native suite 共用账号、端口或截图目录后互相串证。

## 它不是什么

- 不是把所有日志压缩成一个 zip 就算完成。
- 不是永久复用的“黄金截图”。
- 不是设计稿、mock E2E 或单元测试的替代品。
- 不是新的业务真源；业务合同仍由 Helix Strict Matrix 定义。

每次 Run Evidence 只证明那一次运行。代码、合同、后端版本或场景输入发生变化后，必须重新执行并生成新的证据包。
