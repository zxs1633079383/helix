# UC01-16 Surface、ViewModel 与 InteractionFrame 合同

> 状态：Design Decision / Implementation Contract
>
> 日期：2026-07-20
>
> 范围：Message V4 的 UC01-16（`G-01..G-16c`）及其必要同步前置条件。
>
> 本文的定位：定义目标态的 Helix UI 投影合同。它不替代当前代码事实、HTTP/WS
> 字段清单或 Strict Matrix 证据；这些仍以
> [`前端UC投影指令与数据清单-最新代码分析-2026-07-09.md`](./前端UC投影指令与数据清单-最新代码分析-2026-07-09.md)
> 和 Strict Matrix 为准。

## 1. 拍板结论

Helix 不是再给每个端提供 `MessageStore`、`ChannelMemberStore` 或 raw event
消费者。它持久化领域事实，按 UI surface 输出权威、强类型、render-ready 的
ViewModel。各端只有 Frame Cache/Reducer：校验、原子 replace/patch、保存本地
overlay、读取只读状态并渲染。

```text
UiEvent / HostObservation / WS / EffectResult
  -> Helix Command + Domain State
  -> Persist / HTTP / Upload / Timer Effect
  -> PersistOk / WS authoritative echo
  -> Surface Projector
  -> InteractionFrame（多 surface 原子提交）
  -> PC / Mobile Frame Cache
  -> platform renderer
```

### 1.1 不可违反的边界

1. Angular、移动端和 Web 不订阅 `im:post:*`、`im:channel:*`、
   `increment_channel` 等业务 Emit 来决定如何更新 Store。
2. `increment_channel`、`post`、`post_update` 等是 Helix 的入站事实；只有 Helix
   可以将其归一、持久化、投影为 surface mutation。
3. 前端不计算未读、`@我`、加急、排序、预览、权限、成员角色、回复树、话题关系、
   `temporaryId -> serverId` 对账或分页去重。
4. 一个领域提交影响多个 surface 时，必须在同一个 `InteractionFrame` 中原子提交。
5. 业务真相由 Helix 领域状态持久化；ViewModel 对客户端是唯一权威输入，但可由领域
   事实重建，不能成为第二套业务 SoT。
6. 所有无上界集合必须使用 keyset cursor + 有界窗口。禁止前端全量数组、`filter`/
   `find` 重扫或收到一条更新后全表重排。
7. 用户资料属于 Ucenter。Helix 只传稳定的 `userId` 引用；各端复用 Ucenter 展示
   组件渲染名称和头像，不向 Helix 复制用户资料库。
8. 抽屉、弹窗、路由、菜单、动画、光标、像素滚动、成员选择器勾选和草稿是平台 UI
   overlay。Helix 不命令“打开哪个组件”，也不下发 DOM/Widget/CSS/像素指令。

### 1.2 领域事实与投影扇出

```text
Message
  -> message.timeline
  -> message.thread-detail
  -> message.left-dialog-list.preview
  -> message.participant-receipts
  -> message.unread-summary

Channel
  -> message.left-dialog-list
  -> message.channel-summary
  -> message.topic-list

ChannelMember + ChannelViewerState
  -> message.member-roster
  -> message.left-dialog-list 的个人角标/置顶
  -> message.unread-summary
  -> message.participant-receipts

TopicLink
  -> message.timeline 根消息 topicLink
  -> message.topic-list
  -> message.channel-summary.topicCount
  -> message.left-dialog-list.topicCount
```

`ChannelMember` 与 `ChannelViewerState` 必须分开：前者是成员事实（角色、昵称、
加入/退出），后者是当前 `userId` 在频道中的个人状态（未读、@我、加急、置顶、
免打扰、阅读水位）。两者都是 Helix 内部领域状态，不是客户端 Store。

## 2. Command、Effect、Projector、Frame 的职责

| 层 | 职责 | 例子 | 不负责什么 |
|---|---|---|---|
| `ActionBinding` | Helix 已裁决的动作入口 | `send-message`、`revoke`、`create-topic` | 平台菜单/弹窗样式 |
| Command | 表达业务意图并修改领域状态 | `SendMessage`、`MarkChannelRead` | 直接操作 Angular 状态 |
| Effect | 兑现外部副作用 | HTTP、SQLite、上传、Timer、WS | 投影 UI 或决定组件 |
| EffectResult / WS | 回灌外部权威事实 | HTTP 失败、`post`、`increment_channel` | 让端侧猜测最终态 |
| Domain State | 可恢复、可审计的业务事实 | Message、Channel、ViewerState | 直接暴露给 UI |
| Surface Projector | 事实到 UI 合同的唯一变换 | Dialog/Timeline/Roster Projector | 调用 HTTP/WS 或做平台 IO |
| InteractionFrame | 多 surface 的原子交付包 | timeline + dialog + unread | 业务真相或 UI 组件树 |
| Frame Cache | 强类型机械 apply | revision 校验、replace、patch | 业务计算 |

### 2.1 下行合同

```rust
struct InteractionFrame {
    schema_version: SurfaceSchemaVersion,
    transaction_id: TransactionId,
    mutations: Vec<SurfaceMutation>,
}

struct SurfaceMutation {
    surface: SurfaceId,
    scope: SurfaceScope,
    revision: Revision,
    base_revision: Option<Revision>,
    mutation: TypedSurfaceMutation,
}
```

`TypedSurfaceMutation` 是封闭、强类型的 enum，而不是 JSON Patch、数据库 diff 或
raw WS payload。通用 Frame 外壳只负责事务、surface、scope 和版本；每个 surface
定义自己的 `Vm` 与 mutation 集合。

客户端收到 Frame 后：

```text
1. 校验 schema、surface、scope、revision/baseRevision。
2. 对 Frame 内自己已 attach 的全部 surface slot 原子 apply；失败则一个也不提交。
3. patch 基线不匹配或 slot stale 时，丢弃该 slot 并重新 attach 获取最新 snapshot。
4. 暴露 readonly Signal<ViewModel> 给组件；组件不访问其他 slot 进行业务计算。
```

重连不回放 UI outbox。WS `hello -> increment_channel`/同步事实仍先进入 Helix；
Helix 更新领域状态后直接产出当前 surface 的 replace 或 patch。若某个 surface slot
发现 revision gap，只请求该 scope 的最新 snapshot，不让客户端重放历史业务事件。

### 2.2 上行合同

```text
组件点击由 ActionBinding 渲染出的动作
  -> invoke(actionRef, input)
  -> ActionReceipt { requestId, accepted | rejected, validationErrors? }
  -> 后续 InteractionFrame 才是最终业务结果
```

`accepted` 只表示 Helix 已受理，不等于 HTTP 成功、持久化成功或 WS 回声完成。
成员选择器、文件选择器、草稿与确认弹窗是端侧 UI；提交的 `selectedUserIds`、文件引用
和文本都必须由 Helix 再次校验。

### 2.3 HostObservation

HostObservation 是端侧观察到的 UI 边界，不是端侧业务 reducer。例如：

```rust
TimelineEdgeReached {
    channel_id: ChannelId,
    direction: Older | Newer,
    window_token: OpaqueWindowToken,
    visible_anchor_message_id: MessageId,
}
```

Helix 用 token 调用既有历史接口、去重、排序、控制窗口大小，再发新的
`message.timeline` Frame。客户端不得直连历史接口或拼接消息页。

## 3. 公共 VM 与数据结构

### 3.1 公共类型

```rust
struct UserRefVm {
    user_id: UserId,
}

struct ActionBinding {
    action_ref: OpaqueActionRef,
    kind: ActionKind,
    input_shape: InputShape,
    enabled: bool,
    disabled_reason: Option<DisplayReason>,
}

struct WindowPageVm {
    window_token: OpaqueWindowToken,
    has_older: bool,
    has_newer: bool,
    has_more: bool,
}
```

`UserRefVm` 不包含 Ucenter 的名称、组织、部门或头像 URL。各端 Ucenter 组件以
`userId` 解析展示资料；这是一项独立的资源渲染依赖，而不是 IM 业务计算。

### 3.2 有界窗口规则

默认消息时间线窗口为：上方 20 条 + 当前屏幕目标 20 条 + 下方 20 条，最多约 60 条
`MessageVm`。端侧可以传 `WindowHint`，Helix 校验并设定默认值与上限。

成员、话题和频道查询同样使用 cursor 与有界窗口。持久层使用主键/排序索引，读取
复杂度为 `O(log n + k)`；客户端每次只 apply 有上限的 `O(k)` 窗口，不会因为大群
成员退出而扫描或搬移 `O(n)` 条数据。

## 4. Surface 清单

| Surface | Scope | attach 时机 | 覆盖 UC | 领域来源 |
|---|---|---|---|---|
| `message.left-dialog-list` | 当前 `userId` | 登录后常驻 | UC01-10、13、15-16 | Channel + ViewerState + preview Message + TopicLink |
| `message.unread-summary` | 当前 `userId` | 登录后常驻 | UC08、13 | ViewerState 的 O(1) 聚合 |
| `message.timeline` | `channelId + windowToken` | 进入频道 | UC01-11、14-16 | Message + Channel + ViewerState + TopicLink |
| `message.thread-detail` | `channelId + rootMessageId` | 打开回复详情 | UC01、05、07、08、12、14 | root/reply Message |
| `message.channel-summary` | `channelId` | 进入频道/设置页 | UC09、13、15-16 | Channel + ViewerState |
| `message.member-roster` | `channelId + cursor` | 打开成员面板 | UC08、13、15-16 | ChannelMember + Presence |
| `message.topic-list` | `parentChannelId + cursor` | 展开话题 | UC15 | TopicLink + Channel |
| `message.participant-receipts` | `channelId + messageId + kind` | 点击统计 | UC08、13、14 | MessageReceiptState + member snapshot |

### 4.1 `message.left-dialog-list`

**职责**：左侧会话导航的顺序、分区、最后预览、个人 badge 和频道终态。它不接收
`lastPost` 原始实体。

```rust
struct DialogListVm {
    sections: Vec<DialogSectionVm>,
    state: SurfaceLoadState,
}

struct DialogSectionVm {
    kind: DialogSection, // pinned | normal | closed
    items: Vec<DialogRowVm>,
    page: WindowPageVm,
}

struct DialogRowVm {
    channel_id: ChannelId,
    channel_kind: ChannelKind,
    title: ChannelTitleRef,
    avatar: ChannelAvatarRef,
    company_tag: Option<CompanyTagVm>,
    preview: PreviewVm,
    last_activity_at: Timestamp,
    unread_count: u32,
    mention_count: u32,
    urgent_count: u32,
    topic_count: u32,
    has_scheduled_message: bool,
    is_top: bool,
    notification_mode: NotificationMode,
    lifecycle: ChannelLifecycleVm,
    actions: Vec<ActionBinding>,
}
```

```rust
enum PreviewVm {
    Text { author: Option<UserRefVm>, text: DisplayText },
    Document { author: Option<UserRefVm>, title: DisplayText },
    Media { author: Option<UserRefVm>, media_kind: MediaKind, label: DisplayText },
    Forwarded { author: Option<UserRefVm>, summary: DisplayText },
    System { text: DisplayText },
    Recalled { actor: Option<UserRefVm>, text: DisplayText },
    Empty,
}

enum DialogListMutation {
    Replace { view: DialogListVm },
    Patch {
        upserts: Vec<DialogRowVm>,
        removes: Vec<ChannelId>,
        moves: Vec<DialogMove>,
    },
}
```

`DialogMove` 明确给出目标 section 与 `Start/Before/After` 位置。Helix 决定排序；
客户端只做确定的、有限窗口内的机械 splice。

### 4.2 `message.unread-summary`

**职责**：应用导航或角标的当前用户全局统计。不能由 Dialog list reduce 得出。

```rust
struct UnreadSummaryVm {
    unread_total: u32,
    mention_total: u32,
    urgent_total: u32,
    unread_channel_count: u32,
}
```

Helix 内部通过 `ChannelViewerState` delta 维护 `UnreadAggregate`，单次更新为 `O(1)`。
一条入站消息若影响当前用户，Dialog row 与 UnreadSummary 必须处于同一 Frame。

### 4.3 `message.timeline`

**职责**：频道当前锚点附近的完整、可渲染消息窗口，不是 MessageStore，也不是全量历史。

```rust
struct TimelineWindowVm {
    channel_id: ChannelId,
    anchor: TimelineAnchorVm,
    items: Vec<MessageVm>,
    first_unread_message_id: Option<MessageId>,
    target_message_id: Option<MessageId>,
    page: WindowPageVm,
    state: SurfaceLoadState,
}

struct TimelineAnchorVm {
    message_id: Option<MessageId>,
    mode: Latest | Locate | Unread,
}
```

`MessageVm` 是 timeline 与 thread-detail 共享的完整消息行，不允许客户端按 id 回查
另一个 MessageStore：

```rust
struct MessageVm {
    id: MessageKey, // temporaryId 或 serverId，Helix 负责 identity settle
    channel_id: ChannelId,
    author: UserRefVm,
    created_at: Timestamp,
    content: MessageContentVm,
    delivery: DeliveryVm,
    actions: Vec<ActionBinding>,
    reply_summary: ReplySummaryVm,
    read_receipt: ReadReceiptSummaryVm,
    template_confirmation: Option<TemplateConfirmationSummaryVm>,
    urgency: Option<UrgencySummaryVm>,
    pinned: bool,
    bookmarked: bool,
    topic_link: Option<TopicLinkVm>,
}

enum MessageContentVm {
    Text { blocks: Vec<TextBlockVm> },
    Document { document_id: DocumentId, title: DisplayText, summary: DisplayText, access: AccessState },
    Media { media_type: MediaType, resource: MediaRef, thumbnail: Option<MediaRef>, file_name: DisplayText, size: u64, availability: Availability },
    Forwarded { summary: DisplayText, items: Vec<ForwardedItemVm> },
    SystemEvent { kind: SystemEventKind, display_text: DisplayText },
    Recalled { display_text: DisplayText },
}

enum DeliveryVm {
    Uploading { progress_percent: u8 },
    Sending,
    Sent,
    Failed { reason: DisplayReason, retryable: bool },
    Recalled,
}
```

发送者可见 `Uploading/Sending/Failed`；其他成员只会在最终可见后收到 `Sent` 消息。
上传进度由 Helix/Driver 节流投影，端侧不得猜测。

```rust
enum TimelineMutation {
    ReplaceWindow { view: TimelineWindowVm },
    PatchWindow {
        upserts: Vec<MessageVm>,
        removes: Vec<MessageKey>,
        ordered_ids: Vec<MessageKey>,
        page: WindowPageVm,
    },
}
```

定位 `messageId=100` 时，Helix 返回以 100 为 anchor 的完整约 60 条窗口。目标若远离
频道底部，新的实时消息不强塞进该窗口，而是更新 `has_newer`/新消息计数；用户点击
“回到最新”后再请求底部窗口。日期分隔、时间格式、气泡合并、滚动动画和高亮样式由
各端 Renderer 根据 `created_at`、`first_unread_message_id`、`target_message_id` 渲染。

### 4.4 `message.thread-detail`

**职责**：回复详情的完整根消息和扁平、有序回复窗口。它不构造递归树。

```rust
struct ThreadDetailVm {
    channel_id: ChannelId,
    root: MessageVm,
    ordered_reply_ids: Vec<MessageId>,
    nodes: BTreeMap<MessageId, MessageVm>,
    reply_count: u32,
    page: WindowPageVm,
    state: SurfaceLoadState,
}
```

`ordered_reply_ids` 只表达顺序；`nodes` 的每一个值都是含完整消息体的 `MessageVm`。
桌面端可以用抽屉、移动端可以用页面，但两者只渲染相同合同。snapshot replace、append
去重、旧 revision 抑制和跨页顺序都由 Helix 完成。

### 4.5 `message.channel-summary`

**职责**：频道头部和群设置共用的唯一资料合同；不再有独立 ChannelSettingsStore。

```rust
struct ChannelSummaryVm {
    channel_id: ChannelId,
    title: ChannelTitleRef,
    avatar: ChannelAvatarRef,
    notice_summary: Option<DisplayText>,
    purpose: Option<DisplayText>,
    lifecycle: ChannelLifecycleVm,
    member_count: u32,
    online_count: Option<u32>,
    topic_count: u32,
    notification_mode: NotificationMode,
    actions: Vec<ActionBinding>,
    settings_version: Revision,
}
```

群设置的输入草稿与确认弹窗是本地 overlay；保存后的标题、公告、资料、关闭/退出状态
必须由新的 `ChannelSummaryVm` Frame 覆盖，头部与设置页自然一致。

### 4.6 `message.member-roster`

**职责**：成员目录的分页窗口。Helix 已完成成员、角色、昵称和可操作性投影，不允许
客户端合并 `members/owner/adminUsers` 等原始字段。

```rust
struct MemberRosterVm {
    channel_id: ChannelId,
    items: Vec<MemberRowVm>,
    page: WindowPageVm,
    member_count: u32,
    online_count: Option<u32>,
    state: SurfaceLoadState,
}

struct MemberRowVm {
    user: UserRefVm,
    nickname: Option<DisplayText>,
    role: ChannelRole,
    presence: PresenceState,
    membership_state: MembershipState,
    actions: Vec<ActionBinding>,
}
```

成员退出使用 `(channelId, userId)` 主键/索引更新事实与 `member_count`，不扫描全成员。
Helix 返回当前有限窗口的 replace 或 patch；客户端复杂度只与窗口大小 `k` 有关。

### 4.7 `message.topic-list`

**职责**：父频道下按需展开的话题窗口。左侧会话列表只渲染 `topic_count`。

```rust
struct TopicListVm {
    parent_channel_id: ChannelId,
    items: Vec<TopicRowVm>,
    page: WindowPageVm,
    topic_count: u32,
    state: SurfaceLoadState,
}

struct TopicRowVm {
    topic_channel_id: ChannelId,
    root_message_id: MessageId,
    title: ChannelTitleRef,
    root_message_preview: PreviewVm,
    last_activity_at: Timestamp,
    message_count: u32,
    avatar: ChannelAvatarRef,
    lifecycle: ChannelLifecycleVm,
    actions: Vec<ActionBinding>,
}
```

创建话题的最终 Frame 至少同时更新根消息 `topic_link`、父频道 `topic_count` 与左侧
Dialog row；topic-list 已 attach 时再插入/replace 当前窗口。

### 4.8 `message.participant-receipts`

**职责**：单条消息的已读、模板确认和加急确认人员明细。消息行只显示摘要；点击统计
才 attach 本 surface。

```rust
struct ParticipantReceiptsVm {
    channel_id: ChannelId,
    message_id: MessageId,
    kind: ReceiptKind, // read | template_confirmation | urgent_confirmation
    summary: ReceiptSummaryVm,
    completed: Vec<ParticipantReceiptRowVm>,
    pending: Vec<ParticipantReceiptRowVm>,
    page: WindowPageVm,
    state: SurfaceLoadState,
}

struct ParticipantReceiptRowVm {
    user: UserRefVm,
    member_role: ChannelRole,
    status: ReceiptStatus,
    completed_at: Option<Timestamp>,
}
```

会话未读、单条已读、模板确认和加急确认是四个不同概念：

| 状态 | 行内摘要位置 | 人员明细 | 影响左侧/全局未读 |
|---|---|---|---|
| 会话未读 | DialogRow/UnreadSummary | 无 | 是 |
| 单条已读 | `MessageVm.read_receipt` | `kind=read` | 仅当前用户阅读水位变化时 |
| 模板确认 | `MessageVm.template_confirmation` | `kind=template_confirmation` | 否 |
| 加急确认 | `MessageVm.urgency` | `kind=urgent_confirmation` | 加急待处理状态可能影响 |

## 5. UC01-16 投影指令、Projector、Frame 与 VM 清单

本表保留现有“UC / Command / Effect / HTTP / WS / Storage / UI”阅读顺序，并加入
Projector、Frame 和 ViewModel。完整 HTTP body、WS 字段和真实数据库表仍引用当前分析
清单，避免在目标合同中复制后漂移。

| UC / Gate | Command / HostObservation | Effect / HTTP / WS 权威事实 | 持久化领域事实 | Projector | Surface 与 Frame mutation | VM 关键数据 | 双视角与端侧职责 |
|---|---|---|---|---|---|---|---|
| UC01 / G-01 文本发送 | `SendMessage` | Persist pending；`POST /posts/create`；WS `post/posted` echo | Message temporary/server identity、Channel、cursor | Timeline + Dialog | sender provisional: timeline insert + dialog preview；echo: timeline settle + dialog move；必要时 unread | `MessageVm.delivery`、Text content、`PreviewVm` | 发送者看 Sending/Sent/Failed；接收者只看 Sent；端侧不对账 temporaryId |
| UC02 / G-02 文档消息 | `SendMessage(type=DOCUMENT)` | 同 UC01 | Message document payload、Channel | Timeline + Dialog | 同 UC01 | `MessageContentVm::Document`、Document preview | 两端渲染文档卡；端侧不解析 raw props |
| UC03 / G-03 媒体附件 | `SendMessage(media)` | Upload Effect；create；WS post | Message media resource、Channel | Timeline + Dialog | 上传进度 patch；echo settle | `Media` content、`Uploading{progress}` | 发送者看进度/失败；接收者只见最终资源 |
| UC04 / G-03a 重试 | `RetrySend` | 重试 upload/create；WS echo | 同一 temporaryId 的 Message | Timeline + Dialog | patch 原消息 delivery，禁止新增重复行 | `Failed/Sending/Sent` | 端侧只提交 retry binding，保留本地草稿 overlay |
| UC05 / G-04/G-04a 撤回 | `RevokeMessage`；sync replay | revoke HTTP；WS `post_update/posts_update` 或 sync | Message revoke、Channel preview | Timeline + Dialog + Thread | message replace Recalled；dialog preview patch | `MessageContentVm::Recalled`、actions | 双方同一位置看到撤回；端侧不保留旧正文 |
| UC06 / G-05 转发 | `RelayMessages` | createPosts；目标频道 WS post | 每个目标 Message/Channel | 每个目标 Timeline + Dialog | 各目标各自 Frame；部分结果独立 | Forwarded content、Preview | 客户端不拼多目标 payload/成功状态 |

## 6. 典型原子 Frame

### 6.1 他人发来一条 @我的加急消息

```text
InteractionFrame(transactionId=eventSeq) {
  timeline@channelA: PatchWindow(insert canonical MessageVm)     // 已 attach 才发送
  left-dialog-list@viewer: PatchRow(preview + unread + @ + urgent + move)
  unread-summary@viewer: PatchTotals(...)
  participant-receipts@message: Patch(...)                       // 已 attach 才发送
}
```

### 6.2 创建话题并更新原消息

```text
InteractionFrame(transactionId=createTopicCorrelation) {
  timeline@parent: PatchMessage(root.topicLink = Ready(...))
  left-dialog-list@viewer: PatchRow(topicCount + 1)
  channel-summary@parent: Patch(topicCount + 1)
  topic-list@parent: Insert/ReplaceWindow(...)                   // 已 attach 才发送
}
```

Helix 必须先收敛 `channel_created`、`post_update` 等外部事实，再发布最终 Frame。若需要
过程态，只能由 Helix 产生语义明确的 `creating` VM；前端不得自行把多个 WS 事件拼成
话题关系。

## 7. 客户端 SurfaceRuntime 合同

```text
单一 transport Frame stream
  -> SurfaceRuntime
  -> 按 (surface, scope) 定位强类型 FrameCache slot
  -> revision 校验与原子 apply
  -> readonly Signal<SurfaceVm>
  -> component renderer
```

各端公开 API 必须保留类型关联，而不是向组件泄漏 `unknown`：

```ts
attach<'message.timeline'>(scope): SurfaceHandle<TimelineWindowVm>
attach<'message.left-dialog-list'>(scope): SurfaceHandle<DialogListVm>
```

运行时异构 registry 内部可以使用 type erasure，但只允许位于 decoder/registry 边界；
校验 surface discriminator 后必须进入对应的强类型 reducer。组件不得读取 `unknown`、
`any` 或 raw frame 字节。

本地 overlay 只包括草稿、文件句柄、选择状态、焦点、菜单开闭、抽屉路由和动画；它们
不得改变 FrameCache 的业务字段。用户资料展示通过 Ucenter；成员选择通过既有端侧组件；
二者都不构成 IM 业务 Store。

## 8. 从当前 Emit 迁移的规则

| 当前输入/Emit | 新合同中的位置 | 禁止的端侧行为 |
|---|---|---|
| WS `post` / `posted` | Helix HostObservation，settle Message/Channel 后投影 Frame | 根据 event 名插消息、对账 temporaryId |
| `increment_channel` | Helix 入站增量，更新事实后投影 Dialog/Summary/Roster Frame | 消费 `increment` 决定改未读/预览/排序 |
| `im:post:received/updated/deleted` | 被 Timeline/Thread 的强类型 mutation 取代 | raw payload 进入 MessageStore |
| `im:channel:update/member-updated` | 被 Dialog/Summary/Roster mutation 取代 | 根据 channel id 重新查询或合并 owner/admin |
| `im:channel:replies` | 被 ThreadDetailVm replace/patch 取代 | 前端递归建树、按 reqId 猜模式 |
| `im:read:result` | 仅保留 Helix 内部 read relay；目标端收到 Receipt/Surface VM | 前端解释 body 形成公告/回执/成员 UI |

## 9. 验收与复杂度

每个 UC 的验收需同时覆盖：

1. Command/Effect/HTTP/WS/Storage 的真实链路证据；
2. Helix 给定领域事实后的 projector 与 InteractionFrame fixture；
3. Frame 的 snapshot 与 patch 最终状态等价；
4. PC 与移动端使用同一 schema fixture，机械 apply 后得到相同 surface VM；
5. 双用户场景下，发送者过程态不会泄漏给接收者，双方最终实体、顺序、权限和统计一致；
6. duplicate、out-of-order、stale revision、缺 Frame、重连、too_long 和窗口边界均 fail-closed；
7. 项目级性能断言：单行/单消息 patch 为 `O(1)` 或 `O(k)`（有界窗口），持久查询为
   `O(log n + k)`，禁止无意的 `O(n)` 扫描与 `O(n^2)` 关联。

## 10. UC01-16 外的显式边界

本文只固定 UC01-16。公告完整详情、书签列表、待办、系统通知、模块未读、公司群、
搜索、投票、平均分应在各自产品 surface 成熟后增加，不应伪装成 Message/Channel 客户端
Store。其领域事实仍可与 Channel/Message 关联，但需要独立 scope、窗口和验收合同。
