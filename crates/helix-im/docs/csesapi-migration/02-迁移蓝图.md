# csesapi → 新 Go 空项目 迁移蓝图

> 输入：126 路由清单 + F1（HTTP/鉴权/路由基础设施）+ F2（WS 推送契约 29 事件）+ F3（app/store/ent 依赖面）

### 0.2.2 三条核心数据流（迁移正确性以这三条为准）

**A. 发消息（写扇出，HTTP→Pulsar→异步落库→WS）**
```
POST /api/cses/posts/create
  → handler createPost → app CreateCsesPost
  → 发 Pulsar SenderTopic（同步返回 null，HTTP 即结束）
  → post_consumer 消费 → ent.Tx{ INSERT post + co-tx AppendEvent(alloc seq) }
  → a.Publish WS post/posted 帧（顶层 event_seq）→ Hub 分片扇出
  → 目标用户不在本 pod → cluster/Pulsar 跨 pod 转发
```

**B. 离线同步（读拉取，纯 HTTP pull，不靠 WS 维护最终一致）**
```
客户端按 channel 维护本地 cursor(last_event_seq)
  → POST /api/cses/channel/sync/notify  Body{cursors:[{channelId,fromSeq}]}
  → app SyncChannels → 每 channel syncOne 4 分支:
      no_change(fromSeq≥maxSeq) / events(gap≤500) / slice(饱和) / too_long(gap>5000→resetTo 清表)
  → Resp{entries:[{channelId,kind,events,nextSeq?,resetTo?,messages?}],serverTime}
  → 客户端 dispatch + 推进 cursor(必须 finally，单条抛错不阻塞)
```

**C. 状态变更（写 + WS，co-tx event log）**
```
POST /api/cses/posts/revoke|urgentPost|quickReply|makeTopic|... 或 channel/member 变更
  → ent.Tx{ 业务 UPDATE/DELETE + appendEntPostUpdateEventCoTx/DeleteEventCoTx }
      （lib/pq co-tx 铁律: 前一 rows 必须先 Close 再发下一查询）
  → setEntPostEventSeqProp 注入 post.props.channel_event_seq
  → 事务外 a.Publish post_update 帧（props.channel_event_seq = 客户端 pts gate 主路径）
```

### 0.2.3 顶层设计不变量（迁移红线）

1. **HTTP 码恒 200**，成败靠 `dto.CommonRes.status`；唯一例外 personal_guard 403
2. **cookieId == Token == UserId** 三等式；userId 从 `userId` header 回落 `cookieId` header
3. **wire 双格式**：HTTP camelCase / WS snake_case；`createAt`(非 createdAt) / `eventType` 数字枚举 / omitempty
4. **co-tx exactly-1**：每个 mutation 在同一 ent.Tx 内 INSERT 业务行 + INSERT 恰好 1 条 channel_event
5. **event_seq 解耦业务 seq**：sync cursor 用 append-only `channel_event.event_seq`，不用 `post.seq`
6. **WS 照抄**：Hub 分片 / web_conn ShouldSendEvent（cses 走 `ResolveBroadcastViewerUserIds` 双路径单一真源）/ cluster trace 还原 / 仅 2 个 BroadcastHook(add_mentions/add_followers) 一字不改
7. **表名单数**：`channel`/`post`/`channel_member`，不是复数
8. **PG 手动 DDL**：channel_event 分区 + alloc_channel_event_seq 函数启动不自动跑，每环境手动执行

### 1.2 HTTP 层框架选型权衡

| 候选 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| **gorilla/mux** | **零迁移成本**，路由形态 1:1 保留，`Routes` 结构体 19 子路由 + `PathPrefix().Subrouter()` 原样照搬，`mux.Vars` 路径参数语义不变，团队已熟悉 | 已 archived（但 API 冻结、功能稳定、社区仍可用），无原生中间件链（沿用现有 `APIHandler` 包装即可） | ✅ **选定** |
| chi | 轻量、`net/http` 兼容、中间件链优雅、活跃维护 | 需重写全部路由注册 + 子路由 `Mount`，迁移期引入额外改动面 | ✗ |
| gin/echo | 生态大、性能好、binding 自带 | 自带 `gin.Context` 与 mattermost `*web.Context`/`*http.Request` 范式冲突，`WriteJSON`/dto 信封要重适配，WS 升级要 `gin.WrapH`，反增摩擦 | ✗ |

**结论（2026-06-05 用户拍板）**：用 **gorilla/mux**。理由：
- 本次是**搬运现有代码**而非新写服务，决策标准 = 保留最多现有契约、改动面最小 → gorilla 是「零摩擦」选项
- `srv.Router.PathPrefix("/api/cses").Subrouter()` + 各子路由器写法 **1:1 照搬**，`api.go` 的 `Routes` 结构体与 `Init*()` 注册几乎原样迁过去
- `mux.Vars(r)["channelId"]` 路径参数语义不变（`{botUserId}`/`{channelId}`/`{team_id}` 端点无需改）
- 现有 `APIHandler` 包装（RequireSession=false + Cses-Track-Id 透传 + gzip）继续作为「事实中间件」复用，不依赖框架原生中间件链
- archived 风险可接受：mux API 已冻结、无破坏性变更，相比迁 chi 的改动面，保留 gorilla 收益更高（迁移完成、新项目稳定后若需要可再独立评估换框架）

**不可换的契约（无论选哪个框架都必须复刻，来自 F1）**：
1. HTTP 状态码固定 **200**（业务成败靠 `status` 字段；唯一例外 personal_guard 403）
2. 响应信封 `{"status":"SUCCESS|failed|FINISH","message":...,"data":...}`，message/data omitempty
3. `WriteJSON(w, dto)` 是唯一写回入口（Content-Type: application/json）
4. 根前缀 `/api/cses`，19 个子路由前缀保持不变

### 1.3 dto 信封层（不可变契约）

```go
// status 枚举三值
const (
    StatusSuccess = "SUCCESS"
    StatusFailure = "failed"   // 注意：是 "failed" 不是 "FALSE"/"FAILURE"
    StatusFinish  = "FINISH"
)
type CommonRes struct {
    Status  string `json:"status"`
    Message string `json:"message,omitempty"`
    Data    any    `json:"data,omitempty"`
}
```
流式构造 `NewCommonRes().SetSuccess().SetData(x)` / `.SetFailure().SetMessageByErr(err)` 全部保留。

### 1.4 鉴权中间件（不可变契约，来自 F1 §5）

入站解析顺序必须 1:1 复刻：
- **userId**：`userId` header > `cookieId` header（CSES iOS 实际路径，回落）
- **companyId**：`companyId` header > `teamId` header（向后兼容别名）
- **token**：`X-Bot-Token` > `Authorization: Bearer mp_*` > Cookie `MMAUTHTOKEN` > `Cookieid` header
- session 三等式：`session.CookieId == session.Token == session.UserId`
- `session.UserId` 的 JSON tag 是 `"id"`（坑：字段名≠tag）
- personal user 判定：`session.CompanyId == ""` → 403 + `{"status":"failed","message":"PERSONAL_USER_FORBIDDEN"}`
- Bot Token 分支：`mp_` 前缀 token 走 `ResolveBotToken`，不查 Redis UserData；BotAgentTokenAuth 中间件在 Context 注入 `*ent.BotAgentConfig`（bot-agent 调用接口依赖，不能丢）

## 2. 需要带过去的 ent schema 全集

### 2.1 CSES Fork 命名陷阱（迁移前必读）

| 陷阱 | 说明 | 后果 |
|---|---|---|
| **表名单数** | ent 表是 `channel` / `post` / `channel_member`，**不是** mattermost 原版的 `channels` / `posts` / `channelmembers` | grep/migration 写错表名 → 全表查空 |
| **channelmembers 扩展字段** | `channel_member` 表加了 CSES 专属列：`last_read_seq` / `phantom_count` / `phantom_at_read`（离线同步 v2 游标 + phantom 抵消） | 漏迁 → sync cursor 永远卡 0 / badge 误清 |
| **channel_event 事件日志** | append-only 事件表，16 HASH 分区 + per-channel PG sequence 函数 `alloc_channel_event_seq`（CACHE 1） | 漏迁函数/分区 DDL → 离线同步整条链路死 |
| **双写陷阱** | `UpdateCsesChannelPicture` / `GetUserStatusesByIds` / createUser 等少量路径仍走 **原版 mattermost store**（原版 `channels`/`Status`/`Users` 表） | 只迁 CSES ent 不迁原版 store → 这几个端点 panic |
| **post.props 注入 event_seq** | co-tx AppendEvent 后把 `channel_event_seq` 注入 `post.Props`，随 WS 帧带给客户端 pts gate | 漏注 → 客户端 cursor 无法推进 |

### 2.2 ent 表全集（31 张，新项目 schema 集合）

**频道域**（含扩展字段，HIGH 风险）：
- `channel`（扩展：approval_enabled / mention_permission / top_permission / notice_permission / close / source(JSON) / orient / has_schedule_post）


### 3.3 channel_event 离线同步链路（HIGH，核心）

```
写路径（每个 mutation handler）:
  ent.Tx 内 → 业务写 + appendEntPostUpdateEventCoTx/appendEntPostDeleteEventCoTx（co-tx AllocSeqAndInsert）
            → setEntPostEventSeqProp 注入 post.Props[channel_event_seq]
  事务外 → a.Publish WS 帧（携带 event_seq / props.channel_event_seq）

读路径（拉取，非推送）:
  POST /api/cses/channel/sync/notify → SyncChannels → syncOne 4 分支决策树
```

**co-tx 铁律**（来自 decisions/2026-05-29-libpq）：lib/pq 同 tx 发下一查询前，前一个 `rows` 必须先 `Close()`（不能只 defer）；参数化 SQL 禁多语句/尾分号。QuickReply 的 raw jsonb_set 路径：`rows.Close()` 必须在 `appendEntPostUpdateEventCoTx` 之前。

### 3.4 event_seq 注入规则（pts gate）

- `post`/`posted`/`posts_update`：顶层 `event_seq` 字段
- `post_update`：`post.Props.channel_event_seq`（客户端 pts gate 主路径），MakeTopic 额外注顶层 `eventSeq` + `source:"make_topic"`
- `increment_channel`：`lastEventSeq` 字段（sync cursor 初始值）

## 5. 端到端验证策略

### 5.1 httpexpect 接口对拍（HTTP 层）
- 旧服务（mattermost csesapi）与新服务并行起，同一组请求双发

- 边界：personal_user 403、空 userIds 裸 null、searchType nil guard（旧代码 panic 点，新代码必须修）

### 5.2 wsmonitor WS 对拍（推送层）
- 同一业务动作触发后，对比新旧 WS 帧：事件 type、广播范围（channel/user/users 多播）、payload 字段集
- 重点：E16 increment_channel 全字段（~40 字段）、E20 update_channel 的 9 种 payload 形态、event_seq 注入位置（顶层 vs props.channel_event_seq）
- BroadcastHook：仅验 `posted` 的 mentions/followers 连接级注入

### 5.3 sync 协议 4 分支（离线同步核心）
| Kind | 触发条件 | 验证点 |
|---|---|---|
| `no_change` | fromSeq == maxSeq | entries 空 events，无 messages |
| `events` | gap ≤ 阈值 | events 数组 + nextSeq + Messages map（viewers 过滤 + sender 豁免） |
| `snapshot` | 保留未激活 | 当前不触发（注释保留 viewers-edit 场景） |
| `too_long` | gap > SyncGapTooLongThreshold(5000) | resetTo 字段，客户端清表重拉首屏 |

- 客户端 cursor 推进 + persist + buffer 清理必须 finally（单条 dispatch 抛错不阻塞 cursor，否则 sync 风暴）

## 6. Tauri/Rust 接管的接口契约交付物清单

> 每个 keep 路由的 req/resp wire 形态 = Rust 侧需复刻的契约。两铁律：**HTTP camelCase / WS snake_case**；三坑：`createAt`(非 createdAt) / `eventType` 数字枚举 / `omitempty`。

### 6.1 交付物结构（每个 keep 路由一条）
对每个 keep 路由，交付 Rust 侧需要的：
- 路径 + method
- 请求体 wire 形态（JSON 字段名 + 类型 + 必填/可选 + omitempty）
- 响应体 wire 形态（`{status, message, data}` 信封 + data 内层结构）
- 是否触发 WS（触发哪些事件 type + 客户端需消费的字段，尤其 event_seq/channel_event_seq）
- 鉴权要求（user session / bot mp_token / 无鉴权）

### 6.2 高优先交付（Tauri 接管首批，离线同步 + 收发消息）
| 路由 | req wire | resp data wire | WS 消费 |
|---|---|---|---|
| `POST /channel/sync/notify` | `{cursors:[{channelId,fromSeq}]}` | `{entries:[{channelId,kind,events,nextSeq?,resetTo?,messages?}],serverTime}` | 无（纯 pull） |
| `POST /posts/create` | `entity.Post{channelId,userId,type,message,temporaryId,createAt,props}` | null（Pulsar 异步） | E01 post / E02 posted（带 event_seq） |
| `POST /channels/load/increment` | `{timestamp?,ChannelId?}` | null（异步） | E16 increment_channel（lastEventSeq）+ E17 end |
| `POST /channel/load/incrementByChannelId` | `{channelId}` | `*IncrementChannel`（~40 字段全集） | 无 |
| `POST /channels/view` | `{channels:[{id,isRoot?}]}` | null | E20 update_channel（清 badge） |
| `POST /post/read` | `{channelId,endTime?,posts,startTime?,userId?}` | null | E11 post_read + E20 |
| `POST /posts/revoke` | `{postId}` | null | E04 post_update + E20（lastPost JSON string） |
| `POST /posts/postContext` | `{postId,before}` | `*entity.Posts` | 无 |
| `POST /posts/getLatestPost` | `{channelId,timestamp(unused)}` | `[]*ent.Post`（segment 去重） | 无 |

### 6.3 Rust 复刻必知坑（来自 MEMORY + decisions）
- **self-message 空 id**：用户自己发的消息本地 SQLite id 列为空串（仅 temporary_id）；任何 message.id-keyed 逻辑会断；锚点须 `messages.find(m=>m.id)`
- **IncrementChannel.lastPost** 是 JSON string 不是 object（revoke 的 update_channel 同）
- **eventType 数字枚举**：reply/create=1（new 非 edit），edit=2，delete=3
- **Cses-Track-Id**：HTTP header → 响应头回写；WS envelope key `csesTrackId`；64 字符截断
- **wire 契约单一真源**：`docs/cses-im-spec/wire-contract.md` + cses-client `types/sync.ts`，改序列化前必读

### 6.4 全量交付建议
其余 ~90 个 keep 路由按 §6.1 模板逐条生成（建议产出独立 `03-rust-wire-contract.md`，按业务域分组：channel / post / announcement / bookmark / notification / bot-manage / bot-agent / search / user / team / modules）。优先级：Phase 1-4 的 keep 路由先交付，Phase 5 bot/agent 后交付。
