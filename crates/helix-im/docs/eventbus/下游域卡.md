## §0 反推判据（每张卡的"反推校验"行必须过）

> 「一个下游域，只拿到这条事件本身（不查 DB、不调接口、不回问 core/im），能不能完成它的工作？」
> 能 → 卡成立；不能 → 缺的字段就是 §3 信封契约要补的。

## §1 现状 vs 契约（域卡里字段的两种来源，别混）

| 字段 | 现网 `im:__bus__` 信封是否已有 | 来源 |
|---|---|---|
| `event`（= type） | ✅ 有 | `to_effect.rs` 各 emit |
| `data.channel_id` / `connection_id` / `server_msg_id` / `temporary_id` | ✅ 有（按事件） | 各 emit payload |
| `data.increment.{mentionList, urgentPostList}` | ✅ 有（`im:channel:increment` 透传） | `emit_channel_increment` |
| `v`（信封版本） / `actor` / `ts` / `event_seq` / `causation_id` | ✅ **已定必填**（2026-06-16 决议补字段；信封落地中） | 能力契约 §3.1 |

> 卡中标 `[现]` = 现网已有可直接消费；标 `[待]` = 字段**已定必填**但信封尚未落到 `to_effect.rs` emit，当前仍需降级（落地后清零）。

## §3 域卡

### 域卡 D-01 · 系统通知域
- 职责：消息到达时弹窗 / 横幅 / 声音
- 订阅：type ∈ {`im:post:received`, `im:channel:increment`}，scope = 当前 tenant
- 消费信封字段：`event` [现]、`data.channel_id` [现]、`data.server_msg_id` [现]、`actor` [待]、`ts` [待]
- relevance 算法（域自己持 me）：通常"非我发的才弹" → `actor != me`（依赖 `actor` [待]；未补前降级为"全弹/按 channel 静音设置弹"）
- 缺字段降级：无 `actor` → 退化为按 channel 通知开关决定，不回 core 问"谁发的"
- catch-up：通知是即时性的，**不 replay 历史**（掉线期间的旧消息不补弹，避免重连风暴）
- 不做什么：不改未读数（D-03 的事）、不进 @我流（D-02 的事）
- 反推校验：⚠️ "非我发才弹"需 `actor`（[待]）；其余可干

### 域卡 D-02 · @我 / 与我相关域
- 职责：把"@我 / 紧急 / 回复我"聚合成一条流 + 全局红点
- 订阅：type ∈ {`im:channel:increment`, `im:post:received`}，scope = 当前 tenant
- 消费信封字段：`event` [现]、`data.channel_id` [现]、`data.increment.mentionList` [现]、`data.increment.urgentPostList` [现]、`event_seq` [待]
- relevance 算法（域自己持 me）：`mentionList.contains(me) ∨ (me ∈ urgentPostList 目标)`；reply/assignee 等扩展字段进 payload 后再加 `∨ reply_to.author == me`
- 缺字段降级：payload 无 `mentionList` → 该条不进 @我流（**不回 core 补**，符合 IM 不变量"handle 纯函数"）
- catch-up：掉线重连从 last `event_seq` [待] replay；去重键 `(type, channel_id, msg_id)`
- 不做什么：不弹窗（D-01）、不做未读总数（D-03）；只管"与我相关"的聚合
- 反推校验：✅ mentionList/urgentPostList 已透传，持 me 即可算（catch-up 需 `event_seq` [待]）

### 域卡 D-03 · 未读徽章域
- 职责：per-channel + 全局未读计数
- 订阅：type ∈ {`im:channel:increment`, `im:channel:update`}，scope = 当前 tenant
- 消费信封字段：`event` [现]、`data.channel_id` [现]、`data.increment`（增量条目）[现]
- relevance 算法：不涉及"与我相关"（未读是 channel 级聚合，非 per-me 判定）
- 缺字段降级：`im:channel:update`（子 topic 批次结束信号）到达即"该 channel 本批增量收完"，据此结算计数；缺增量明细 → 标记 channel 脏、按 cursor 对账，不臆造数字
- catch-up：未读是**派生态**，重连后由同步链路（cursor / `im:channels:loaded`）重算，不靠事件 replay 累加（避免重复计数）
- 不做什么：不弹窗、不进 @我流；只算数字
- 反推校验：✅ channel_id + 增量足够算 per-channel 未读

### 域卡 D-04 · 生命周期 / 连接状态域
- 职责：显示"连接中 / 已就绪 / 断线 / 需重拉首屏"
- 订阅：type ∈ {`im:connection:established`, `im:channels:loaded`, `im:sync:too_long`}
- 消费信封字段：`event` [现]、`data.connection_id` [现，established]、`data.channel_id` [现，too_long]
- relevance 算法：不涉及（全局/连接级状态，非 per-me）
- 缺字段降级：`im:sync:too_long` 到达 → 触发"清内存 buffer + 重拉首屏"（对齐 IM 不变量"too_long 清内存不清表"）；无需额外字段
- catch-up：连接态是**当前快照**语义，不 replay；重连后以最新一条 established/too_long 为准
- 不做什么：不算未读、不弹消息通知；只反映链路健康
- 反推校验：✅ 事件本身即状态信号，无需回调

### 域卡 D-05 · 运维域　🚫 已下线（不做 · 2026-06-16 决议）

> **决议**：运维消息（`im:ops:*` / 强制下线 / 限流 / 公告）**移出 helix EventBus roadmap**——不立 ADR、不做域卡。
> **理由**：① 现网 cses-client 也**未实现**独立 ops 事件族（强制下线 / 限流均无证据，见 [`场景全集.md`](./场景全集.md) §3.5）；② 现存运维场景（token 过期 401 / 503 维护 / 版本更新 / 下载进度）走各自现成机制（HTTP interceptor / `UpdateService`），不需要新总线；③ 不为未启动的能力预建框架（GOAL §2）。
> **重启条件**：若未来产品确需服务端主动运维推送（如强制下线），先新增 ADR 定义 `im:ops:*` 事件 type + PUB/REP 归属 + 信封上下文，再复活本卡。tombstone 保留防反复重提。

## §4 跨域不变量（防职责越界）

| 只有这个域能做 | 域 |
|---|---|
| 弹窗 / 横幅 / 声音 | D-01 系统通知 |
| "与我相关"聚合 + 红点 | D-02 @我 |
| 未读数字 | D-03 徽章 |
| 连接/链路状态 | D-04 生命周期 |

> 一条事件可被多域同时消费（一次操作扇出无限内容），但**每个语义只允许一个域负责**——D-01 不许改未读、D-03 不许弹窗，否则双写打架。
