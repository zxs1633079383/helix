# helix · 任务/进度模块 EventBus 域卡（独立模块事件契约）

> ⚠️ **placement**：这是**未来独立业务模块 `helix-task`** 的事件契约，非 IM 一部分；暂存于此，模块立项后迁到 `crates/helix-task/docs/`。
> 来源：cses-client 任务域实挖（全量 25 场景见 [`场景全集.md`](./场景全集.md) §2.2）。
> 统一信封见能力契约 [§3.1](../../../../docs/过会方案/helix-eventbus-设计.md)；relevance 各下游域自己算（模块只透传原始字段）。

---

## §0 模块职责

任务/进度模块产出"任务被指派、状态流转、截止、评论@我、检查点验收"等事件，喂给通知域 / @我域 / 未读域 / 任务列表域。
> OKR 不是独立模块——现网 `/pages/okr` 仅 UI 抽屉，复用任务事件，不单列。

## §1 现网三通道（helix 要统一收口为一套 EventSink）

| 现网通道 | 用途 | helix 归一 |
|---|---|---|
| HTTP 系统通知 `{id,type:'task',operation,content,members[]}` | 红点/桌面通知 | `Effect::Emit`（PUB） |
| `dataPilot-dataChange` WS `{mode,pk:taskId,body}`（80ms 批） | 列表实时增删改 | `Effect::Emit`（PUB），批次=一个 step（HX-C007） |
| 内存 `TaskEventBus`（RxJS） | 组件间通信 | **不进 helix EventBus**（域内本地） |

## §2 产出事件清单（建议 helix type；触发与字段对齐现网）

| 场景 | 建议 type | 方向 | 关键 payload | relevance 原始字段 | 喂给下游域 |
|---|---|---|---|---|---|
| 任务指派给我 | `task:assigned` | PUB | taskId,title,leaderIds,members,creatorId | `members`/`leaderIds` | 通知/@我 |
| 状态变更 | `task:status-changed` | PUB | taskId,oldStatus,newStatus | — | 未读/列表 |
| 截止提醒 | `task:deadline-near` | PUB | taskId,title,stopTime | (定向 me) | 通知 |
| 评论/@我 | `task:commented` | PUB | taskId,content,mentions[] | `mentions` | @我 |
| 个人完成/取消 | `task:member-completed` | PUB | taskId,memberId | (定向 me) | 通知 |
| 催办(他人拒绝) | `task:member-rejected` | PUB | taskId,memberName,reason | (定向 me) | @我/通知 |
| 成员添加/移除 | `task:member-changed` | PUB | taskId,members[],leaders[] | `members`/`leaders` | @我/列表 |
| 检查点验收/拒绝 | `task:checkpoint-*` | PUB | taskId,checkpointId | (定向 me) | @我/通知 |
| 任务接受/拒绝/撤销 | `task:member-*` | PUB | taskId | (定向 me) | 通知 |
| 字段/时间/优先级/标签/依赖变更 | `task:field-changed` | PUB | taskId,field,newValue,oldValue | — | 列表 |
| 看板卡片移动 | `task:moved` | PUB | taskId,statusId | — | 列表 |
| 实时列表增删改 | `task:list-changed` | PUB | mode,pk,body | — | 列表 |
| 创建/删除 | `task:created`/`:deleted` | PUB | taskId / ids[] | — | 列表 |

## §3 REP 双向

现网任务**无 server-push 式 REP**；二次确认（删除/放弃任务）走 UI `NzModalService.confirm` = REP 方向①（core 问 UI 拍板），与会议同构。无"申请→批准"链。

## §4 relevance 原始字段透传清单（模块必填，下游自己算 @我）

`members[]` / `leaderIds[]` / `mentions[]` / `assigneeId` / 定向通知的 `recipients[]`——缺即下游算不出"指派我/@我/催我"。

## §5 catch-up & 缺口

- catch-up：任务列表是派生态，重连后 HTTP `loadTaskList()` 重算，不靠事件 replay 累加；但**通知/红点**需 `event_seq` 补齐漏掉的指派/催办。
- 现网缺口：通知靠 HTTP 系统通知（非长连推送），离线期可能漏——helix 统一 EventBus + catch-up 可补。

## §6 反推校验

✅ 指派/状态/截止/评论事件带 taskId + 上述 relevance 字段，下游持 me 即可算"与我相关"，无需回调。⚠️ 依赖信封补 `actor`（谁指派的）+ `event_seq`（catch-up）。
