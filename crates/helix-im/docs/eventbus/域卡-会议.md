> ⚠️ **placement**：未来独立模块 **`helix-meeting`** 的事件契约；暂存于此，立项后迁 `crates/helix-meeting/docs/`。
> 来源：cses-client 会议域实挖（全量 40 PUB + 5 REP 见 [`场景全集.md`](./场景全集.md) §2.3 / §4.1）。
> 统一信封见能力契约 [§3.1](../../../../docs/过会方案/helix-eventbus-设计.md)。
> **会议是 helix REP 模式的最佳范例库**——5 个标准"申请→批准"闭环。

---

## §0 模块职责

会议模块产出会议全生命周期事件（开始/结束/成员进出/权限/呼叫/投票/提问/媒体状态），并承载 helix 里**最完整的 REP 双向交互**。

## §1 现网通道

| 通道 | 用途 | helix 归一 |
|---|---|---|
| `EventBusService.use('Meeting').on(meetingId)` action 分发 | 会议内全部广播 | `Effect::Emit`（PUB），scope=meetingId |
| HTTP POST `accept*/refuse*/apply*` | REP 响应 | `Effect::Request`/`Reply` + corr |
| Tauri 弹窗 `meeting-remind`/`callJoin-remind` | 入会/呼叫提醒 | PUB → 通知域 |

## §2 产出事件清单（PUB，按族；全 40 项见场景全集 §2.3）

| 事件族 | 代表 action | 关键 payload | 喂给下游域 |
|---|---|---|---|
| 会议生命周期 | startMeeting/endMeeting/cancelMeeting/updateMeetingConfig | meeting{}/config{} | 生命周期/通知 |
| 成员进出 | joinMeeting/leave/removeMember | user,isReconnect | 成员列表 |
| 角色 | assignModerator/assignCoModerator/revokeModerator | newModerator/userId | 成员/权限 |
| 呼叫 | meetingCall/callTimeOut/refuseCall/cancelCall | users[] | 通知（呼叫我=与我相关） |
| 媒体状态 | turnCamera/turnMicrophone/screenSharing | memberMsg,isOpen* | 媒体 UI |
| 互动 | addMeetingUserLike/meetingAddQuestion/pinQuestion | user,emoji,question | 互动 UI |
| OKR 流程 | startVote/stopVote/startWriteKr/remindWriteKR/remindVote | krTitle,members[] | 提醒（提醒我=与我相关） |
| 提醒(弹窗) | meeting-remind/callJoin-remind | startTime | 通知 |

## §3 REP 双向闭环（★ 核心，5 个）

| 场景 | 发起→等待 | 请求 | 响应 | helix 方向 |
|---|---|---|---|---|
| 会议邀请确认 | 主持人→被邀请者 | `invitedUsersNeedConfirm` | HTTP `acceptInvitedUsersConfirm`/`refuse` | 方向① |
| 入会申请批准 | 参与者→主持人 | `applyJoin` | HTTP `acceptApply`/`refuseApplies` | 方向① |
| 开麦申请批准 | 参与者→主持人 | `applyOpenMicrophone` | HTTP `accept`/`refuseOpenMicrophone` | 方向① |
| 开麦邀请反馈 | 主持人→参与者 | `inviteOpenMicrophone` | HTTP `feedbackOpenMicrophoneInvite{accept}` | 方向① |
| 本地录制批准 | 参与者→主持人 | `applyLocalRecord` | HTTP `accept`/`refuseLocalRecord` | 方向① |

> **机制**：申请方发请求 → server 广播待批 action → 对端 HTTP 响应 → server 广播结果 action。**对应 helix `Effect::Request{corr}` → `Tick::PortReply{corr}`**。
> **超时兜底是刚需**：现网 `callTimeOut` 实证"被呼叫者不响应"必须有超时分支——对齐 REP 文档 §3.2「用户不点→`ScheduleTimer` 兜底」。

## §4 relevance 原始字段透传清单

`invitor`/`members[]`（邀请我）、`users[]`（呼叫我/批我）、`user`（申请者）——下游据此算"这个申请/呼叫/邀请是不是冲我来的"。

## §5 catch-up & 缺口

- catch-up：会议是**强在场**语义，断线重连用 `isReconnect` 重取当前快照，不 replay 历史 action。
- 缺口：会议改期（reschedule）无独立 action（隐含在 updateMeeting）；日历级"15min 前提醒"在会议模块外——helix 立 meeting 模块时需补。

## §6 反推校验

✅ PUB 事件带 meetingId + user/members，下游可干。✅ REP 闭环天然带 corr 语义（申请 id），完美映射 helix corr_map。⚠️ 依赖信封 `event_seq` 仅用于审计（在场态不 replay）。
