# G02-G03a - 文档、媒体、上传过程态与重试

> 状态：终局 V2 合同。G03 的 Rust→Java Prepare → 流式 OSS PUT → Rust→Java Verify → Rust→Go CreatePost、文件进度和失败恢复已落地；multipart/断点续传仍 deferred。

## 1. 共用原则

G02、G03 与 G01 共用 `message.composer` 的稳定 `message.create` capability 和 `im.message-content.v2` 输入合同。区别只能在 `content.kind` 的 codec、effect plan、过程态和最终 `MessageContentVm`；不能为每一种内容给 Composer 根 VM 增字段。

```text
message.create
  + content.kind=document -> G02
  + content.kind=media    -> G03
  + same actionRef / channel scope / epoch validation
```

## 2. G02 - 文档消息

| 层 | 完整合同 |
|---|---|
| ActionBinding | `message.create`，输入 content kind=`document`；只允许 Helix policy 已提供的 document reference。 |
| Command Tick | 校验 binding、document reference、访问权、reply；创建 temporary Message。 |
| Effects | `PersistAtomic(temporary document Message + PendingSend)` -> PersistOk 后 `Http(CreatePost)` + timeout。 |
| 过程 Row | `MessageRowVm.content=Document{documentId,title,summary,access}`，`delivery=Sending`。 |
| Composer | timeline + dialog；已打开 thread 时条件更新。发送者不改自己的 unread。 |
| Echo | canonical document facts PersistOk 后将同一逻辑行 settle 到 `Sent`。 |
| UI | PC/Mobile renderer 以 document semantic renderer key 画卡片；不解 raw `props.document`。 |

## 3. G03 - 媒体/文件消息

### 3.1 本轮明确的边界

文件选择、操作系统句柄与权限令牌属于 host/driver 能力；上传主体由 driver 以固定缓冲流式读取，不把整文件读入内存。前端必须分别注入 Go `api_base_url` 与 Java `default_api_base_url=env.restHost`；Rust 直连 Java `/oss/getPresignedUrl` 与 `/oss/completeMediaUpload`，最终 `/posts/create` 才走 Go，两个 base 可以不同 origin 且不得互相推导。multipart/断点续传仍 deferred，不能把浏览器 `File`、FFI pointer 或 raw upload props 传进 VM/Frame。

### 3.2 已落地的 typed 合同

```text
HostObservation::SelectedAttachment(opaque host reference)
  -> Helix validates policy
  -> temporary Message { content=MediaPending, delivery=FILE Uploading / IMAGE Sending }
  -> PersistAtomic(Message + pending_media prepare journal) -> PersistOk -> timeline/dialog Frame
  -> Effect::Http(Java Prepare) / UploadFile(OSS PUT) / Http(Java Verify) / Http(Go CreatePost)
  -> PortProgress(corr, bytes) -> 5% latest-wins Persist -> PersistOk -> Frame
  -> terminal PortReply consumes corr
  -> WS canonical echo -> Sent Frame
```

| 数据 | V2 目标类型 |
|---|---|
| 输入 | `MediaInputRef`，版本化、host opaque、不可直接渲染。 |
| 过程内容 | `MediaPendingVm { mediaKind, displayName }`。 |
| 过程 delivery | `FILE` 为 `Uploading { progressPercent }`；`IMAGE` 沿用整条消息 `Sending` 转圈，不展示百分比。 |
| 最终内容 | `Media { resource, thumbnail?, fileName, size, availability }`，所有字段为 typed union。 |
| 影响 Surface | timeline、dialog，条件 thread；上传进度不会让 composer actionRef 重签。 |

文件进度只更新所属 message 行：driver 每 64 KiB 流式读取，但 host 只在跨过 5% 桶时回灌；Helix 同一时刻最多保留一个进度 Persist，在途期间只覆盖一个最新待提交值。retry PUT 启动时同时冻结 action 授权的 window token 与 causation，后续进度 readback 不得退回 `latest`。图片策略固定为 `Disabled`，不会产生进度 Tick。端侧不得自行猜进度。

`PortProgress` 只 peek correlation，不消费；同 corr 的最终 `PortReply` 才结束 PUT。进度列为 `message.upload_progress_percent`，只做按 `temporary_id` 的单行 `BatchUpdate`，禁止逐块 JSON read-modify-write。PUT 的成功回执若先于某笔进度 Persist 回执到达，终态必须暂存到该进度回执完成后再推进，避免旧百分比跨 worker 反向覆盖 100%。

### 3.3 类型、数量与凭据边界

- 图文出站类型固定为 `IMAGE`，文件固定为 `FILE`；兼容入站旧别名 `rich`/`file`，但不得继续向 Go 发送小写类型。
- `IMAGE`/`rich` 的唯一现网字段为 `props.files[1..=9] + props.imagePosition(top|bottom)`；canonical 输入、SQLite props、Complete 回填、retry target 与 `/posts/create` 全程保持该形状。禁止双写历史 `images/textPosition`。
- `FILE` 只接受 `props.file`，出现 `props.files` 必须在任何 Effect 产生前失败关闭，避免单文件与图片集合语义混用。
- 单条图文必须包含 1..=9 张图；第 10 张在任何 Effect 产生前失败关闭。
- 九张图的 Java prepare 必须在一个 Effect 批次吐给 host 并发执行；图片策略固定为整条 Sending，不发逐图百分比。
- UI 只提交 `localPath/fileName/contentType/size/sha256`。Java 用服务端 HMAC 密钥、登录用户与稳定 `clientUploadId` 生成不可预测的 owner-bound `fileId/objectKey`，并返回绑定完整性声明的 `uploadToken`；UI/Rust 不选择 bucket、key 或 TTL。
- `pending_media` 只持久化恢复所需的业务标识、uploadToken 与阶段。预签名 PUT URL、签名 headers 永远写空，不跨进程保存；token 不进入公开 props，并在 storage/HTTP 日志边界脱敏。
- 首次发送必须用同一 `PersistAtomic` 提交临时 message 与 prepare journal；事务失败后的
  `unsend` 补偿仍要把 message 与原始 prepare journal 原子写回。这样补偿后即使进程重启，
  retry 也只能恢复 journal 并重新走 Java prepare，不会把未 verify 的 props 直发 Go。
- PUT 失败或进程在 PUT 阶段重启，一律回到 Prepare 获取新签名；Java 会删除同身份下未 completed 的模糊成功对象后再签 forbid-overwrite URL。只有已确认 PUT 成功的 Verify 阶段可按原 `fileId/objectKey/uploadToken` 重试 Verify；completed 对象禁止再 Prepare 覆盖。
- verify 必须验 uploadToken 并对拍 OSS 实际 `contentLength/contentType/sha256`，成功后写 completed marker；最终消息只保存 Java `/oss/media/object/{fileId}` 稳定 URL，该路由仅对 completed 对象 302 到短时 GET 签名。

## 4. G03a - 重试失败消息

`retrySend` 不在 composer capability catalog 中，而在失败 `MessageRowVm.actions` 中：它必须绑定具体 `temporaryId`、失败原因和 retry policy。

```text
MessageRowVm { id=T, delivery=Failed{retryable=true}, actions=[retrySend(T)] }
  -> ActionInvocationEnvelope(surface=message.timeline, scope=window, actionRef=retrySend)
  -> Tick::Command
  -> PersistAtomic(same T, delivery=Sending, retry attempt)
  -> PersistOk -> timeline/dialog Frame
  -> existing upload/create plan
  -> echo -> same T settle Sent
```

禁止 retry 创建第二个消息行、第二个 temporaryId 或前端复制原文重新调用 `message.create`。若 retry policy 不允许，binding 不下发或 `enabled=false` 并带 typed disabled reason。

`retry` binding 只接受空 input。action registry 先完成 actor/scope/revision 校验，prepare 阶段只构造 canonical `im_retry_send {message_id, req_id}`；只有 registry receipt 已提交为 `Accepted` 后才能执行本地 retry。`req_id` 与 action 授权的 timeline window token 一并写入 `PendingSend`，retry 的 `Sending/Uploading` PersistOk readback Frame 携带同一 causation 并返回同一 window，Frame 发出后才释放 action in-flight ledger；后续成功或再次失败的终态 Frame 继续沿用该 causation 与 window。

## 5. Frame 与 UI

| 事实提交 | Frame mutation | PC/Mobile 呈现 |
|---|---|---|
| document PersistOk | timeline/dialog replaceView，row=`Document + Sending` | 文档卡 + 发送中。 |
| media prepare PersistOk | timeline/dialog row=`MediaPending + Uploading(0)` | 媒体占位与进度。 |
| file progress PersistOk | 所属窗口 row progress 更新 | 文件显示 5% 步进，不重建业务排序。 |
| image prepare/PUT | 整条 row 保持 Sending | 图文整条消息转圈，无图片百分比。 |
| retry PersistOk | 同一 row `Failed -> Sending/Uploading` | 失败按钮收起，恢复过程态。 |
| canonical echo PersistOk | 同一 row `Sent + final content` | 最终内容卡。 |

所有 Frame 仍走 `03` 的整帧校验、原子 apply、ack/resync。multipart/断点续传后续若引入，也不得改变上述进度、凭据与 retry 边界。
