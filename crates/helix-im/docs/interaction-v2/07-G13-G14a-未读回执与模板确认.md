# G13-G14a - 未读、回执与模板确认

> 状态：终局 V2 合同。读状态是已提交的用户事实，不是客户端看过一眼就可自行修改的 UI 本地变量。

## 1. 三类状态不能混成一个计数

| 领域事实 | 归属 | 典型呈现 | 不可混淆之处 |
|---|---|---|---|
| `ViewerChannelState` | 某用户在某频道 | dialog 未读角标、全局未读、first unread | 只代表“我”对频道读到哪里。 |
| `MessageReceiptState` | 某用户对某条消息 | 消息行已读摘要、参与者回执明细 | 是逐条、逐人的消息事实。 |
| `TemplateConfirmationState` | 某用户对要求确认的模板消息 | “已确认/待确认”、确认明细 | 业务确认不是阅读；读过不等于确认。 |

`message.unread-summary` 只投影第一类聚合；`message.participant-receipts` 只投影第二、三类的明细。`MessageRowVmV2` 可带自己的摘要，不把整个成员列表塞进 timeline 行。

```rust
struct MessageIndicatorsVm {
    receipt_summary: Option<ReceiptSummaryVm>,
    template_confirmation: Option<TemplateConfirmationSummaryVm>,
    urgency: Option<UrgencyVm>,
}

struct ParticipantReceiptsVm {
    message: ReceiptMessageContextVm,
    items: Vec<ParticipantReceiptRowVm>,
    page: PageVm,
}
```

一条 `ParticipantReceiptRowVm` 用 `state: read | unread | confirmed | pending_confirmation` 表示该成员对该消息的状态；不要维护同一批成员的 `read_items + unread_items` 或 `confirmed + pending` 两套平行列表。需要筛选时由明确的 filter/分页合同提供，避免同一 VM 的双索引漂移。

## 2. G13 - 频道未读归零

### 2.1 输入与 Tick

`message.timeline` 在获得稳定 `timelineEpoch` 后给出 `channel.mark-read` ActionBinding；也可以由端侧的可见区观察上报 `HostObservation::MessagesVisible`。两者最后都归一为同一领域意图，而不是两条互相竞争的链路。

```text
ActionBinding(channel.mark-read) / HostObservation::MessagesVisible
  -> Tick::Command(MarkChannelRead { channelId, upToMessageId })
  -> validate membership + current timeline epoch + monotonic read boundary
  -> Effect::Http(MarkChannelRead)
  -> authoritative WS/sync fact
  -> Effect::PersistAtomic(ViewerChannelState, unread aggregate)
  -> PersistOk
  -> InteractionFrame v2
```

HTTP 成功只是请求接受，不是 UI 真源。服务端 WS、sync 或规范化的 port reply 带来的 authoritative boundary 才能推进 `ViewerChannelState`。网络失败时保留当前已提交的未读数；平台不得先把整个 dialog 未读清零再祈祷成功。

### 2.2 Frame 和受影响 Surface

同一用户、同一次已提交 read boundary 应至少在同一个 Frame 更新：

1. `message.left-dialog-list@User` 的该频道未读角标/排序所需摘要；
2. `message.unread-summary@User` 的总未读、@我、加急聚合；
3. 已 attach 的 `message.timeline@Timeline(channelId, windowToken)` 的 `firstUnread`、行级定位标记；
4. 必要时 `message.channel-summary@Channel(channelId)` 的个人已读状态。

这不是客户端“同时改四个 store”；是 `SurfaceComposer` 用同一个 `PersistOk` 后的事实集，生成一笔有同一 `transactionId` 的多 Surface Frame。

## 3. G14 - 某条消息的已读回执

```text
ActionBinding(message.mark-read) / visibility observation
  -> Tick::Command(MarkMessageRead { channelId, messageId })
  -> Effect::Http(MarkMessageRead)
  -> WS/sync receipt fact
  -> PersistAtomic(MessageReceiptState)
  -> PersistOk
  -> Frame(timeline row summary + attached receipt detail)
```

如果消息行和 `message.participant-receipts` 都已 attach，它们必须从同一次已提交 receipt 事实投影，放入同一 Frame。只打开 timeline 时不需要偷偷 attach receipts；下一次用户请求明细时，surface snapshot 直接从持久化事实得到。

G14 的“某条消息被读”不自动等同于 G13 的“频道读到这里”。后者只有在该消息确实推进该用户频道 read boundary 时，才由领域规则一起改写 `ViewerChannelState`，并连带更新未读 Surface。

## 4. G14a - 模板消息确认

模板/需确认消息的 row 只在 `TemplateConfirmationPolicy` 允许时签发 `template.confirm` binding：

```text
ActionBinding(template.confirm)
  -> Tick::Command(ConfirmTemplateMessage)
  -> policy + membership + message-version validation
  -> Effect::Http(ConfirmTemplateMessage)
  -> WS/sync confirmation fact
  -> PersistAtomic(TemplateConfirmationState)
  -> PersistOk
  -> Frame(timeline/thread summary + attached participant receipts)
```

确认可以同时让消息行的 confirmation summary 改变，且在 receipt detail attach 时更新对应成员行。它不会伪造一个“全部已读”结果，也不应因为读回执更新而重复签发确认 ActionBinding。

## 5. ActionBinding、VM 与缓存边界

| 位置 | 应放的内容 | 禁止放的内容 |
|---|---|---|
| `MessageRowVmV2` | 当前消息可见的 receipt/confirmation 摘要及已获授权的动作。 | 整个成员 roster、客户端推测的回执数。 |
| `ParticipantReceiptsVm` | 有界成员回执/确认行、cursor、精确的 message context。 | timeline 的复制副本、两套相反状态数组。 |
| `TimelineWindowVm` | `firstUnread`、窗口锚点、rows。 | 全频道的永久 read cursor store。 |
| platform overlay | 打开回执抽屉/页面、局部 loading、滚动位置。 | 未经 Frame 的 `readCount += 1` 业务改写。 |

ActionRef 属于收到它的 surface epoch/revision：timeline 滚窗后旧 row ref 失效；receipt detail 翻页后旧 detail ref 失效；它们都不能把一个过期动作“路由”到当前消息。端侧将 `ActionRejected(stale_ref)` 回报，Helix 返回该 slot 的 snapshot/patch，而不是让客户端猜如何补账。

## 6. 失败、同步与跨端一致性

| 情况 | Core / Effect | UI 结果 |
|---|---|---|
| HTTP 拒绝或 WS 未确认 | 不提交对应 read/receipt/confirmation 事实；记录可观测的 action outcome。 | 保持最近 Frame；可显示局部失败状态，但不改业务数字。 |
| sync gap | GS03/GS04 补偿对应事实后重新 compose。 | 全局 `runtime.syncing` 可见；用户仍可继续操作。 |
| unknown message / channel | 先 hydrate 所需 scope，再验证该 binding。 | 不显示伪造的 receipt；Frame 到达后重渲染。 |
| PC 与 Mobile | 使用同一 `ReceiptState` 枚举、排序和过滤规则。 | PC 可抽屉，Mobile 可独立页；显示形态不同，不得解释出不同计数。 |

本 Gate 不增设第十个 Surface：回执明细已有 `message.participant-receipts`，未读聚合已有 `message.unread-summary`。新增的只是清晰的领域事实和 projector，不是一个新的“万能状态面板”。
