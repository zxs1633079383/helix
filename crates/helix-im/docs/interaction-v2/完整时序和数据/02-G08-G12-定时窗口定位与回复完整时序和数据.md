# G08-G12 定时、窗口、定位与回复完整时序和数据

> 对应上级分册 `06-G08-G12-定时窗口定位与回复.md`。写类 G08/G09 必须等待 WS/sync；
> 读类 G10-G12 可把经过校验的 HTTP data 作为 authoritative input，但仍必须先 PersistOk 再发 Frame。

## 1. Gate 与 Go 接口总表

| Gate | Go endpoint | 请求关键字段 | `SUCCESS.data` | 权威事件/用途 |
|---|---|---|---|---|
| G08 创建定时 | `/posts/createSchedule` | `post`、`schedulePostAt` | 无 | `post_schedule_created`。 |
| G08 读取草稿 | `/posts/getSchedule` | `channelId` | owner-only schedule draft | attach/hydrate schedule UI。 |
| G09 取消定时 | `/posts/cancelSchedule` | `channelId` | 无 | `post_schedule_canceled`。 |
| G10 首屏 | `/posts/getLatestPost` 或 `/posts/top20` | `channelId,timestamp` 或 `channel_id` | Post 数组 | latest bounded window。 |
| G10a 更早 | `/posts/postContext` | `postId,before` | Post 数组 | older context。 |
| G10a 更新后窗口 | `/posts/getPostsAfterIndex` | `postIds`（值是单 id string） | `{posts,count}` | newer context。 |
| G11 定位 | `/posts/get` + `/posts/postContext` | ids / target+before | Post 数组 | hydrate target and context。 |
| G12 thread | `/posts/getReplies` | `replyId,pageNumber,pageSize,revoke?` | `{rootPost,replies}` | root + reply page。 |
| G12 branch | `/posts/getReplyBranch` | `replyFirstLevelId,pageNumber,pageSize,revoke?` | `{data,hasMore}` | branch page。 |

## 2. G08 创建与读取定时消息

### 2.1 上行与 Go wire

目标 owner 是 `message.composer@Channel(C)` 的 `message.schedule` binding。UI 提交 versioned
content 和绝对毫秒时间，actor/channel/action kind 由 binding/scope 固定。

当前 Go wire：

```json
{
  "post": {
    "channelId": "C",
    "message": "scheduled text",
    "type": "NORMAL",
    "props": {}
  },
  "schedulePostAt": 1780000000000
}
```

Go 用 session 覆盖 `post.userId`；若 body 中 userId 与 session 冲突则失败。`temporaryId` 不接受
renderer 伪造，应由 Helix/服务端发送状态机生成。

成功响应：

```json
{ "status": "SUCCESS", "message": "createScheduledPost success" }
```

权威 `post_schedule_created` 至少携带当前 user/channel 的 schedule 状态、status=`scheduled` 与
revision；Go 按 userId + channelId 单播。

### 2.2 完整时序

```text
schedule binding invoke
  -> validate capability/time/content/owner
  -> Http(posts/createSchedule)
  -> CommonRes SUCCESS                    // 不改 UI
  -> WS post_schedule_created / sync
  -> PersistAtomic(ScheduledDraft + ChannelScheduleState + event cursor)
  -> PersistOk
  -> one Frame for attached dialog + channel summary (+ composer if capability changes)
```

Persist 写集：`scheduleId/temporaryId`、owner、channel、canonical content、sendAt、status、revision、
viewer channel `hasScheduledMessage`。定时正文只对 owner 可见，不进入其他成员 Frame。

Frame 的 dialog row 必须重新给出完整 `DialogRowVm`，其中：

```json
{
  "channelId": "C",
  "hasScheduledMessage": true,
  "preview": { "kind": "text", "author": { "userId": "owner" }, "text": "existing canonical preview" }
}
```

上例只展示变化字段；实际 replaceView row 仍必须含 README 所列所有必填字段。定时草稿不能覆盖
频道当前消息 preview，也不能让接收者提前看到正文。

读取 owner 草稿：

```json
{ "channelId": "C" }
```

Go data 保留 Post 顶层字段并增加 aliases：`scheduleId/schedule_id`、`sendAt/send_at`、
`status="scheduled"`、`revision`、`scheduleOwnerUserId`、`canViewContent=true`。Helix 必须校验
owner/channel 后归一化，不能把整份 Go Post 放进 Frame。

## 3. G09 取消定时消息与到点发送

取消 wire 与成功回包：

```jsonc
{ "channelId": "C" }
{ "status": "SUCCESS", "message": "cancelScheduledPost success" }
```

完整链路：

```text
cancelSchedule binding
  -> Http(posts/cancelSchedule)
  -> SUCCESS (keep current scheduled VM)
  -> WS post_schedule_canceled(status=canceled, revision)
  -> PersistAtomic(remove/mark canceled draft + channel schedule state)
  -> PersistOk
  -> dialog.hasScheduledMessage=false + channel summary update in one Frame
```

到点投递不是本地 timer mutation。Go 的 delay/consumer 进入 canonical create post 链；Helix 收到
真实 post WS/sync 后，按 G01/G02/G03 产生 Sent message Frame，同时用权威 schedule event/state
清除 `hasScheduledMessage`。两个事实若分两次提交，就按各自 PersistOk 发单调 Frame，不能由 UI 猜原子性。

## 4. G10 首屏有界窗口

### 4.1 请求/响应

优先 current latest 请求：

```json
{ "channelId": "C", "timestamp": 0 }
```

Go 返回：

```jsonc
{
  "status": "SUCCESS",
  "message": "post sender success",
  "data": ["<canonical Post>", "..."]
}
```

`top20` 的 wire 是命名例外：

```json
{ "channel_id": "C" }
```

### 4.2 完整时序与数据归一化

```text
EnterChannel(C, WindowHint)
  -> attach summary/composer
  -> AttachTimeline(C,W)
  -> StorageScan(local bounded rows)
  -> if coverage insufficient: Http(getLatestPost/top20)
  -> validate audience/channel + normalize Post -> Message facts
  -> PersistAtomic(messages + coverage + cursor/index)
  -> PersistOk
  -> timelineSnapshot@Timeline(C,W)
```

`TimelineWindowVm` 完整数据：

```jsonc
{
  "channelId": "C",
  "anchor": { "mode": "latest" },
  "items": ["<complete MessageVm ordered by canonical order>"],
  "page": {
    "windowToken": "W",
    "hasOlder": true,
    "hasNewer": false,
    "hasMore": true
  },
  "state": "ready"
}
```

如果没有消息，items=[]、state=`empty`，page/token 仍完整。窗口上限由 Helix policy 固定；Go
当前 latest/top20 是约 20 条，不应在文档中伪称 Go 已返回 60 条。若产品目标是 60，Helix 要通过
有界多页读取实现并为额外请求提供测试/预算。

## 5. G10a 上拉更早与向后补窗

更早请求：

```json
{ "postId": "visible-anchor-M", "before": 20 }
```

返回 `CommonRes.data = Post[]`。向后接口的 wire 陷阱是 key 为复数、值为单字符串：

```json
{ "postIds": "visible-anchor-M" }
```

返回：

```json
{
  "status": "SUCCESS",
  "message": "post sender success",
  "data": { "posts": [], "count": 0 }
}
```

完整链路：验证当前 timeline epoch/windowToken/anchor -> local scan or HTTP -> normalize/dedupe ->
PersistAtomic coverage -> PersistOk -> `timelinePatch(replaceView(next bounded window))`。去重按 message id/index，
构窗 `O(local+remote+visible)`，不可在 renderer 对两页反复 `find` 形成 `O(n^2)`。

窗口 patch 必须给新完整 items、anchor/page/firstUnread/target/state。滚窗会刷新 row-scoped actions；
channel-scoped composer capabilityEpoch 不因窗口变化而改变。

## 6. G11 定位原消息

Go 没有独立 locate endpoint。Helix 的 target hydration 组合是：

```jsonc
POST /posts/get         { "postIds": ["TARGET"] }
POST /posts/postContext { "postId": "TARGET", "before": 20 }
```

必要时再用 `getPostsAfterIndex` 补 newer side。完整时序：

```text
LocateMessage(TARGET)
  -> validate target/channel visibility
  -> local index hit ? compose : Http(get + context)
  -> PersistAtomic(target + bounded context + coverage)
  -> PersistOk
  -> timeline snapshot/patch with anchor.mode=locate,
     anchor.messageId=TARGET, targetMessageId=TARGET
  -> optional UiDirective after cache commit
```

当前 `UiDirective` 没有 payload，合法数据只能是：

```json
{ "directiveId": "reveal-TARGET-8", "kind": "revealMessage" }
```

平台从已经原子提交的 `TimelineWindowVm.targetMessageId` 取得 target；不能从 directive 私自增加
`targetMessageId` 字段。动画、像素位置、高亮时长属于 overlay。

## 7. G12 回复与分支

### 7.1 Go wire 与返回

root replies：

```json
{ "replyId": "ROOT", "pageNumber": 1, "pageSize": 20, "revoke": false }
```

```jsonc
{
  "status": "SUCCESS",
  "data": {
    "rootPost": "<Post>",
    "replies": ["<Post>"]
  }
}
```

branch：

```json
{ "replyFirstLevelId": "R1", "pageNumber": 1, "pageSize": 20, "revoke": false }
```

```jsonc
{
  "status": "SUCCESS",
  "data": { "data": ["<Post>"], "hasMore": false }
}
```

Go handler 会规范化缺失/非法页参数为 pageNumber=1/pageSize=20；Helix builder也显式给默认值。

### 7.2 完整时序与 Persist

```text
OpenThread(C,ROOT)
  -> AttachThread(C,ROOT)
  -> StorageScan(root + reply relation + page coverage)
  -> Http(getReplies/getReplyBranch) when incomplete
  -> validate all posts belong to C and relation root/first-level is legal
  -> PersistAtomic(messages + reply edges + page coverage)
  -> PersistOk
  -> threadDetailSnapshot/patch
```

Persist 使用 message id -> row index 和 root -> ordered reply ids；插入/查找 `O(log n)` 或 `O(1)`，
输出按 canonical reply order `O(visible)`。不得在 UI 递归扫描全 nodes 推导树。

`ThreadDetailVm` 完整数据：

```jsonc
{
  "channelId": "C",
  "root": "<complete MessageVm id=ROOT>",
  "orderedReplyIds": ["R1", "R2"],
  "nodes": {
    "R1": "<complete MessageVm id=R1>",
    "R2": "<complete MessageVm id=R2>"
  },
  "replyCount": 2,
  "page": {
    "windowToken": "thread-page-1",
    "hasOlder": false,
    "hasNewer": false,
    "hasMore": false
  },
  "state": "ready"
}
```

新 reply WS 到达并 PersistOk 后，已 attach thread 与包含 root 的 timeline reply summary 在同一 Frame
替换；未 attach thread 只持久化，下一次 attach 给 snapshot。若 reply 成为最新频道活动，dialog
preview 也由同一 committed fact set 计算。

## 8. 失败与恢复

| 情况 | 结果 |
|---|---|
| schedule HTTP failed/timeout | 保持上次 schedule VM；不先改 hasScheduledMessage。 |
| schedule WS duplicate | revision/event identity 幂等，不重复清/建草稿。 |
| window response含跨频道或不可见 Post | 整批拒绝/隔离，slot state failed 或触发 authoritative resync。 |
| target 不存在 | timeline 维持原窗口，request outcome not-found；不发 reveal directive。 |
| reply relation 不合法 | 不写 edges，不发布 thread Frame。 |
| patch base revision gap | 整帧拒绝，请求该 slot snapshot；不在 UI 拼旧页。 |
