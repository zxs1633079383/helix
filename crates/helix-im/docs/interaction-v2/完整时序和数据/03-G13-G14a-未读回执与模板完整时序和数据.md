# G13-G14a 未读、回执与模板完整时序和数据

> 对应上级分册 `07-G13-G14a-未读回执与模板确认.md`。本页严格区分频道 read boundary、
> 逐消息 read receipt、模板“收到”和业务“确认”。Go 当前只有 templateReceived，不能冒充确认。

## 1. 三类事实与 Go 对齐

| Gate/事实 | Go endpoint | authoritative output | Frame owner |
|---|---|---|---|
| G13 viewer 频道已读 | `/channels/view` | `post_read` + viewer `update_channel` | dialog + unread + timeline + optional summary。 |
| G14 标记消息已读 | `/post/read` | `post_read` + viewer `update_channel` | timeline row + optional receipt detail；可能推进 G13。 |
| G14 查询回执 | `/post/read/list` | HTTP `PostReadDto[]` | participant receipts snapshot。 |
| G14a 模板已收到 | `/post/templateReceived` | handler success；application received fact | 不能直接等同 template confirmation。 |
| 公告已读/确认旁路 | `/post/announcement/read`、`/announcement/acceptList` | announcement-specific data | 仅公告子域，不能自动当通用模板确认。 |

## 2. G13 频道未读归零

### 2.1 上行与 Go wire

`message.timeline` 的 `channel.mark-read` binding 或稳定可见区 observation 归一成频道 read intent。
Go `/channels/view` 请求：

```json
{
  "channels": [
    { "id": "C", "isRoot": true }
  ]
}
```

`isRoot` 可选；Go 当前按 session user 执行 CAS 推进并清 badge。成功响应无 data：

```json
{ "status": "SUCCESS" }
```

Go application 会为权威边界发布 `post_read`（data 含 channelId）并发布当前 viewer 的
`update_channel`。因此 HTTP `SUCCESS` 仍不是 UI 清零条件。

### 2.2 完整时序

```text
MessagesVisible / channel.mark-read
  -> normalize MarkChannelRead(C, upToMessageId/readBoundary)
  -> validate membership + timeline epoch + monotonic boundary
  -> Http(channels/view)
  -> SUCCESS                              // keep current unread
  -> WS post_read + update_channel / sync
  -> reconcile authoritative boundary + viewer absolute unread aggregate
  -> PersistAtomic(ViewerChannelState + receipt facts + cursor/eventSeq)
  -> PersistOk
  -> one multi-surface InteractionFrame
```

### 2.3 Persist 与完整 Frame

```text
ViewerChannelState(viewer,C):
  readBoundaryMessageId / sequence
  unreadCount, mentionCount, urgentCount
  firstUnreadMessageId
ViewerAggregate(viewer):
  unreadTotal, mentionTotal, urgentTotal, unreadChannelCount
```

一次 commit 至少替换：

1. dialog 完整 row：`unreadCount/mentionCount/urgentCount` 为权威绝对值；
2. unread summary 完整聚合；
3. 所有已 attach C timeline：`firstUnreadMessageId` 与完整 rows；
4. channel summary：仅当 VM 当前设计承载个人通知/read 状态时更新。

Frame 示例的关键 mutation：

```jsonc
[
  {
    "surface": "message.left-dialog-list",
    "scope": { "kind": "user", "userId": "U", "teamId": "T" },
    "revision": 12,
    "baseRevision": 11,
    "mutation": { "kind": "dialogListPatch", "patch": { "kind": "replaceView", "view": "<complete DialogListVm>" } },
    "surfaceEpoch": 2
  },
  {
    "surface": "message.unread-summary",
    "scope": { "kind": "user", "userId": "U", "teamId": "T" },
    "revision": 12,
    "baseRevision": 11,
    "mutation": {
      "kind": "unreadSummaryPatch",
      "patch": {
        "kind": "replaceView",
        "view": { "unreadTotal": 4, "mentionTotal": 1, "urgentTotal": 0, "unreadChannelCount": 2 }
      }
    },
    "surfaceEpoch": 2
  }
]
```

不得端侧先将角标置 0。不同已 attach slot 可以有不同 revision，但必须属于同一 transaction，
整帧验证成功后原子替换。

## 3. G14 标记某条消息已读

### 3.1 Go 写接口

按 posts 列表标记：

```json
{ "channelId": "C", "posts": ["M"] }
```

按时间区间标记：

```json
{ "channelId": "C", "startTime": 1770000000000, "endTime": 1780000000000 }
```

`userId` 缺失时由 Go session 填充；V2 不应由 renderer 提交 userId。成功：

```json
{ "status": "SUCCESS" }
```

### 3.2 写链时序

```text
message.mark-read binding / visibility observation
  -> MarkMessageRead(C,M)
  -> Http(post/read)
  -> SUCCESS (no count change)
  -> WS post_read / sync receipt fact
  -> PersistAtomic(MessageReceiptState + optional ViewerChannelState)
  -> PersistOk
  -> timeline/thread row + attached participant receipts Frame
     + G13 surfaces only if channel boundary actually advanced
```

逐消息回执与频道 boundary 不能双向推断。Go event 同时带来两者时可以同 commit；只有 receipt 时
不能擅自把频道 unread 清零。

### 3.3 Go 回执查询 data

请求：

```json
{ "postIds": ["M1", "M2"] }
```

Go `PostReadDto` 每项：

```jsonc
{
  "postId": "M1",
  "authorUserId": "AUTHOR",
  "status": "<server status>",
  "unavailableReason": "optional",
  "readBits": "optional bitmap representation",
  "snapshotId": "S",
  "snapshotVersion": 3,
  "memberIds": ["U1", "U2"],
  "readerIds": ["U2"],
  "readers": [{ "userId": "U2" }]
}
```

Helix 不把 bitmap 或两套 raw lists 直接下发。它校验 snapshot/version/member audience，归一成：

```jsonc
{
  "channelId": "C",
  "messageId": "M1",
  "kind": "read",
  "summary": { "completedCount": 1, "pendingCount": 1 },
  "completed": [
    { "user": { "userId": "U2" }, "memberRole": "member", "status": "completed", "completedAt": 1780000000000 }
  ],
  "pending": [
    { "user": { "userId": "U1" }, "memberRole": "member", "status": "pending" }
  ],
  "page": { "windowToken": "receipt-page-1", "hasOlder": false, "hasNewer": false, "hasMore": false },
  "state": "ready"
}
```

Go 当前 reader 仅有 userId，`completedAt` 若无权威值必须省略，不能用本地查询时间代填。

### 3.4 ViewReceipt 当前 live action

`viewReceipt` 是当前唯一 live `ActionDispatch`：

```text
timeline row ActionBinding(viewReceipt)
  -> invoke input must be empty
  -> Http(post/read/list {postIds:[M]})
  -> validate CommonRes/data and author permission
  -> PersistAtomic receipt snapshot facts
  -> PersistOk
  -> participantReceiptsSnapshot(kind=read, causationId=requestId)
```

permission denied 时可发布 `state=forbidden` 的完整 receipts snapshot，不泄露成员数组。

## 4. G14a 模板“收到”与“确认”的对齐边界

### 4.1 当前 Go 只有 received

请求：

```json
{ "postId": "M" }
```

Go 也兼容历史 `post_id`，但 Helix 发 canonical camelCase。成功：

```json
{ "status": "SUCCESS", "message": "templateReceived success" }
```

handler/application 名称和注释都定义为“当前用户标记模板消息已收到”。这只能产生：

```text
TemplateReceiptState = received
```

它不能未经额外领域规则被升级为：

```text
TemplateConfirmationState = confirmed
```

### 4.2 目标确认链与 GAP

目标 V2 `template.confirm` 链应是：

```text
template.confirm binding
  -> validate TemplateConfirmationPolicy + message version + membership
  -> explicit Go confirm command/endpoint
  -> authoritative confirmation event/sync
  -> PersistAtomic(TemplateConfirmationState)
  -> PersistOk
  -> timeline/thread confirmation summary
     + participantReceipts(kind=templateConfirmation) when attached
```

当前缺少“explicit Go confirm command/endpoint + authoritative confirmation event”的确定映射，因此：

- `im_template_received` 只能用于 received，不可签发 `template.confirm`；
- `ReceiptKind::TemplateConfirmation` 类型存在不代表数据真源已经存在；
- `/post/announcement/read` 和 `/announcement/acceptList` 是公告专用，不可泛化到所有模板；
- 在补齐 Go 领域语义前，G14a business confirmation 必须标 `GAP`，不能 runtime green。

### 4.3 未来完整 Frame 数据

当 Go 语义补齐后，message row 的 `templateConfirmation` 至少需要：

```json
{
  "policyVersion": 2,
  "state": "pending | confirmed | unavailable",
  "confirmedCount": 3,
  "pendingCount": 1,
  "selectedByViewer": true,
  "canConfirm": false
}
```

receipts detail 使用 `ParticipantReceiptsVm.kind="templateConfirmation"`，completed/pending 每个成员只出现
一次。当前字段还是 `SurfaceDataVm`；终局若要保证跨端语义，宜版本化为强类型 confirmation summary。

## 5. 失败、隐私与复杂度

| 情况 | 正确结果 |
|---|---|
| mark-read HTTP failed | 不改 unread/read count，保留上一 Frame。 |
| self reads own message | Go 可能不发布作者回执；Helix不得伪造 reader。 |
| snapshotId/version mismatch | receipt detail fail-closed/resync，不把 bitmap 与新 roster 混算。 |
| viewer 无明细权限 | `state=forbidden`，completed/pending 为空。 |
| duplicate post_read | `(message,user,boundary/revision)` 幂等，不重复计数。 |
| received 被误当 confirmed | 合同错误；必须拒绝映射并记录诊断。 |

未读聚合按 channel contribution index 更新为 `O(log n)`/`O(1)`，不要每个 read event 扫描所有 dialog。
receipt snapshot 构造按有界成员页 `O(visible members)`；PC/Mobile 只遍历 VM，不解析 bitmap。
