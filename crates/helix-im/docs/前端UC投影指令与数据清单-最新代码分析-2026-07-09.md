# 前端 UC 投影指令与数据清单（Helix 最新代码分析，2026-07-09）

## 0. 范围与口径

- 代码基线（2026-07-10 复核）：
  - Helix: `7156261631f9e232f6a9527e1d2e1588f494d974`
  - cses-im-server: `d251a718d8789ee04a104661dea5b41b98a13da7`
  - cses-client: `0d2ce5fe37e228ac37dbe3743fb534e6d54aa62a`，另有本次未提交的 message-v4 投影接线工作区改动
- 本清单按前端 `message-v4` UC gate 划分，并以 Helix 最新代码为主轴核对 command、Effect、投影字段、HTTP、WS、DB 表。
- 显式排除：`bot/agent`、`search`、`vote/average`。这些命令或 UC 不进入主表，仅在本段说明排除口径。
- PC 前端和双用户 E2E 的唯一执行端是 `cses-client`；不引用或依赖任何历史验证场的运行时、fixture、日志或测试态。
- 前端存储口径以 Helix storage 为唯一目标库：不再分析 cses-client 自身 sqlite/状态表作为业务 SoT；`cses-client` 只保留宿主日志、投影 trace 和 DOM 结果作为验收证据。
- `后端数据库表` 指 Go `cses-im-server` Ent schema 的实际表名；`Helix storage 表` 指 `crates/helix-im/src/schema.rs` 中 SQLite 表，也是未来前端侧本地存储权威。
- 读族 HTTP 的 `im:read:result` 外层固定字段是 `{req_id, body}` / `{req_id, error}`；`body` 由后端响应体权威决定，Helix 不冻结内部字段。
- 文档里保留的代码字段名 `unknown` / `unknownChannelById` 不是“未知证据”，而是 UI/投影语义里的“陌生频道/待加载频道”字段；证据不足处统一写“待补证”或“待补投影”。

## 3. 发送消息核心链路和 sync 对齐

### 3.1 G-02 文档库链接占位口径

message-v3 的正式 `DOCUMENT` 发送不是单纯文件上传链路：`sendDocumentMessage(snapshot)` 先用 `snapshotToPlainText(snapshot, 2000)` 生成 `message`，用前 50 字生成 `simpleMessage`，再构造 `type=DOCUMENT`、`viewers=["all"]`、`props.document={snapshot,version:1}`，最后复用普通 `sendMessage(..., {dispatchEvent:true})` 走 `/posts/create`。

文档库链接识别口径来自 message-v3 `internal-doc-link.util.ts`：只认 `http://doc.cses7.com/doc/<id>`、`http://doc.cses7.com/folder/<id>`、`http://doc.cses7.com/docv/<id>?version=...`，预览卡 host 是 `CSES 文档`，doc 标题是 `打开文档`。

所以当前 G-02 可先这样占位，不要再写成泛泛的 `doc`：

```json
{
  "type": "DOCUMENT",
  "message": "【文档】 http://doc.cses7.com/doc/abc123",
  "simpleMessage": "【文档】 http://doc.cses7.com/doc/abc123",
  "viewers": ["all"],
  "props": {
    "document": {
      "version": 1,
      "url": "http://doc.cses7.com/doc/abc123",
      "title": "打开文档",
      "placeholder": true
    }
  }
}
```

后续接回正式文档编辑器时，把 `props.document.url/title/placeholder` 换成 message-v3 的 `props.document.snapshot/version=1`，HTTP/WS/Helix storage 链路不需要另起 UC。

### 3.2 Go 发送主链路事实

`app.SendPosts` 的主链路是：`prepareSendContext` 组装 post/count -> `commitDurableMessage` 调 `CsesPost.SavePosts` -> `SavePosts` 先更新 channel/member lastPost 与计数，再事务内插 `post`、更新 `channel`、更新 `channel_member` -> `appendEntPostCreateEventStandalone` 追加 `channel_event(type=1)` -> `selfReadOnSend` 推进发送者 `channel_member.last_read_seq` 并把 `msg_count_all` GREATEST 到 `channel.total_msg_count_all` -> `publishPrimaryVisibility` 只广播 `post` 帧并带 `event_seq`。

普通发送链路没有看到单独的 `update_channel` 广播作为 lastPost 主来源；`update_channel` 主要在 `ReadPost` 清 badge、`channels/view` 已读、频道属性变更、撤回最后一条、加急等副链出现。因此 Helix 收到 `post` 后必须自己更新本地 `message` 与 `channel.last_post/last_root_post_at/unread_count/unread_post_id`，不能等普通发送的 `update_channel`。

### 3.3 Helix 当前在线 post 已做什么

Helix `ws/handlers/post.rs` 当前会解析 `post` 帧的 `channelId/event_seq`，先做 echo settle，再把事件交给 `Channel::ingest`。连续事件 apply 时会：

| 本地动作 | 当前代码状态 |
|---|---|
| 入库 Message | 已做：`event_to_storage_op(PostUpsert)` -> `message` upsert |
| 更新 Channel lastPost/unread | 已做：`post_updates` + `GuardedBump` 写 `channel.last_post`, `unread_count`, `unread_post_id`, `last_root_post_at`, `has_schedule_post` |
| 推进本地 cursor | 已做：`advance_cursor` 单调写 `channel_event_cursor.last_event_seq` |
| 前端消息投影 | 已做：`emit_for_kind(PostUpsert)` -> `im:post:received` |
| 前端频道薄投影 | 在线 post 当前未发 `im:channel:update-by-post`；这个 emit 只在 sync mutation 路径存在 |
| ChannelMember count/read 域 | Helix storage 当前 `channel_member` 只有成员身份/角色/昵称字段，不具备 `msg_count/msg_count_all/last_read_seq/phantom_count/phantom_at_read` 本地列 |
| 本地 ChannelEvent 日志 | Helix 当前只有 `channel_event_cursor`，没有本地 `channel_event` 明细表；明细事件以 Go `channel_event` 为 SoT，经 sync/notify 回放 |

### 3.4 离线 sync 链路事实

Go `/api/cses/channel/sync/notify` 请求体是 `{cursors:[{channelId,fromSeq}]}`，返回 `entries`。单 channel 分支是 `no_change`、`events`、`too_long`、保留的 `snapshot`。`events` 携 `events[]` 与按可见性过滤后的 `messages` map；`nextSeq` 是 cursor 推进锚。事件类型目前固定：`1=new`、`2=edit`、`3=delete`、`6=read`。

Helix `sync/flow.rs` 当前按 `nextSeq/max(event.seq)` 算 commit target，先用 `batch_upsert_events_with_messages` 写 `message`，再用 `sync_unread_bump_ops` 补 `channel` 未读/lastPost，持久化成功后才 commit cursor。`too_long` 只清内存 buffer/cursor 并 emit `im:sync:too_long`，SQLite 表不清，由上层重新拉首屏覆盖。

### 3.5 现在还需要补齐的 Helix 操作

| 项 | 当前差距 | 建议补齐 |
|---|---|---|
| 在线 post 频道刷新投影 | 在线 WS `post` 已写 `channel`，但未 emit `im:channel:update-by-post`；sync 路径会 emit | 在线 apply/flush 后补同一个 thin emit，或明确 UI 只靠 `im:post:received` 触发 dialog 重查 |
| 已读清本地 unread | Go `channels/view` 会推进 `msg_count/msg_count_all` 与 `last_read_seq`，并单播 `update_channel`；但 update payload 主要是 `lastViewedAt/mentionList/mentionCount/mentionUser`，Helix 本地 `unread_count` 不一定被清零 | Helix 在 `im_post_read` / `channels/view` 成功或对应 `update_channel` 语义上补 `channel.unread_count=0`，并与 Go count-domain 口径对齐 |
| ChannelMember read/count 域 | 后端实体有 `msgCount/msgCountAll/lastReadSeq/phantomCount/phantomAtRead`，Helix `channel_member` 没这些列 | 若未来前端全由 Helix storage 承接未读，需要给 Helix `channel_member` 增列并在 send/read/sync 应用中维护 |
| 本地 channel_event 明细 | Go `channel_event` 是离线同步 SoT；Helix 只有 cursor 镜像 | 如果只做最终状态，保留 cursor 即可；如果要本地回放/审计/调试，需要新增 Helix `channel_event` 表并在 sync apply 时落事件 |
| G-02 文档消息 | 当前旧占位值语义太粗 | 先按文档库 URL 占位；正式接 message-v3 snapshot 后替换 `props.document.snapshot` |

### 3.6 和 Go DDD / agent 蜂群对齐后的 Helix 分工

这部分按两个仓的 agent 边界拆：Go 侧 `post-domain-agent + sync-domain-agent + channel-domain-agent` 已经把发送与离线同步沉到 `docs/ddd/发送消息逻辑全流程.md` 和 `docs/specs/2026-07-09-offline-sync-current-flow.md`；Helix 侧应由 `im-message-domain-agent + im-sync-domain-agent + im-channel-domain-agent` 联合收口。核心结论如下。

| Helix 操作域 | 当前 Go 事实 | Helix 当前状态 | Helix 应补齐 |
|---|---|---|---|
| 在线 `post` 入库 | Go `SendPosts` 先写 `post/channel/channel_member`，再追加 `channel_event(type=1)`，WS 主帧是 `post + event_seq`；普通发送不额外依赖 `update_channel` 更新 lastPost | 已解析 `post`，写 `message`，用 `GuardedBump` 更新 `channel.last_post/unread_count/unread_post_id/last_root_post_at`，写 `channel_event_cursor` | 保持 `post` 为普通发送主真源，不等 `update_channel`；补在线 `im:channel:update-by-post`，让 dialog 薄投影和 sync 路径一致 |
| `update_channel` | 普通发送链路的 `update_channel` 主要是 mention/read/channel 变更/撤回最后一条/urgent 等副链，不是 lastPost 主帧 | Helix `update_channel` 白名单 PATCH 可收 `unreadCount/mentionCount/lastPost/lastEventSeq` 等字段 | 不要把普通发送是否成功绑定到 `update_channel`；但 read/channel mutation 收到显式 `unreadCount=0` 时必须清本地 unread |
| `channel_member` count/read | Go 维护 `msg_count/msg_count_root/msg_count_private/msg_count_all/last_read_seq/phantom_count/phantom_at_read`，sender self-read 会推进 `last_read_seq + msg_count_all` | Helix `channel_member` 只有身份/角色/昵称，无法镜像后端 count-domain | 新增本地列或单独 read-state 表，至少覆盖 `last_read_seq`, `msg_count_all`, `phantom_count`, `phantom_at_read`；否则 Helix 只能用 `channel.unread_count` 做最终态，不具备后端同级诊断能力 |
| `channel_event` | Go `channel_event.event_seq` 是唯一 sync cursor；类型固定 `1=new,2=edit,3=delete,6=read` | Helix 只有 `channel_event_cursor`，没有事件明细；sync events 直接转成最终态写 `message/channel` | 默认继续 cursor-only 可运行；若要本地 replay/debug/跨端一致性审计，新增 `channel_event` 明细表，并在 online post 与 sync apply 都落事件行 |
| `type=6 read` | `post/read` 不写 `channel_event`；`channels/view` 才通过 `markEntChannelReadStandalone` 写 `channel_event(type=6)`，且 read 事件可无 `msgId` | Helix sync 解析 type6，但 `EventEnvelope` 不保留 actor/read payload；无 `msgId` 的 type6 基本只推进 cursor | 解析并保留 `actorId`；当 actor 是当前用户时按 `channelId/eventSeq` 清 `channel.unread_count`，并写本地 read-state；当 actor 是他人时只做 read echo/已读位展示，不清自己的 unread |
| 离线 `events/messages` | Go `events` 不按 viewers 过滤，`messages` map 才按 viewers 过滤；不可见消息是 phantom，只推进 cursor 不渲染 | Helix `messages` 缺失时不落 message，只提交 cursor；可见 type1 才做 `sync_unread_bump_ops` | 保持 phantom 不渲染；如果新增 channel_event 明细表，phantom 也应落事件明细但不落 message |
| `too_long` | Go `too_long resetTo=maxSeq` 表示客户端清本地增量视图后重拉首屏 | Helix 只清内存 buffer/cursor 并 emit `im:sync:too_long`，不清 SQLite 表 | 明确上层收到 `im:sync:too_long` 后要触发首屏/单群 reload 覆盖；若 Helix 要自洽，需要给 `too_long` 增加“按 channel 清 message/channel projection 后重拉”的可选策略 |
| 无 `event_seq` post | Go append event 失败时可能仍广播 `post` 但无顶层 `event_seq`；Helix 已把缺序 post 当 render-only | Helix `emit_unsequenced_post` 只发 `im:post:received(event_seq=0)`，不推进 cursor、不写 storage | 继续不推进 cursor；但应增加告警/指标，把“缺 event_seq 的 post”标为后端事件链断裂风险，不能算同步闭环成功 |

### 3.7 你还需要额外考虑的点

| 点 | 为什么重要 | 建议 |
|---|---|---|
| `im_channels_view` 与 `im_post_read` 语义不要合并 | Go 明确区分：`post/read` 是消息已读位回执；`channels/view` 是会话级水位、count-domain、type6 read event | UC-3.1 要同时覆盖两个命令：打开会话先 `channels/view` 清会话未读，按需对最近消息产生 `post_read` 回执 |
| `actorId` 当前在 Helix sync 事件里丢了 | type6 read 要判断“谁读了”；缺 actor 无法决定是否清当前用户 unread | `EventEnvelope` 增 `actor_id` 或专门 `ReadEventFields`，parser 从 `event.actorId/actor_id` 提取 |
| `last_read_seq` 是后端读水位，不等于本地 `channel_event_cursor` | cursor 表示“我同步到了哪条事件”；last_read_seq 表示“该成员已读到哪条事件” | Helix 需要同时存 `channel_event_cursor.last_event_seq` 和 member/read-state 的 `last_read_seq`，不能用一个字段替代另一个 |
| `msg_count_all` 是未读 count-domain 的已读水位 | 后端未读不是只靠 message 条数算；sender self-read 和 receiver view 都用 `msg_count_all` 防 badge 误增 | 若 Helix 未来完全接管前端 unread，必须镜像 `msg_count_all` 或保证 `channel.unread_count` 始终由后端投影/Helix GuardedBump 修正 |
| 多端同账号一致性 | PC 和 mobile 都由 Helix storage 承接时，一个端 `channels/view` 后另一个端要靠 `update_channel`/sync read event 收敛 | 需要双端场景测试：A 端读、B 端离线后同步，验证 `unread_count/last_read_seq/read_bits` 一致 |
| `allHash` 心跳兜底 | 非活跃群可能没有在线 post/gap，Go 通过 pong `hashMismatch` 让客户端触发 sync | Helix 需要确认 ping payload 带活跃 cursors/allHash，pong gaps/hashMismatch 能触发 `im_sync_channels` |

## 4. 最新代码核对出的缺口

| 缺口 | 当前代码事实 | 建议口径 |
|---|---|---|
| 在线 post 缺少频道薄投影 | Helix 在线 `post` 路径写 `message/channel/cursor` 并 emit `im:post:received`，但 `im:channel:update-by-post` 只在 sync mutation 路径发 | 补在线 `im:channel:update-by-post`，或让 UI 明确用 `im:post:received` 触发 dialog 重查 |
| ChannelMember 本地 count/read 字段缺失 | Go `channel_member` 有 `msgCount/msgCountAll/lastReadSeq/phantomCount/phantomAtRead`；Helix `channel_member` 表目前只有成员身份/角色/昵称 | Helix storage 若要完全接管前端未读，需要补这些列和写路径 |
| 本地 channel_event 明细缺失 | Go `channel_event` 是 append-only SoT；Helix 只有 `channel_event_cursor` | 保持 cursor-only 是可运行口径；如要本地 replay/audit，再新增 `channel_event` 表 |
| 已读清 unread 口径未闭环 | Go read/view 主链路推进 count-domain 与 `last_read_seq`，但发给 Helix 的 `update_channel` 不一定包含 `unreadCount=0`；Helix 当前 `post_read` 只覆盖 `message.read_bits` | 补 Helix read 成功/回声后的 `channel.unread_count=0` 或等待后端明确下发 `unreadCount` |
