> 代码基线：`reactor/MessageV3-helix`，核对日期 2026-09-06。本文描述当前真实代码，
> 不使用已经物理下线的 `InteractionFrame`、`Surface` 或 V1 compatibility 作为运行时层。

## 用户目录身份合同（2026-09-18）

消息身份只携带 `userId` 与来源 `teamId`，姓名、部门、头像由宿主当前用户目录提供。
登录注入的 `user_name/org_name/dept_name` 和旧命令中的姓名字段仅兼容接收，不进入发送、重试、
本地消息表或 MessageV3 事件。旧 `userSnapshot` 入站仅提取缺失的 ID，然后丢弃；新输入不需要快照。

- 回复保留关系 ID、`repliedUserId/repliedTeamId`、正文及富内容，不保留 `repliedUserName`。小回复摘要使用 `replyUserId/replyTeamId`，也不保留 `replyUserName`。
- 合并转发内容归档保持不变，卡片 `preview` 为 `{userId,teamId,text}`，详情行携来源 `teamId`。
  历史只有 `author` 的预览不能反推用户 ID，只能输出空 ID 供宿主占位；不得使用旧姓名。
- 普通文字接龙摘要使用 `creatorId/teamId`，条目使用 `authorId/teamId`；身份快照不落库。
  分类接龙的业务填写 Profile、任务名称与其他内容字段不在清理范围。
- `message.team_id` 保存来源公司；旧 `user_snapshot`、chain 身份快照列兼容保留但新写为空。
  启动迁移先保留身份 ID，再清除消息、引用、转发预览、频道摘要与置顶缓存中的旧身份副本。
  旧 `props.mergeMessage/merge_message` JSON 文本容器递归清理后仍保持字符串；普通正文中的 JSON 文本不解析。
  迁移只更新声明的 IM 表，不触碰宿主用户目录、不删除消息正文，不清空用户数据库。
- 此处只定义 Helix 合同；真实服务部署、目录同步与三端 UI 验证需对应宿主证据，不能由单测代替。

## 成员通知摘要的用户引用（2026-09-20）

邀请、移除与自退的 `NOTICE` 消息和频道 `lastPost` 增加可选 `summaryParts`：

```json
[{"kind":"user","userId":"actor","companyId":"company-a"},
 {"kind":"text","text":"邀请"},
 {"kind":"user","userId":"target","companyId":"company-b"},
 {"kind":"text","text":"加入群聊"}]
```

- 唯一文案计划在 `message_summary/member_notice.rs`。实时入站、同步回放的持久化完成投影、历史消息、频道完整/patch 写入和末条读回都调用同一规则；不根据在线状态选择不同摘要模板。
- `summaryParts` 只包含文本与用户身份，不包含姓名快照。宿主按公司/用户键读取本地目录、按真实频道取得昵称，并将当前用户展示为“您”；不能改写邀请/移除等业务文本。
- 用户公司优先取引用上的 `teamId/companyId`，否则用消息 `teamId`。被移除者的 ID 不依赖当前成员列表；旧缓存 props 仍有 ID 时，读取投影直接重建计划，无需修改服务端历史数据。
- 保序单次扫描所有通知目标，输出最多 10 个目标和总人数，最多 23 段；不扫描整群。旧 `simpleMessage` 由同一计划生成以兼容旧宿主，升级消费者优先用结构化引用。
- 缺 ID、损坏 props、未知通知或撤回不发布计划，并移除输入中不再适用的旧计划。没有目录事实时展示未知占位，不能把旧消息姓名当成目录权威。
- 仅生成/消费该可选字段，不新增数据库列、网络请求协议或 EventSink 事件名；不改变序号、持久化屏障、事件顺序和消息正文。需要同时交付 Helix 与宿主消费者后才生效。

## 1. 先统一四个方向

“入站”和“出站”必须以 Helix core 为观察点，否则 HTTP、WS 和 UI 事件很容易混为一层。

| 方向 | 当前类型 | 说明 |
|---|---|---|
| 应用命令入站 | `Tick::Command(AppCommand)` | UI/FFI/Native 调 Helix，例如 `im_send_message`、`im_retry_send`。 |
| 服务端推送入站 | `Tick::Inbound(Bytes)` | driver 收到 Go WebSocket 原始帧后喂给 Helix，例如 `action=post`。 |
| 端口结果入站 | `Tick::PortReply { corr, outcome }` | `Persist`、`PersistAtomic`、`Http`、`UploadFile` 的终态回报。 |
| 定时器入站 | `Tick::Timer(timer_id)` | driver 的 `TimerRegistry` 到期后回灌。 |
| I/O 意图出站 | `Effect::Persist/Http/ScheduleTimer/...` | Helix 只描述副作用，不直接访问 SQLite、HTTP 或计时器。 |
| 业务事件出站 | `Effect::Emit { event: DomainEventBytes }` | driver 交给 `EventSink`，PC 为 broadcast，Mobile FFI 为 step 级批量回调。 |

因此发送消息的网络出站是 **`Effect::Http`**，不是 Channel。对 UI/Mobile 的业务出站才是
**`Effect::Emit -> EventSink`**。HTTP 与存储的响应都通过 correlation 对应的
**`Tick::PortReply`** 回到 `ImModule`。

主要入口：

- `ImModule::handle`：`../../src/module/trait_impl.rs:20`
- `Effect` 合同：`../../../helix-core/src/effect/operation.rs`
- host 兑现器：`../../../helix-driver-host/src/dispatch.rs:28`

### 2.2 第一步不是 HTTP，而是乐观落库

`handle_send_message` 首个 step 只产出持久化意图并登记 pending correlation：

1. `Effect::Persist`（普通文本）或 `Effect::PersistAtomic`（带媒体 journal）：写本地
   `message` 表，`temporary_id` 为主键，`send_status='sending'`。
2. 内存登记 `PendingSend`：保存 `temporaryId`、timeout timer、body、connectionId、
   persist correlation 和可选 `req_id`。

此时不会发布 `im:post:sending`。只有匹配的 `PersistOk` 将 `PendingSend` 从 `Local` 推进到
`Sending`，再通过 `Effect::Emit { event: DomainEventBytes }` 只给当前发送端发布
`im:post:sending`；Persist 失败只进入 durable `unsend`/retry 事实，不产生伪成功事件。

乐观事件只含消息事实，不含 `actionCapabilities`、Frame、Surface 或重复的 snake_case
字段：

```json
{
  "event": "im:post:sending",
  "data": {
    "channelId": "26-char-channel-id",
    "temporaryId": "helix-generated-id",
    "userId": "sender-id",
    "message": "hello",
    "type": "TEXT",
    "createAt": 1785370000000,
    "sendStatus": "sending"
  }
}
```

本地 `message` 乐观行真实写入字段来自
`../../src/send/pending/persistence.rs:6`，包括：

`temporary_id`、`id`、`channel_id`、`user_id`、`message`、`type`、`props`、`viewers`、
`mentions`、回复字段、`create_at`、`send_status` 和 `upload_progress_percent`。

### 2.3 PersistOk 才允许发 posts/create

driver 兑现 `Effect::Persist`：

```text
Effect::Persist
  -> helix-driver-host dispatch_effects
  -> per-table-set 单 worker Storage port
  -> SQLite execute_storage_ops
  -> Tick::PortReply { corr=P1, Ok|Err }
  -> ImModule::handle_port_reply
```

`PersistOk` 时 `PendingSend.status` 从 `Local` 变为 `Sending`，并先 Emit `im:post:sending`。
文本消息在当前代码还会先完成
已 attach timeline 的本地读回；完成后调用 `emit_posts_create_http`。若乐观持久化失败，
则不发 HTTP，消息写为 `unsend`，撤销 timer，并 Emit `im:post:send-failed`。

`emit_posts_create_http` 产出两项：

```text
Effect::Http {
  POST {api_base_url}/posts/create,
  Content-Type: application/json,
  connectionId: <hello connection id>,

  Cses-Track-Id: <req_id, when present>

  id: pending_send.timeout_timer,
  after_ms: send_timeout_ms
}
```

默认 `send_timeout_ms=15000`。timer 只在 `posts/create` 真正出站时启动，不会把媒体上传耗时

### 2.4 driver 如何执行 HTTP，以及为什么响应是 PortReply

host 的 `OwnedEffect::Http` 使用有界、背压为 Block 的 HTTP worker pool。worker 通过
`HttpRequester` 发请求，再把真实 HTTP status、headers 和 body 编为 ADR-007 信封，
最后回灌：

```text
Tick::PortReply {
  corr: H1,
  outcome: Ok(ReplyBytes(http-envelope)) | Err(PortError)
}
```

Helix 依靠 `corr_map[H1] = OutboundSendHttp { channel_id, temporary_id }` 找回业务上下文。
它不依赖 callback 闭包，也不让 driver 理解 IM 状态。

### 2.5 图片与文件不是直接进入 posts/create

`im_send_message` 仍是统一入口。`type=IMAGE` 的富图片和 `type=FILE` 会从 `props` 提取本地
文件事实，先经过媒体上传状态机，全部附件完成后才进入上面的 `posts/create`：

```text
PersistAtomic(message sending + pending_media stage=prepare)
  -> Tick::PortReply(optimistic persist)
  -> Effect::Http POST {java_api_base_url}/oss/getPresignedUrl
  -> Tick::PortReply(prepare)
  -> Persist pending_media stage=put
  -> Tick::PortReply(stage persist)
  -> Effect::UploadFile(PUT presigned URL, local_path)
  -> Tick::PortProgress -> Persist upload_progress_percent
  -> Tick::PortReply(upload)
  -> Persist pending_media stage=complete
  -> PersistAtomic(stable props + delete pending_media journal)
  -> Tick::PortReply(local completion)
  -> 所有附件完成
  -> Effect::Http POST {api_base_url}/posts/create
  -> Effect::ScheduleTimer(15000ms)
```

当前媒体链只有 **Java 预签名请求 + 对对象存储的直接 PUT + Helix 本地 completion**；
PUT 成功后不会再调用 Java `/oss/complete`。稳定 `props` 只保留 `bucket`、`fileId`、
`uri`、`name`、`contentType`、`size`、`sha256` 等消息引用。预签名 URL 和签名
headers 是短期秘密，写 `pending_media` journal 时故意置空，失败或重启后必须重新申请票据。

上传进度通过 `Tick::PortProgress` 回灌并持久化，文件消息可更新
`upload_progress_percent`；它不是终态 `PortReply`。任一步失败都会把消息变为 `unsend`
并留下可安全重试的媒体事实。重启扫描不会自动上传，而是把未完成媒体恢复为失败态；
用户执行 `im_retry_send` 后复用同一 `temporaryId`，重新申请预签名票据再上传。

### 3.1 HTTP SUCCESS 的真实含义

`createPost` 在 `CreateCsesPostWithTrack` 返回 nil 后立即回复：

```json
{
  "status": "SUCCESS",
  "message": "post sender success"
}
```

这个响应 **没有 `data.id`**。启用 Pulsar 时，它只证明 payload 已成功投递到
`post_sender-1`，并不证明 consumer 已完成 DB commit 或 WS 广播。未配置 producer 时，
同步 fallback 会在落库与广播完成后才返回，但 HTTP wire 仍不带 server id。

另外 Go 的 `CommonRes` 无论成功失败都写 HTTP 200，业务成败必须看 `status`：
`SUCCESS`、`failed` 或 `FINISH`。

### 3.2 Go 的权威持久提交

consumer 的 `SendPosts` 在每频道 lane 内先执行强一致事务：

```text
post
+ channel / channel_member 计数投影
+ channel_event(type=new, event_seq)
+ delivery_outbox
```

单条 fast path 通过 `CommitSinglePostMessageTx` 完成；通用路径使用
`SavePostsInTx -> appendEntPostCreateEventCoTx -> insertDeliveryOutbox`。事务成功后才
`publishPostEvent`。重复的 `(channel_id,user_id,temporary_id)` 由 Go 的
`post_idempotency` 事实返回已提交 post identity，不再新建第二条事件。

`publishPostEvent` 使用：

```json
{
  "action": "post",
  "data": {
    "id": "server-post-id",
    "temporaryId": "same-client-identity",
    "channelId": "channel-id",
    "userId": "sender-id",
    "message": "hello",
    "eventSeq": 42,
    "event_seq": 42,
    "props": {
      "channel_event_seq": 42
    }
  },
  "event_seq": 42
}
```

当前 `publishPostEvent` 没有设置 `OmitConnectionId` 或 `OmitUsers`。因此从现行 Go
代码看，sender 只要仍是频道成员且连接在线，就与其他在线成员一样经过
`ShouldSendEvent(channelId)`，会收到自己的 `post` echo。跨 pod 时先本地 hub，再经集群
转发到远端节点。

## 4. HTTP 回报与 WS authority 是两条并行归并路径

### 4.1 当前 HTTP PortReply 行为

`handle_outbound_send_http_reply` 的实际行为是：

| HTTP PortReply | 当前 Helix 行为 |
|---|---|
| `PortOutcome::Err` | 立即写 `send_status=unsend`，CancelTimer，Emit `im:post:send-failed`。 |
| 信封/JSON 非法或 `status != SUCCESS` | 不推进，等待 15s timer 失败。 |
| `SUCCESS` 且响应含合法 26 字符 post id | 按 `temporary_id` 覆写 `id=server_id,status=sent`，CancelTimer。 |
| `SUCCESS` 但无 server id | **当前代码仍写 `send_status=sent` 并 CancelTimer**，但保留 `PendingSend` 等 WS echo 后补 server id。 |

最后一行是当前实现事实，不是理想合同。它与“只有合法 server post id 才能进入 Sent”的
目标不一致，而 Go `createPost` 的正常响应恰好不带 id。验收时应把这个差异单独列为待修，
不能把 HTTP admission 冒充 DB/WS authority。

### 4.2 WS post 入站和 temporaryId 对账

## 5. sender / receiver 双视角如何落库

连续 `post` authority 会编译为一个 `Effect::PersistAtomic`，包含：

1. `message`：以 `temporary_id` upsert 服务端 post 事实。
2. `channel`：更新 `last_post`、`last_post_at`、`last_root_post_at`。
3. `channel_member(channel_id, viewer_user_id)`：写当前 viewer 的未读绝对态。
4. `channel_event_cursor`：单调推进 `last_event_seq`。

双视角只在 `channel_member` 的当前 viewer 行分叉：

| 视角 | 判断 | 本地写入 |
|---|---|---|
| sender | `post.userId == auth_user_id` 或 echo | `unread_count=0`，清 `unread_post_id`，同步更新 lastPost。 |
| receiver | 可见且 sender 不是本人 | `ScopedGuardedBump unread_count += 1`，写 `unread_post_id` 和 lastPost。 |
| 不可见成员 | viewers 不包含当前用户 | 不落可见消息，不增加未读；sync 时只允许 cursor phantom 前进。 |

未读不是 UI 自己 `+1`，也不是全群共用一个值。每个客户端由 Helix 按自己的
`auth_user_id` 计算并写当前 viewer 的 `channel_member` 复合键行。

原子提交的 `PortReply::Ok` 到达后，Helix **还不会立即 Emit**。它先执行：

```text
Effect::Persist {
  ScopedGet channel_member
  key = (channel_id, auth_user_id)
}
```

只有这个持久读回成功，才顺序发布：

```json
{"event":"im:post:received","data":{"id":"server-post-id","temporaryId":"same-id","channelId":"channel-id","userId":"sender-id","message":"hello","type":"TEXT","createAt":1785370000000,"eventSeq":42,"sendStatus":"sent"}}
{"event":"im:channel:update","data":{"channelId":"channel-id","lastPost":{"id":"server-post-id","userId":"sender-id","message":"hello","createAt":1785370000000},"unreadCount":0}}
```

receiver 的第二条结构相同，但 `unreadCount` 为原值 `N+1`。这两个事件来自本地表的持久
事实与读回，不从 raw WS payload 直接拼 UI 终态。

## 6. EventSink 如何到 PC 和 Mobile

`Effect::Emit` 在 host `dispatch_effects` 中同步调用 `EventSink::emit`。

| 平台 | 当前出口 |
|---|---|
| Native/PC | `NativeEventSink` 写入 Tokio broadcast；消费者从 receiver 读取 `DomainEventBytes`。 |
| FFI/Mobile | `FfiEventSink` 在一个 engine step 内先缓冲全部 Emit，step 末编码为一个 batch，只调用一次 `on_domain_events_batch`。 |
| Web | `WebOwnedEffect::Emit` 交给浏览器 glue 兑现。 |

这里没有 Frame 或 Surface 包装。需要注意：Native EventSink 是非阻塞 broadcast；没有订阅者
时事件会被丢弃并记录 metric，EventSink 不是 durable queue。本地 SQLite 才是重建依据。

## 7. “离线发送”必须拆成三种情况

### 7.1 sender 在无网状态点击发送

当前 `handle_send_message` **没有以 `ConnState` 阻止命令**，所以仍会：

1. 本地乐观落库 `sending`。
2. sender 收到 `im:post:sending`。
3. 乐观 PersistOk 后尝试 `POST /posts/create`。
4. `HttpRequester` 返回网络 `PortError` 时立即写 `unsend`、CancelTimer，并 Emit
   `im:post:send-failed`。

当前没有自动离线队列或后台自动重发。失败后必须由用户动作触发 `im_retry_send`。

### 7.2 请求可能已到 Go，但 HTTP 回包丢失

这是“不确定提交”边界：

- Go 如果已经完成 DB commit，在线 WS echo 可以先于 HTTP error/timeout 到达，并按
  `temporaryId` 收敛为 sent。
- 若随后断线，Go 的 `post + channel_event` 仍是持久权威；重连同步能把它补回。
- 若 Go 从未接收请求，本地最终是 failed，等待手动 retry。

`temporaryId` 是跨 retry、HTTP、WS、sync 的幂等身份。重试不能创建第二个 identity。

### 7.3 receiver 离线，sender 在线发送

Go 不要求 receiver 在线才提交消息。receiver 没有 live socket 时只是不收到实时 WS；
`post` 和 `channel_event` 已在 Go DB。

receiver 重连后：

```text
driver Tick::Connected
  -> 等 Go hello
  -> Tick::Inbound(action=hello)
  -> handle_hello 保存 connectionId
  -> Effect::Http POST /channels/load/increment
  -> increment_channel / increment_channel_end
  -> 对需要补偿的 channel 发 POST /channel/sync/notify
  -> Go 返回 events + viewer-filtered messages + nextSeq
  -> Tick::PortReply(SyncPull)
  -> 同一 message/channel/channel_member/cursor PersistAtomic
  -> 持久读回
  -> im:post:received + im:channel:update
```

Go 离线同步 endpoint：

```text
POST /api/cses/channel/sync/notify
body = {"cursors":[{"channelId":"...","fromSeq":41}]}
```

Go 按 `channel_event.event_seq` 返回 `no_change`、`events`、饱和 events slice 或 `too_long`。
`events` 同时带当前 caller 可见的 `messages` map；完全非成员被 fail-closed 为不泄露真实
maxSeq 的 no_change，私密 viewers 不可见的消息只推进 phantom cursor。

## 8. timeout 与 retry

### 8.1 15 秒 timeout

`Tick::Timer` 命中 `PendingSend.timeout_timer` 且状态仍非 `Sent/UnSend` 时：

1. `send_status` 写为 `unsend`。
2. 发布 `im:post:send-failed`。
3. 不产生新的 HTTP，因此不会自动补发。

HTTP 明确失败会立即走相同终态，不等 15 秒。HTTP success 或 WS echo 会 CancelTimer。

### 8.2 手动 retry

```json
{
  "name": "im_retry_send",
  "payload": {
    "message_id": "same-temporary-id",
    "req_id": "retry-request-id"
  }
}
```

重试路径：

1. 内存有 `PendingSend`：只接受 `SendStatus::UnSend`。
2. 进程重启或内存 miss：先 `Effect::Persist(Get message by temporary_id)`。
3. 从 durable `message` 行重建原 camelCase body；只允许 `send_status=unsend`。
4. 复用同一 `temporaryId`，分配新的 timer/correlation。
5. 写回 `sending` 并 Emit `im:post:sending`。
6. PersistOk 后重新进入普通 `posts/create` 链。

所以当前具备“重启后可手动重试”，但不具备“启动时扫描所有 failed/sending 自动排队重发”。
`on_start` 只扫描 channel cursor，并不会扫描 message 表构造 durable send outbox。

## 9. 当前实现的明确缺口

1. **HTTP admission 被提前当作 Sent**：Go 正常 `SUCCESS` 无 server id；Helix 当前仍写
   `send_status=sent` 并撤 timer。若合同要求合法 server id 才能 Sent，这里尚未达标。
2. **没有 durable 自动发送队列**：本地 `message` 能保存 failed/sending，retry 也能读回，
   但没有启动扫描、FIFO、自动重试或网络恢复自动 drain。
3. **旧注释仍有漂移**：部分发送代码注释仍写 “surface/timeline V2”，实际生产下行已经是
   MessageV3 Emit；不能据这些注释恢复 Frame/Surface。
4. **本文件是源码审计，不是真链路 Green**：Go producer、PG commit、双账号 WS、PC EventSink
   消费和 Mobile FFI callback 仍需要各自 runtime 证据，不能由 Rust replay 代替。
