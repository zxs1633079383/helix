# 发送衔接竞态修复与验证

日期：2026-09-08。仓库：Helix，分支：reactor/MessageV3-helix。

## 缺陷与修复

P1 乐观消息落库成功后，附着窗口的本地读回携带 deferred_send_http。
新的同窗口查询推进 generation，旧读回原先直接返回，导致 posts/create 和
15 秒发送 timer 都不产生。公开 ImModule::handle 回归在修改前稳定断言失败：
HTTP 数量实际 0、期望 1；修改后通过。这证明代码缺陷，不能倒推截图中两条
历史请求必然经过该分支，历史逐跳证据仍缺。

修复仅让旧本地查询丢弃窗口投影后继续其消息发送。WS transport reset 保留
这类本地回包关联，身份切换仍删除。第二个断线回归也先红后绿。
正常最新窗口的投影顺序、P1 持久化门槛、发送请求格式与原有 timer 均保留。
发送 timer 从 HTTP 启动计算 15 秒；本修复没有增加从用户点击到终态的总超时。
已留在旧进程/数据库中的 sending 不会因源码修改自动重发。

## 并发与复杂度

- 同窗口连续发送、普通查询插入、四频道交错、1,024 条读回逆序完成均覆盖。
- 每条消息断言独立 HTTP、对应 channelId/temporaryId、唯一 15 秒 timer；
  重复回包没有副作用，逐条触发 timeout 均有对应 send-failed 投影。
- 过期分支按 temporaryId 平均 O(1) 查找；请求复制/序列化为 O(消息体长度)。
  没有新增锁、线程、队列或全 pending 扫描；transport reset 保持原有
  O(correlation 数量) retain，只扩展保留条件。
- 1,024 条是可控交错正确性回放，不是网络并发吞吐；release stress 也只测
  sans-IO 内核。没有向 PRE 发起容量压测，不声明海量连接/RPS 上限。
