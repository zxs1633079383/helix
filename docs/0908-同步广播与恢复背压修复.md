# 同步广播与恢复背压修复

本轮完成源码行为修复与本地真实 Go/Native 链路验收。PRE 仍运行旧镜像；本报告不把未部署代码称为线上已修复。

## 原因与领域边界

旧恢复一次生产 2436 份完整频道投影，经 WS 增量队列发送；单连接 bulk 容量 2048，满时关闭整条 WS。请求中的 connectionId 头未传到发布范围，恢复还会扇出至该用户其他连接。重复 hello 可重置恢复状态并触发额外请求。跨 Pod 转发只有发布入队语义，没有远端消费者持久化 ACK，不能靠阻塞本地 Hub 修复端到端背压。

Go application 负责成员/公司权限和投影；store 端口负责成员查询，HTTP 层只转换协议。Helix IM 负责恢复状态机和持久化门槛；core 不引入 HTTP、数据库或运行时依赖。Native/FFI/Web 复用同一业务语义。

## 已实现行为

1. 旧 WS 路径把 HTTP connectionId 传入 data/end 广播；接收端同时校验连接 ID 与明确的用户 ID。跨节点转发保留范围。旧客户端缺少 connectionId 时保留用户路由兼容。
2. Go hello 增加 `incrementPageVersion: 1`。新 Helix 仅在明确协商后使用 `POST /channels/load/increment/page`；旧 Go 保持旧协议。
3. 首响应返回按 `update_at DESC, id ASC` 冻结的 ID manifest，以及最多 64 个完整投影。续页只携带下一批最多 64 个 ID；服务端重新校验用户、公司、成员归属，并恢复 manifest 顺序。期间活跃度变化不能导致翻页跳项或重排。
4. Helix 同时只允许一个分页 HTTP 或一个本页 PersistAtomic。整页验证完成后才生成写操作，PersistOk 后才更新内存恢复集合并请求下一页。失败、断线和旧关联不继续请求、不发成功；新的连接可重新恢复。
5. 全页落库后复用既有 global-end / sync 调度与最终持久化屏障，最终发 `im:channel-sync-ready`，由既有本地查询链消费。空清单也经过持久化屏障。
6. 相同活跃连接的重复 hello 幂等；新连接或断线后的 hello 仍恢复。合法的启动扫描补偿保留，在分页在途时合并到当前流。
7. 新增分页请求、页持久化、逐频道提交诊断，保留关联号。实时与 bulk 队列容量均仍为 2048。

初次库存扫描和 ID manifest 为 O(N)，包含首批选择所需的频道元数据；完整投影每页最多 64。续页成员查询限于当前 64 ID，cursor 只发送当前页，避免每页重复扫描/传输全部库存形成 O(N²)。不引入服务器分页会话，续页可命中其他 Pod。此合同不是跨所有页的数据库时间点快照，期间的成员/业务变化仍由重新鉴权及既有实时恢复合同处理。

## 复跑方式与运行边界

在 Go worktree 按 `scripts/cnpg-test-dsn.sh` 取得测试 DSN，创建本轮独立临时目录，设置 `CSES_IM_INCREMENT_NATIVE_FIXTURE` 后运行 `go test ./internal/api -run TestIncrementPageHTTPPressure -count=1 -v`。Go 写出 ready.json 后，读取其中 httpBase/wsUrl 作为 `MESSAGEV3_GO_HTTP_BASE` / `MESSAGEV3_GO_WS_URL`，设置 `MESSAGEV3_ENV=local`、`MESSAGEV3_PHASE_POOL=0` 和同一夹具目录，运行：

```text
cargo test -p helix-driver-native --test increment_pull_real increment_pull_real_go_sqlite_ready -- --ignored --nocapture
```

Native 无论断言成功或业务失败均写 done 释放 Go 夹具，Go 等待上限十分钟。两端测试都需成功才算完整验收。

新 Go 与新 Helix 配对后，根频道恢复投影不再进入 WS bulk 队列；旧客户端仍走旧 WS 路径，不能保证旧客户端大库存不再溢出。单频道/话题旧路径保持兼容。部署顺序为先让所有 Go HTTP/WS 节点具备分页 API，再发布 Helix 客户端；混合节点期间不能只部署带 capability 的 WS 节点而让 HTTP 落到无该 API 的旧节点。
