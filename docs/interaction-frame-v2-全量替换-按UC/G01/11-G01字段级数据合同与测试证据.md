# G01 字段级数据合同与测试证据

> 结论来自当前 Helix、cses-client 源码、单元测试和 WDIO IPC Mock。本文不把 fixture、Mock 或静态类型升级为真实 Go/PG/双端运行证据。

## 1. 最终顺序

当前 G01 普通文本发送的准确顺序是：

1. `MessageUiComposer` 产生用户意图。
2. `ShellService.sendText()` 直接组装 `im_send_message`，不是调用 `ActionBinding`。
3. `HelixCommandPort` 经 Tauri invoke 发送 `{ payload: commandPayload }`。
4. Tauri 返回 `AcceptedCommand`；这只证明命令已入队。
5. Native adapter 把命令变为 `Tick::Command(AppCommand)`。
6. `ImModule::handle_send_message` 校验输入、由 Helix 分配 `temporaryId`、构建 `CreatePostBody`。
7. Helix 建立内存 `PendingSend(status=Local)`，输出 P1 `Effect::Persist` 和一个旧式 `im:post:sending` 诊断 emit。
8. Driver 把 `message.send_status=sending` 写入 SQLite，并以 `Tick::PortReply(P1, Ok)` 回灌。
9. Helix 推进 `PendingSend Local -> Sending`，查询已 attach 的 Timeline。
10. SQLite Timeline readback 回来后，Helix 形成第一个正式 `InteractionFrameV2`，其中只有 `message.timeline`，消息 `delivery.kind=sending`。
11. 同一因果阶段才释放 `Effect::Http(posts/create)` 和 `Effect::ScheduleTimer(15s)`。
12. Tauri Native sink 只验证外层 `event/data/schemaVersion=2`，不解析或重组 VM。
13. `im:__bus__ -> ProjectionBusService -> ProjectionStore -> SurfaceRuntime` 严格解码整帧。
14. `SurfaceRuntime` 校验 transaction、slot、scope、epoch、revision，先 stage 全部 mutation，再原子 swap。
15. Angular 回送 `FrameApplied`，随后 DOM 从 `MessageVm` 渲染 `sending`。
16. Go `posts/create` 在远端 PG 事务中提交 post、计数、event 和 outbox。
17. HTTP 成功、失败或 timer 让 Helix输出终态 `Effect::Persist`；WS `post` 也可按 `temporaryId` 做权威对账。
18. 终态 SQLite `PersistOk` 后再次 Timeline readback。
19. Helix 形成第二个正式 `InteractionFrameV2`：`delivery.kind=sent` 或 `failed`。
20. Angular再次原子 apply、回送 `FrameApplied`，同一逻辑行收敛到终态。
21. 如果本端或观察端还收到可 apply 的 WS `post`，通用 post handler 会另走
    `DialogPatchByPost`：先更新/读取本地 channel 绝对累计值，再输出 Dialog Frame。

这里必须纠正两个顺序误解：

- `Effect` 不是 `Persist` 之后的单一步骤。`Persist`、`Http`、`Emit`、`ScheduleTimer` 都是 `Effect` 的不同变体。
- `Surface` 不是 Frame 之后的对象。Surface mutation 是 `InteractionFrameV2.mutations[]` 的组成部分；客户端再按 `(surface, canonicalScope)` 把它放入 `SurfaceRuntime` slot。

## 2. ActionBinding 在 G01 的真实位置

### 2.1 当前发送入口不走 ActionBinding

`ShellService.sendText()` 调用私有 `sendMessage()`，直接发：

```json
{
  "channel_id": "<active-channel>",
  "type": "TEXT",
  "text": "<composer-text>",
  "req_id": "<client-generated-correlation>"
}
```

可选字段是 `props`、`replied`。因此当前上行是：

```text
direct command -> Tick::Command
```

不是：

```text
ActionBinding(message.create) -> ActionInvocationEnvelope
```

当前 `ComposerVm.actions` 类型已经存在，但仓内没有 `message.create` binding 的 G01 producer。

### 2.2 G01 Frame 里的 ActionBinding 是消息行能力

`sending`、`sent` fixture 的 `MessageVm.actions[]` 都包含现有消息可执行能力，例如：

- `reply`
- `forward`
- `react`
- `urgent`
- `createTopic`
- `revoke`
- `retry`
- `urgentConfirm`
- `urgentCancel`
- `markRead`
- `viewReceipt`
- `templateConfirm`
- `locate`

字段合同：

| 字段 | 类型 | Owner | 约束 |
|---|---|---|---|
| `actionRef` | `string` | Helix | opaque capability；Angular 不得构造或改写 |
| `kind` | `string` | Helix | renderer 选择控件/输入适配 |
| `inputShape` | `string` | Helix | 描述 action input 形状 |
| `surfaceEpoch` | safe `u64/number` | Helix | 必须大于 0；上行原样回送 |
| `enabled` | `bool` | Helix | false 时客户端必须禁止调用 |
| `disabledReason?` | `string` | Helix | disabled 的呈现原因 |

真正调用 binding 时才形成：

| `ActionInvocationEnvelope` 字段 | 语义 |
|---|---|
| `schemaVersion=1` | Action 上行 envelope 自己的版本域，不是 Frame V1 |
| `requestId` | action 因果键 |
| `actorId` | trusted platform runtime 注入 |
| `surface` | binding 所在 Surface |
| `scope` | binding 所在 canonical scope |
| `surfaceEpoch` | 从 binding/slot 原样复制 |
| `observedRevision` | 当前 ready slot revision |
| `invocation.actionRef` | opaque binding 引用 |
| `invocation.input` | 用户输入，值为 bounded `SurfaceDataVm` |

所以 G01 的类图必须同时画出 `ActionBinding`，但不能把它错误排在普通发送 command 前面。

## 3. 命令与受理字段

### 3.1 Angular command payload

| 字段 | 必填 | 来源 | 规则 |

`replied` 字段：

| 字段 | 语义 |
|---|---|
| `id` | 当前被回复消息 |
| `reply_id` | 被回复消息自己的直接回复锚 |
| `reply_root_id` | 线程根 |
| `reply_first_level_id` | 第一层分支锚 |

### 3.2 Tauri `AcceptedCommand`

| 字段 | 当前值/语义 |
|---|---|
| `reqId` | Native 确认的 request correlation |
| `command` | `im_send_message` |
| `helixCommand` | 实际入 Helix 的 command name |
| `accepted` | `true` 只表示 queue admission |

`accepted=true` 不能让 UI 自行插入 `sending`，也不能让 UI 标 `sent`。IPC reject 同样不能伪造成业务 `failed` Frame。

## 4. Tick 与 Effect

### 4.1 G01 会经过的 Tick

| Tick | G01 用途 | 路由 |
|---|---|---|
| `Command(AppCommand{name,payload})` | `im_send_message` 起点 | `Module::accepts()` |
| `PortReply{corr,outcome}` | SQLite P1、Timeline read、HTTP、终态 persist/read | `corr_map` O(1) 定向 |
| `Inbound(InboundBytes)` | WS `post` echo/recovery | `Module::accepts()` |
| `Timer(TimerId)` | 15 秒发送超时 | `timer_map` 定向 |
| `Connected/Disconnected` | 连接生命周期 | 非单次 G01 主路径 |

`now_ms` 不在 Tick 内，由 execution shell 单独注入。

### 4.2 G01 会输出的 Effect

| Effect | 字段 | G01 用途 |
|---|---|---|
| `Persist` | `corr, ops[]` | P1 乐观行、sent/failed 身份与状态 |
| `Http` | `corr, req` | `POST /api/cses/posts/create` |
| `Emit` | `event: DomainEventBytes` | 正式 V2 Frame；另有旧式 sending diagnostic |
| `ScheduleTimer` | `id, after_ms` | HTTP 真正出站后 arm 15 秒 |
| `CancelTimer` | `id` | HTTP/echo 已知终态后撤销 |
| `PersistFire` | `ops[]` | timer 失败态的幂等写；无 PortReply |

同一个 step 返回的 `Vec<Effect>` 没有执行顺序保证。真正的先后必须由 `Correlation -> Tick::PortReply` 切成多个 step。这正是 P1 persist barrier 的原因。

## 8. “三个 Frame”纠错

### 8.1 当前 producer 明确存在的 Frame

1. `sending.frame-v2.json`
   - 一个 `message.timeline` mutation；
   - `MessageVm.id=temporaryId`；
   - `eventSeq=0`；
   - `delivery.kind=sending`。

2. `sent.frame-v2.json`
   - 一个 `message.timeline` mutation；
   - revision 从 2 推进到 3；
   - `MessageVm.id=serverId`；
   - `delivery.kind=sent`。

另有 `failed.frame-v2.json`，它是 sent 的失败分支，不是成功发送链的第三帧。

### 8.2 direct G01 replay 没有第三个 `messageDialogLeft` Frame

`g01_wdio_fixture_contract_test.rs` 对 sending、sent、failed 三个 producer 输出逐个断言：

```text
surface_names(frame) == {"message.timeline"}
all mutations have SurfaceId::MessageTimeline
```

因此，“direct command producer 固定依次发送
`sending -> sent -> messageDialogLeft` 三个 Frame”不符合当前测试。

`message.left-dialog-list` 的类型和 producer 能力确实存在：

- scope 是 `{kind:"user",userId,teamId}`；
- VM 是 `DialogListVm{sections,state}`；
- row 是 `DialogRowVm`；
- mutation 是 `dialogListSnapshot` 或 `dialogListPatch`。

它有两类真实入口：

1. 独立 dialog query/recovery/snapshot；
2. WS `post` 被 channel gate apply 后形成 `PendingDialogPatch`，执行
   `GuardedBump + Get(channel)`，在 `DialogPatchByPost` 的 `PortReply::Ok` 后输出 Frame。

第二类就是运行日志中可能看到的“第三个 DialogLeft Frame”，但必须带上三个限定：

- 它依赖 WS `post` 是否送达本端，以及该 post 是否被 gate apply；
- 它与 HTTP terminal 使用不同 correlation，所以可能在 `sent` 前或后到达；
- 它至少包含 `message.left-dialog-list`，当 unread contribution 变化时同一 Frame 还会配对
  `message.unread-summary`，不是名为 `messageDialogLeft` 的独立 Frame 类型。

cses-client 的 `snapshots.json` 和 `patch-transaction.json` 还能证明 `SurfaceRuntime` 可原子应用
Dialog + Unread + Timeline 多 slot，但它们本身仍不能证明一次 G01 运行一定产生 Dialog Frame。

### 8.3 当前 Dialog Frame 的字段与时序

当前条件链是：

```text
Tick::Inbound(post)
-> channel gate apply
-> Persist message/cursor and collect PendingDialogPatch
-> Effect::Persist {
     bump_channel_unread_op,
     get_channel_row_op
   }
-> Tick::PortReply(DialogPatchByPost, Ok(channel row))
-> patch_from_dialog_projection_with_causation
-> Effect::Emit(InteractionFrameV2)
```

Frame 内：

- scope 是 `{kind:"user",userId,teamId}`；
- `message.left-dialog-list` mutation 是 `dialogListPatch + replaceView`；
- `DialogListVm` 是 `sections[] + state`；
- `DialogRowVm` 包含
  `channelId/channelKind/rootMessageId/title/avatar/companyTag/preview/lastActivityAt/`
  `unreadCount/mentionCount/urgentCount/topicCount/memberCount/memberLeaves/`
  `hasScheduledMessage/isTop/notificationMode/lifecycle/settingsVersion/purpose/header/actions`；
- 如果 unread aggregate 真的推进，同一 Frame 追加 `message.unread-summary` mutation；
- 若 channel readback 为空或写失败，跳过 emit，禁止把 event delta 冒充绝对累计值。

## 9. SurfaceRuntime apply 算法

输入完整 Frame 后：

1. `decodeInteractionFrame` 严格校验 schema 和所有闭合字段。
2. `recentTransactions` 检查重复 `transactionId`。
3. 对每个 mutation 计算 `(surface, canonicalScope)` slot key。
4. 未 attach 的 mutation 跳过，不变成 UI 本地事实。
5. 对 attach slot 检查上一版 `surfaceEpoch/revision`。
6. Patch 出现 revision gap 时，不提交同一 Frame 的任何 staged slot，并请求 resync。
7. 任一 attach mutation stale 时，整帧不 swap。
8. 全部通过后一次性写 `states`，更新 action revision index。
9. 原子更新 `runtimeState` 和 `transactionId` 去重表。
10. 按 committed `causationId` 收敛 pending ActionBinding overlay。
11. `version` signal 只 bump 一次，组件观察到一致快照。
12. 尝试全部 directive。
13. 产生内容为空的 `FrameApplied{transactionId,appliedSlots,result}`。

复杂度：

- Frame apply 为 `O(k + a)`，`k` 是 mutation 数，`a` 是新 VM 中 action refs 数；
- slot、transaction、pending action 查找为 Map 的均摊 `O(1)`；
- 没有让 Angular 按 raw event 重算 Timeline/Dialog/Unread 的 `O(n*m)` 业务归并。

## 10. FrameApplied

字段：

| 字段 | 语义 |
|---|---|
| `transactionId` | 已处理 Frame 的 transaction |
| `appliedSlots` | 实际 staged 并 swap 的 attach slot 数 |
| `result` | `applied` 或 `directive-failed` |

它只在完整 Frame commit 且 directive 已尝试后产生，不能带 `mutations`、`directives` 或消息正文。Tauri transport 成功后，客户端诊断计数 `frameAppliedAcks` 才增加。

## 11. IPC Mock 到底证明什么

`TauriMockBridge` 严格拆成两条独立通道：

### 11.1 command receipt mock

`mockAccepted()` 只 mock `im_send_message` invoke 返回：

```json
{
  "reqId": "...",
  "command": "im_send_message",
  "helixCommand": "im_send_message",
  "accepted": true
}
```

此时没有 Frame emit。对应单元测试断言 `emit` 尚未调用。

### 11.2 Frame replay

`replay()` 只接受：

- `schemaVersion === 2`
- `mutations.length > 0`

随后通过 Tauri event plugin 发：

```json
{
  "event": "im:__bus__",
  "payload": {
    "channel": "im:interaction:frame",
    "payload": {
      "event": "im:interaction:frame",
      "data": "<complete-frame>"
    }
  }
}
```

WDIO `g01-mock-sent` 的顺序是：

```text
mock AcceptedCommand
click send
replay Helix-derived sending Frame
assert DOM sending
replay Helix-derived sent Frame
assert DOM sent and one invoke
```

`g01-ipc-rejected` 则证明 invoke reject 不会产生业务 failed DOM。

Mock 绕过 Rust/Tauri engine/SQLite/HTTP/WS/Go/PG，只证明：

- 真实 Angular UI 点击；
- 当前 Tauri event ingress 形状；
- V2 codec；
- SurfaceRuntime revision/atomic apply；
- typed component/DOM 状态。
