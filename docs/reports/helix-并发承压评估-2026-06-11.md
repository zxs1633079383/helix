# Helix 并发承压评估（实测版）

> 2026-06-11 · 四专家审查（rust / runtime-agnostic / tauri-skeleton / dioxus-core）+ 对抗证伪 + release 压测实跑。
> 问题：core + driver-native + helix-im 现状能否扛「海量并发、高频操作」IM 场景。
> 压测机：i7-13700K / 64GB，`--release`（workspace profile 为 opt-level="z"+lto 面向 wasm 体积，数字偏保守）。
> 压测代码（资产，已入库）：`crates/helix-im/tests/stress_test.rs` · `crates/helix-driver-native/tests/{stress_storage,stress_engine}.rs`

## 一句话判定

**内核层完全能扛（高出现实入站速率 2-3 个数量级）；存储层与事件泵层现状不能裸扛——1 个实测复现的死锁 + 9 倍写放大 + 2 个功能性断点。修复清单明确，全部是局部改动。**

## 实测数字（分层）

| 层 | 测项 | 实测 | 判定 |
|---|---|---|---|
| 内核 step | 10 万帧顺序入站（含 JSON parse + Effect 构造） | **53.7 万帧/秒**（单帧 1.86µs） | ✅ 远非瓶颈 |
| 内核 gate | 5000 缺口乱序堆积 / 补洞单 step 放行 5001 条 | **94-97 万事件/秒**（5.1-5.3ms） | ✅ |
| 内核 sync | 593KB · 5000 事件 sync 响应 parse+构造 ops | **8.9ms** 消化完 | ✅ |
| 存储 | batch_upsert 现状（逐行 autocommit） | **1.3 万行/秒** | ⚠️ 能用不富裕 |
| 存储 | 同 SQL 包显式事务基线 | **12.2 万行/秒 → 写放大 9.0x 坐实** | 🔴 必修 |
| 存储 | monotonic_upsert（cursor 热路径） | **7.4K 次/秒**（每次跑 CREATE TABLE DDL） | ⚠️ 必修 |
| 端到端泵 | 裸灌 >256 个 Command | **永久死锁（实测复现）** | 🔴 P0 |
| 端到端泵 | 守 in-flight=100 背压后 | 9.7K persist 环/秒 | 与存储上限同量级 |

## 证实的瓶颈（对抗证伪后存活，按优先级）

| # | 问题 | 位置 | 事实 | 修法 |
|---|---|---|---|---|
| **E1·P0** | **泵死锁**：PortReply 回灌与入站 Tick 共用 cap=256 有界 mpsc，且 dispatch 同步 `await` 全部 Persist 完成才收下一帧——洪峰 >256 pending 即环形等待冻结 | engine_loop.rs:193-214/321-323 | 实测复现 | PortReply 走独立通道（或 unbounded 回灌）+ dispatch 不阻塞 join（fire-and-track） |
| **E2·P0** | **batch_upsert 无事务**：逐行 autocommit，N 行 = N 次 WAL 提交 | storage.rs:172-195 | 实测 9.0x | 包 `begin()/commit()`，顺手复用 SQL 字符串 |
| **E3·P0** | **needs_continuation 被 `_` 忽略**：离线同步 >500 条截断不续拉 = **丢消息**（功能 bug 非性能） | module.rs:195 | 证实 | Events 分支按 needs_continuation 续发 sync Http |
| **E4·P0** | **scan_corr PortReply 路由缺失**：on_start 的 cursor 加载吐了 Scan 却无人消费回报 = 死代码，proactive resync 实际不工作 | module.rs:559-567 + handle_port_reply | 证实 | handle_port_reply 加 scan_corr 分支：解析 rows → register_channel |
| **E5·P1** | monotonic_upsert 热路径每次跑 `CREATE TABLE IF NOT EXISTS` | storage.rs:243-264 | 实测拖到 7.4K/s | 建表挪到 `open()` 一次性 |
| **E6·P1** | gate buffer（BTreeMap）无客户端容量上限，唯一防线是服务端 too_long | channel.rs:55/151 | 证实 | ingest 入口加 len 上限 → 主动触发 too_long 路径 |
| **E7·P1** | broadcast(1024) 慢消费者 lagged **静默**丢事件，UI 无感知 | event_sink.rs:52 | 证实 | 监听 lagged 计数 → 触发 UI 全量刷新事件 |
| **E8·P2** | timer 查找 O(N) 线性扫描（gate / pending_send） | module.rs:294-321 | 证实 | TimerId→owner 反向索引 |
| **E9·P2** | 热路径分配未达零分配承诺（列名 String 元组、scope_key to_string、consume_effects 深拷贝 ops） | to_effect.rs / engine_loop.rs:116-143 | 证实 | 静态列名表 + Cow + ops 移交而非克隆（HX-C005 追踪） |

## 被证伪的（不要再当瓶颈说）

- **「按 table 分组导致全串行」**——表面属实（first_table_key 确实按表名分组），但**不是吞吐根因**：SQLite 单写锁下同库写本就串行，按 channel 分组收益在攒批与隔离而非并行写。降级 minor；与设计文档 §3.2 的表述差异保留为对齐项，非性能项。

## 答辩口径

> 「内核 50 万帧/秒、乱序缓冲百万级——**架构选型被实测证明正确**；当前瓶颈全部在驱动兑现层的工程细节（事务包裹、回灌通道、续拉），共 4 个 P0，每个都是局部修改、有实测基线可对照验收（修完事务包裹即白拿 9 倍）。这正是 sans-IO 切分的价值：性能问题被隔离在 driver 边缘，内核与业务逻辑零改动。」

## 修复后实测（同日闭环，E1-E4 + B1 全部落地）

| 项 | 修复前 | 修复后 |
|---|---|---|
| 泵死锁（>256 裸灌） | 永久冻结 | **10k 裸灌全闭环不冻结**；新增 graceful drain（关闭后断言全落盘） |
| batch_upsert 5000 行 | 369ms（13.5K 行/秒，放大 9.6x） | **~40-60ms（82K-122K 行/秒，放大 ~1.0x）** |
| 有界背压下泵吞吐 | —（无背压，OOM 路径） | 6.0-6.5K 环/秒（队列 1024 + 背压传导回入站） |
| 离线同步 >500 事件 | 截断丢消息 | 自动续拉至完成（fromSeq 单调终止保证 + inflight 守卫） |
| proactive resync | 死代码（回报无人消费 + 扫虚构表） | 工作（路由 0 + 对齐 `_helix_monotonic` 真实 schema） |

修复经对抗 review 拦截 4 条 blocking 后回炉收口（多表路由保序 / 无界队列 OOM / shutdown 空洞 / scan schema 错位），全量 85 测试 + 三栖 + 双闸门绿。E5-E9（P1/P2）仍在待办。

## 2026-06-12 E5/E10 重测 + stress-verify 对抗审 verdict（销 ROADMAP D5 一半）

> 触发：用户问「core+driver+业务压测了吗 / 能否扛通用业务海量涌入」。主对话重跑三层 + 落地 E10 + 跑 `stress-verify` workflow 对抗审。**结论：单模块写已实测充分；「通用业务海量涌入」主张被对抗审 REJECT——证据只覆盖单模块独占写，真问号是多模块并发写。**

### 三层重测数字（macOS i7-13700K dev，/tmp 真 APFS，--release，warm）

| 层 | 测项 | 实测 | 对照 06-11 |
|---|---|---|---|
| 内核 step | 10万帧顺序入站 | 44.0-52.8 万帧/s | 同量级（机器/负载抖动） |
| 内核缓冲 | 5000 乱序堆积 | 92.1-97.2 万帧/s | 同量级 |
| 内核 flush | 补洞单 step 放行 5001 | 87.0-90.0 万事件/s | 同量级 |
| 存储 batch | batch_upsert 5000 行 | 91-100K 行/s，**放大 ~1.0x（A≈B）** | E2 修复稳定 |
| 存储 cursor | monotonic_upsert | E5 后 FULL **8.1K/s** → E10 后 NORMAL warm **15-18K/s** | E5 仅 7.4K→8.1K（DDL ~10%）|
| 端到端泵 | 10k 裸灌无窗 / 背压窗 | **22K 环/s（不死锁）/ 21K 环/s** | E1 修复稳定（数字随机器升） |
| 端到端泵 | graceful drain | 500 commands → DB=500 全落盘 | ✅ |

### E10（synchronous=NORMAL）真实增益：~2x，**不是数量级**

- cursor：FULL 8.1K → NORMAL ~16K ≈ **2x**（macOS）。pre-E10 storage.rs 无 synchronous pragma = SQLite 默认 **FULL**（git `d58dff1~1` 已核），故此对比是真实 FULL→NORMAL 同仓对照。
- ⚠️ **「822 calls/s」retract**：该数字（曾见于 ROADMAP/待办清单）**本仓从未实测**，是外部引用值，本机 baseline 已 8.1K 远高于它，不能作 E10 基线。已在两文档标注撤回。
- ⚠️ **方法学软肋**（对抗审指出，采纳）：8.1K vs 16K 是「跨一次代码改动 + 两次独立 run」，非单测内 FULL/NORMAL 干净 A/B。要严格证明需单测内先 FULL 测、再 NORMAL 测。
- ⚠️ **平台依赖**（对抗审指出，采纳）：macOS `fsync` 弱（不默认 F_FULLFSYNC），FULL 本就偏轻 → 2x。**生产 Linux 真盘（fdatasync 重）上 FULL 可能真接近百/千级、NORMAL 才是数量级**——macOS 数字不代表生产，E10 价值平台依赖。

### 「通用业务海量涌入」= REJECT（证据不足，非架构错）

stress-verify 对抗审 verdict=REJECT。**架构没问题，是主张超出数据**——已实测的全是**单模块独占写池**峰值。四个真缺口（按重要性）：

1. 🔴 **单写者池 + 多模块并发写未测**：`sync_write_pool`/`user_write_pool` 都 `max_connections=1`。22K/90K 是单模块串行独占数字。第二个通用模块（presence 高频状态 / docs 实时协作）接入后，所有 `batch_upsert` 竞争**同一个写连接**，WAL commit 写锁独占 → 在 `user_write_pool.begin()` 串行排队（`busy_timeout=5s` 是超时兜底非并发能力）。**这才是「通用海量」的真瓶颈，零实测。**
2. 🟠 **生产 Linux 真盘数字缺**：全部 macOS 弱 fsync 数字，不代表生产。
3. 🟠 **wasm/FFI 存储无基线**：`WasmStorage` 的 batch/monotonic/get/scan 全 `todo!()`（M3 才做），所有存储性能主张仅 native 成立。
4. 🟡 **E9 未修**：`scope_key: channel_id.0.to_string()`（to_effect.rs:36）每事件 cursor 热路径仍堆分配，违 HX-C005。

> 注：对抗审有一处事实错误（称「E10 前后都跑 NORMAL」）——主对话查 git 史证伪（pre-E10 = FULL 默认）。但其余三点全部成立并采纳。这也是「对抗审默认倾向 reject + 主对话复核」的正确闭环：审计抓真问题，主对话挡误判。

### 修正后答辩口径

> 「内核层 44-52 万帧/s、业务无关——通用海量入站无压力，已实测。存储**单模块**写健康（batch 90-100K 行/s 放大 1.0x、cursor NORMAL ~16K/s）、端到端泵 22K 环/s 不死锁有背压。**但『多模块并发写单写者池』是通用海量的真问号，尚未实测**；生产 Linux 数字 + wasm 存储 + E9 零分配三项待补。架构选型正确，缺的是『多模块并发写』这条 benchmark 和 driver 兑现层三项工程细节。」
