Architecture review — helix

2026-06-22

Sans-IO 六边形内核。端口层是深的，无需动 —— Transport / Storage / Clock / EventSink / HttpRequester / IdSource 都是小接口、真接缝、删除测试通过。 摩擦集中在 helix-im 的有状态心脏（gate / 效果生产 / 关联路由）与 core 的 Effect 表面（类型缺失的契约）。 下列候选都尊重既有 ADR 与 HX-C 不变量；与之冲突处单独标注。

Problem

cursor 单调性这个核心不变量没有 locality —— buffer、timer arm、flush、unread-bump 决策分散在 6+ 文件，timer 派发还是 O(N) 全扫。

Solution

把 gate 升成深聚合：对外只露 ingest / advance / on_timer / peek / commit，buffer + timer 反向索引 + flush + bump 应用全部藏进实现。

  • locality：不变量归一处
  • 删除测试：现在跨 6 caller 复活
  • timer O(N) → O(1) 反向索引
  • 测试打一个接缝，不用编排 4 文件
  • handler 退化成"解析+转交"
  • 顺带消化 channel.rs 518 行超限债
✅ 与 ROADMAP E8 timer 反向索引 同向；与过会"头号风险（乱序 backfill proptest）"对齐 —— 收成单接缝后，那条 proptest 终于有干净的测试面可打。

2 · 统一 IM→Effect 的防腐接缝

Strong in-process

acl/to_effect.rs (748) · acl/to_effect_s1.rs (207) · channel.rs (event_to_upsert_op / event_to_storage_op / edit_content_op / revoke_op / apply_read_op)

Before — 三个事实源，调用方各自 import

to_effect.rs
message upsert · cursor · sync_notify
to_effect_s1.rs
members · nickname · channel_set_cols
channel.rs
edit / revoke / read 的 op 工厂

⚠ s1 文件因 300 行硬顶被迫切出，不是因内聚切出。kind→op 的 dispatch 在 channel.rs 又重复一次。

After — 一个 kind-dispatched 入口

acl::to_effect(event) → Vec<StorageOp>

kind 1/2/3/6 + channel/member 内部按表分派

调用方一个 import，编译器保证 edit 帧走 edit op。

Problem

同一职责（IM 概念 → core Effect）被切成 3 个事实源，kind→op 映射靠 caller 内联 match，没有类型保证覆盖完整。

Solution

一个 kind-dispatched 入口承担全部翻译；内部可再拆小文件，但接缝只有一个，调用方不挑工厂。

  • leverage：一个接缝，N 个 caller
  • kind 分派归一处，不再重复
  • read_bits 不被 edit 覆盖等坑收进实现
⚠ 内部拆分仍须守 300 行硬顶（structure-gate WHITELIST）；接缝统一是目的，文件数不是。

Problem

ImWsContext 是纯数据穿透，字段全 pub(crate)，corr 分配靠从 module.rs 注入 4 份相同闭包；handler 拿到无界 &mut state，没法挂不变量检查。

Solution

给 context 一个小接口（corr() / gate(id) / now()），裸 state 藏到实现后；handler 只拿它需要的能力。

  • 删 4 份重复闭包
  • 不变量可在接口处断言
  • 测 handler 不用塞全 state
⚠ 依赖候选 1（gate 聚合）先落 —— gate(id) 才有东西可返回。建议接在候选 1 之后。

4 · 把"必达 / fire" 编进类型，而非命名

Worth exploring ports & adapters

helix-core/src/effect.rs (304–400)

Before — 区分靠后缀 + 文档

Persist { corr, ops } // 必达，等 PortReply

PersistFire { ops } // fire，可丢

Http { corr, req } // 必达

HttpFire { req } // fire

区别只在后缀 + EFFECT-5 注释。写错无编译报错 → 静默丢数据 / 悬挂等待。

After — 兑现语义进类型

enum Fulfillment { MustReply(Correlation), Fire }

Persist { how: Fulfillment, ops }

Http { how: Fulfillment, req }

"是否必达"成为编译期事实，driver 的背压契约挂在 Fulfillment 上。

Problem

必达 vs fire-and-forget、无序兑现、背压"绝不 drop"全是文档契约（EFFECT-2/5），不是类型属性；core↔前端唯一对话面缺类型护栏。

Solution

把兑现语义折进一个 Fulfillment 标签，让 Effect 变体减少、契约可被穷尽匹配。

  • Effect 变体收窄
  • 契约从注释升类型
  • driver 兑现穷尽可查
⚠ 触及 core 公开面 —— 过会拍板 #2「cargo public-api 冻结公开类型面」会红。须配套更新快照基线 + DomainEvent 契约版本化（拍板 #5）。这是收敛公开面、不是扩张，值得为它过一次基线。

Problem

Solution

corr 来源收口到已有的 IdSource 端口；一次调用同时分配 id + 登记 Continuation，让 reply 路由可穷尽。

  • 魔数防撞 → 端口保证
  • alloc+登记一步，删 4 闭包
  • 第二个模块加入也不撞
✅ 这正是 BLK-1b 注释里写明的"更健壮方案"，且 core 的 IdSource 端口已经在那里 —— 接线即可，不新增公开类型。

6 · FFI handle 生命周期收成一个 owned 类型

Worth exploring FFI / ports & adapters

helix-driver-ffi/src/api.rs (55–217, 733 lines)

Before — 6 步销毁协议漏给 C++

tick_tx: Mutex<Option<Sender>>
shutdown_tx: Mutex<Option<oneshot>>
pump_thread: Mutex<Option<JoinHandle>>
destroy()：take→take→join 严格时序

所有权散在三个 Mutex<Option>；销毁顺序 + "禁 panic"约束 + ctx 存活窗口全压给 C++ 调用方。

After — 一个深生命周期类型

struct PumpHandle { … }
impl Drop → 有序收束（一处）

C-ABI 只露 create / command / destroy；时序不变量藏进 Drop，extern "C" 仅薄转发。

Problem

opaque 指针的所有权语义没被藏住 —— 三个 Mutex<Option<T>> + 6 步销毁顺序泄漏成 C++ 调用方的责任（HX-C006 说应隐藏）。

Solution

把 tick/shutdown/thread 收进一个 owned PumpHandle，时序不变量落到 Drop；extern "C" 退成薄转发。

  • 销毁时序归一处
  • C++ 责任面缩小
  • 顺带消化 api.rs 733 行债

7 · Storage Spec 的列名 stringly-typing

Speculative ports & adapters

helix-core/src/effect.rs (104–290) — UpsertSpec / GuardedBumpSpec / Row = Vec<(String, SqlValue)>

观察 — Spec 是 SQL 参数容器

UpsertSpec { table: &str,

rows: Vec<(String, SqlValue)>,

conflict_key, exclude_from_update }

列名是裸 String，没有编译期 schema 校验；错列要到 driver SQL 执行才炸。helix-im 调用方必须背列名。

张力 — 这是有意的通用原语

GOAL §1.6 + ADR-004 明确：core 的 Spec 故意通用，把业务 schema 挡在 core 外。

所以这不是"业务泄漏"，而是"SQL 形状 vs 类型安全"的取舍。深化（列名 newtype / 让 driver 从高层请求 codegen 出 spec）可能重新翻 ADR。

⚠ 与 GOAL §1.6 / ADR-004 张力 —— 仅当 helix-im 端真的频繁踩"错列运行时才炸"时才值得重开。否则维持现状。列为 Speculative，不建议现在动。

刻意不动（既有取舍，非摩擦）

  • • ExecutionShell::step() → &[Effect] 借用 scratch：这是 HX-C005 热路径零分配的有意设计，返回 Vec 会违反铁律。保持借用语义。
  • • 端口层全员（Transport / Storage trait / Clock / EventSink / Http / IdSource）：删除测试全过，真接缝（native + ffi + host 多适配器）。无需深化。
  • • helix-driver-host 共享存储/网络：已是深接缝，native/ffi 薄壳委托，ADR-007/010 兑现。模块注册归属的 native/ffi 不对称是文档问题，非代码重复。
  • • wasm 适配器：探查时被计入"适配器数"，但 ADR-006 已归档暂停维护 —— 不计入交付，也不作为深化对象。

Top recommendation

先做 候选 1 — channel gate 深聚合

它压住的是唯一被标 CRITICAL 的摩擦：cursor 单调不变量没有 locality，散在 6+ 文件、timer 还是 O(N)。 收成一个深接缝后，候选 3（context 接口）、候选 5（corr 路由）都有了干净落点，过会"头号风险"那条乱序 backfill proptest 也终于有单一测试面可打。 一个动作，concentrates 最多复杂度 —— 删除测试在这里失败得最响。

建议顺序：1 → 3 → 2 → 5 →（4 需过 public-api 基线）→ 6。候选 7 暂缓。
