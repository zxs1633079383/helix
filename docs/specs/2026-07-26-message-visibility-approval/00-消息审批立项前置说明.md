# 公司大群消息审批：立项前置说明

> 本文用于方案评审开场。先确认需求、依赖和责任是否成立，再讨论具体架构。

## 1. 当前结论

根据当前同步口径，公司大群消息审批**本期不进入研发交付**。

原因不是消息侧无法实现，而是立项前提尚未完整：

1. 当前版本组织架构不支持审批所需的多任职、多上级、动态负责人解析等能力。
2. 新版组织架构是否覆盖这些能力、何时可用，尚未形成明确合同。
3. 组织架构团队未来是否需要通用审批组件，目前没有确定规划。
4. 审批能力的长期 Owner、双方投入和联调排期尚未确认。

因此当前状态建议定义为：

> **需求已识别，方案已预研，依赖和责任未就绪，暂不承诺上线时间。**

## 2. 需要先确认的问题

在进入技术方案前，需要先回答四个问题：

### 2.1 是否确定要做

- 这是明确业务需求，还是预留能力？
- 是否属于下一期正式范围？
- 哪类消息必须审批，解决的业务风险是什么？
- 业务负责人和最终验收人是谁？

### 2.2 组织能力何时具备

- 新版组织架构是否支持多任职、多上级和关系类型？
- 是否支持查询部门负责人和最终部门成员？
- 是否提供组织变更事件、组织版本和人员有效性查询？
- 能否给出稳定 API、负责人和可联调时间？

### 2.3 通用审批能力由谁维护

审批流程不应因为首个场景是消息，就默认沉淀在 IM。

当前只有组织架构和消息两个核心团队，需要在立项时明确：

- 组织架构团队是否承接独立通用审批组件。
- 消息团队是否仅负责业务接入和最终投递。
- 若选择消息侧内建，是否明确接受公共能力绑定 IM 的长期成本。

### 2.4 是否具备可执行排期

- 双方交付物是否清楚。
- 最小组件合同是否能够冻结。
- 是否有共同联调窗口和验收环境。
- 依赖延期时由谁决定缩范围、延期或切换方案。

## 3. 职责建议

### 核心责任团队

| 团队 | 建议职责 |
|---|---|
| 组织架构团队 | 组织事实、组织 API、变更事件；推荐承接独立通用审批组件 |
| 消息团队 | 消息场景、内容引用、审批接入、最终 `viewers` 和消息投递 |

双方是核心 Owner，不虚构不存在的第三个组件团队。

### 需要配合的角色

| 角色 | 配合事项 |
|---|---|
| 业务/产品 | 确认范围、审批规则、优先级和验收口径 |
| PC、Flutter、Web | 审批入口、待办、状态和操作结果展示 |
| 测试 | 发起人、审批人、目标成员和非目标成员的端到端验证 |
| 安全/权限 | `viewers`、附件、搜索、回复和历史读取的权限审计 |
| 运维/中间件 | 新组件部署、事件可靠性、监控和 SLA；仅在独立部署时介入 |

这些角色提供产品、端侧和质量保障，不替代组织架构与消息团队的核心责任。

## 4. 进入方案评审的 Gate

以下条件全部明确后，再进入具体方案：

- [ ] 需求确定进入正式版本，并有业务 Owner。
- [ ] 组织架构能力范围、接口负责人和可用时间明确。
- [ ] 通用审批组件或消息侧兜底方案的长期 Owner 明确。
- [ ] 双方交付物、联调窗口和验收标准明确。

若管理层要求在条件未齐备时继续推进，需要同步确认：

- 接受哪些依赖风险。
- 谁承担延期责任和临时建设成本。
- 是否接受公共审批能力进入 IM。
- 后续抽离和接管由谁负责。
