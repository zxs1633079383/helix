# 公司大群消息审批：立项前置说明

> 我们以消息团队视角同步当前判断。本文只确认现状、边界、风险和下一步，不展开技术实现。

## 1. 当前判断

当前V1版本组织架构不具备消息审批所需能力；新版组织架构能够支持到什么范围、何时可用，目前尚未确认。组织架构团队未来是否有通用审批组件需求，也没有明确规划。

从当前计划看，新组织架构可以为消息审批提供用户、公司、部门、成员和权限基础，但多任职、多上级、组织变更事件及通用审批组件均未进入明确范围。因此这份计划目前只能视为消息审批的基础依赖计划

基于以上现状，我们建议先确认需求是否正式立项、组织能力何时就绪以及双方长期责任，再进入具体技术方案。

我们对当前状态的定义是：

> **需求已识别，依赖和责任尚未就绪，本期暂不承诺交付时间。**

如果在前置条件未满足时继续推进，我们需要同步明确风险接受人、长期维护责任，以及未来重复建设和能力抽离成本。

## 2. 当前事实

我们目前确认的事实包括：

- 当前不存在可以直接复用的通用审批组件。
- 组织架构支持多任职、多上级和动态负责人解析等能力尚未明确。
- 新版组织架构的能力范围、接口合同、稳定版本和可用时间尚未确认。
- 组织架构团队未来是否建设或使用通用审批组件尚未明确。
- 当前核心责任方只有组织架构团队和消息团队。

## 3. 我们负责什么

作为消息团队，我们可以承担：

- 梳理公司大群消息审批场景和验收用例。
- 保存待审消息正文、附件、内容 revision 和摘要哈希。
- 接入审批服务，提交业务引用并回查审批状态。
- 消费审批完成事件并处理重复、乱序和失败恢复。
- 在正式投递时解析目标成员，生成最终 `viewers`。
- 幂等创建正式消息，并完成 PC、Flutter、Web 的状态展示。
- 配合组织架构团队完成首个业务场景联调和验收。

消息内容、消息可见性和最终投递仍由我们负责。

## 4. 我们不建议承担什么

我们不建议将以下能力默认沉淀在 IM：

- 通用审批流程定义和执行。
- 逐级 N、会签和或签的公共状态机。
- 通用审批任务、权限、转交和代理。
- 跨业务复用的审批审计和历史记录。
- 组织关系解析规则及组织变化后的任务重算。

这些能力并非消息场景独有。由我们在 IM 内长期维护，会让公共业务能力反向依赖消息系统。

## 5. 未来功能冗余与架构成本

如果我们先在 IM 内建设完整审批能力，后续公告、通知、权限申请、组织流程等场景仍可能重新建设同类能力。

未来冗余不仅是重复代码，还包括：

- 流程模型、节点规则和状态定义重复。
- 审批任务、动作权限和转交逻辑重复。
- 多任职、多上级和负责人解析重复。
- 审批记录、审计口径和查询接口重复。
- 监控、告警、补偿和运维责任重复。
- 不同业务对同一组织变化产生不一致处理。

即使后续再将能力抽离，我们仍需承担接口迁移、历史实例迁移、数据兼容、双写切换和责任转移成本。

因此，我们希望在立项时先确认长期边界，而不是先完成一套消息内实现，再处理已经形成的架构债务。

## 6. 需要组织架构团队确认的事项

我们需要组织架构团队明确：

- 新版是否支持多任职、多上级和可配置关系类型。
- 是否支持查询部门负责人、有效任职和最终部门成员。
- 是否提供组织变更事件、组织版本和人员有效性查询。
- API 负责人、接口稳定时间和可联调时间。
- 未来是否存在通用审批组件需求或建设规划。
- 是否愿意承接边界独立的通用审批组件。

这些确认用于冻结双方依赖，不要求组织架构团队理解消息内部存储和投递实现。


## 7. 进入技术方案前的 Gate

我们建议以下条件全部明确后，再进入两套技术方案：

- [ ] 需求正式立项，并明确业务责任边界和目标版本。
- [ ] 新版组织架构能力范围、接口负责人和可用时间明确。
- [ ] 通用审批能力的长期 Owner 明确。
- [ ] 双方交付物、联调时间和验收标准明确。
- [ ] 若选择消息侧内建，明确接受功能冗余、长期维护和抽离成本。

Gate 未通过时，我们保持方案预研状态，不承诺研发排期。

## 8. 管理层坚持推进时需要明确的风险

如果决定在前置条件未齐备时推进，我们需要同步确认：

- 哪些组织能力缺口被接受，临时方案是什么。
- 依赖延期和整体交付风险由谁接受。
- 是否接受通用审批能力阶段性进入 IM。
- 消息团队是否长期维护。
- 其他业务出现同类需求时，如何避免继续重复建设。

这些事项需要形成明确结论。
