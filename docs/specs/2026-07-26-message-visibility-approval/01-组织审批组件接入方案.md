# 方案一：组织侧建设通用审批组件

> **推荐方案**
>
> [方案决策稿](./README.md) · [架构图](./01-组织审批组件接入架构.mmd)

## 1. 背景与目标

公司大群开启审批后，普通发送、跨部门发送和部门定向消息需要先经过审批，再按最终组织成员生成 `viewers` 并投递。

审批中的逐级 N、会签、或签、转交、任务权限和审计都具备通用属性，不建议沉淀在 IM。当前只有组织架构和消息两个团队，建议由组织架构团队建设并维护独立审批组件，消息团队负责首个业务场景和投递闭环。

目标是解决两件事：

1. 消息审批按期落地。
2. 审批能力可以继续复用，不形成公共能力依赖 IM 的反向链路。

## 2. 核心判断

- 组织架构服务继续负责人员、部门、任职和上下级关系。
- 审批组件与组织架构服务模块隔离，但由组织架构团队承担生命周期。
- 消息系统继续负责正文、附件、revision、最终 `viewers` 和正式消息。
- 审批组件只持业务引用、摘要和摘要哈希，不复制消息内容。
- `APPROVED` 仅代表流程通过，`DELIVERED` 才代表消息发送完成。

## 3. 职责边界

| 能力 | 组织架构团队 | 消息团队 |
|---|---|---|
| 组织事实 | 人员、任职、多上级、负责人、成员和变更事件 | 通过 API 使用，不复制组织数据 |
| 审批组件 | 流程、节点、任务、权限、审计和事件 | 提交业务上下文并消费结果 |
| 待审内容 | 不保存正文和附件 | 保存内容 revision 和摘要哈希 |
| 审批详情 | 提供任务授权凭证 | 按任务权限返回内容 |
| 正式投递 | 不创建消息 | 生成 `viewers` 并幂等创建正式消息 |
| 端侧展示 | 输出权威状态与允许动作 | Helix 统一投影，三端机械渲染 |

双方以 API、事件和状态合同协作，不要求组织架构团队理解消息内部存储，也不让消息系统实现通用流程能力。

## 4. 业务链路

1. 用户在公司大群提交消息，选择目标部门或指定人员。
2. 消息系统读取审批开关并请求策略判定。
3. 明确免审时走原发送链；未命中规则时默认审批。
4. 消息系统保存待审内容，向组件提交业务引用、摘要和摘要哈希。
5. 审批组件创建实例，每进入一个节点都重新查询组织架构。
6. 所有目标分支通过后，组件发布完成事件。
7. 消息系统回查权威状态并校验 revision 与摘要哈希。
8. 消息系统按投递时组织架构重新解析部门成员，合并指定人员并去重。
9. 消息系统幂等创建一条正式消息。

目标部门 ID 在提交时固定，部门成员不冻结。

## 5. 一期范围

- 发起人上级链，支持配置最多 N 级。
- 目标部门负责人。
- 多任职、多上级和关系类型。
- 串行、会签、或签。
- 同意、拒绝、退回、发起人撤回。
- 转交当前任务，不改变后续节点规则。
- 多部门和指定人员分支全部通过后统一发送。
- 无审批人默认阻塞，可配置 fallback、继续上溯或跳过。

一期不做流程设计器，不建设大而全的 OA 平台。

## 6. 最小组件合同

组织架构团队需要提供：

- 幂等创建审批实例。
- 查询实例、当前节点、任务和允许动作。
- 同意、拒绝、退回、撤回和转交。
- 节点进入时动态解析审批人。
- 组织变更触发当前未完成节点重算。
- 可靠完成事件和权威状态查询。
- 消息投递结果回写。

组件内部表结构、存储选型和实现方式不进入双方接口合同。

## 7. 并行推进

| 阶段 | 组织架构团队 | 消息团队 | 共同产出 |
|---|---|---|---|
| 合同冻结 | API、事件、状态和组织解析 | 业务引用、摘要和投递合同 | 场景及异常用例 |
| 并行开发 | 审批组件和组织 Adapter | 内容、审批 Adapter 和投递链 | Mock 联调 |
| 集成联调 | 节点推进、任务权限和事件 | 回查、成员解析和正式投递 | 全链路验证 |
| 验收 | 审批状态和组织审计 | `viewers` 与消息投递证据 | 多角色正反向结果 |

## 8. 关键规则

- 组织变更事件只作为触发信号，组件仍需回查组织 API。
- 只重算当前未完成节点，已完成决定不回滚。
- 退回修改后产生新 revision 和摘要哈希，旧任务失效。
- 目标为空、部门失效或组织查询失败时阻断，不能降级为全员可见。
- 完成事件只负责通知，消息系统必须回查权威状态。
- 重复或乱序事件不能创建第二条正式消息。

## 9. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 首次建设带来协作成本 | 先冻结最小合同，再并行开发 |
| 组件建设范围膨胀 | 一期只覆盖消息所需通用内核 |
| 跨系统状态不一致 | 事件通知、状态回查、摘要校验和幂等 |
| 最终人员变化 | 投递时重新解析部门成员 |
| `viewers` 旁路泄露 | 上线前完成读取、定位、回复、搜索和附件权限审计 |

产品口径 `channel.type = 0` 与当前 Go `ChannelTypeOpen = "O"` 的协议映射也需要在开发前确认。

## 10. 结论

建议按本方案推进。它能够完成当前消息审批，同时避免把公共流程能力长期绑定到 IM。

若最小组件合同在约定里程碑内无法冻结，应重新评审范围、资源和方案选择；方案二不自动生效，也不默认将缺口转由消息团队承接。
