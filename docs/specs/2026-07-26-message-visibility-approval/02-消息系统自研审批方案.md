# 方案二：消息侧内建审批

> **兜底方案，需单独评审**
>
> [方案决策稿](./README.md) · [架构图](./02-消息系统自研审批架构.mmd)

## 1. 适用场景

当组织侧无法在约定里程碑内提供最小审批组件，而消息审批又有明确上线期限时，可评审由消息团队在 `cses-im-server` 内建设 `message_approval` 模块。

该方案交付路径更短，但会把通用审批能力绑定到 IM。它不是与方案一并列的长期优选，而是业务期限优先时的兜底。

## 2. 核心方案

- 组织架构团队只提供组织 API 和组织变更事件。
- 消息团队自行实现审批策略、流程实例、任务权限、节点收敛和审计。
- 审批模块与既有消息发送链保持边界。
- 所有目标分支通过后，审批模块只发出“允许投递”的事实。
- 既有消息链继续负责 `post`、`viewers`、`channel_event`、outbox 和 WS。

一期不拆独立微服务，也不做通用 OA 平台。

## 3. 职责边界

| 能力 | 组织架构团队 | 消息团队 |
|---|---|---|
| 组织事实 | 人员、任职、多上级、负责人、成员和变更事件 | 通过 API 使用 |
| 审批流程 | 不负责 | 策略、实例、节点、任务和审计 |
| 组织变化 | 发布事件 | 回查 API 并重算当前节点 |
| 待审内容 | 不负责 | 保存正文、附件、revision 和摘要哈希 |
| 正式投递 | 提供最终成员 | 生成 `viewers` 并创建正式消息 |

## 4. 业务链路

1. 用户提交消息并选择目标部门或指定人员。
2. 消息系统读取审批开关并执行策略判定。
3. 明确免审时直接发送；未命中规则时默认审批。
4. 消息系统保存内容 revision，创建审批实例和目标分支。
5. 每进入一个节点时调用组织 API 解析审批人。
6. 审批模块完成逐级 N、会签或或签收敛。
7. 全部分支通过后进入 `APPROVED`。
8. 投递 Worker 回查实例并校验 revision 和摘要哈希。
9. 消息系统按最新部门成员生成 `viewers`。
10. 既有消息链幂等创建一条正式消息。

## 5. 一期范围

- 发起人上级链和目标部门负责人。
- 多任职、多上级和关系类型。
- 串行、会签、或签。
- 同意、拒绝、退回、撤回和当前任务转交。
- 多目标分支全部通过后统一发送。
- 无审批人默认阻塞，可配置 fallback、继续上溯或跳过。

## 6. 模块边界

`message_approval` 至少包含：

- `Policy`：判定免审或选择流程。
- `ApprovalInstance`：维护状态、目标和内容 revision。
- `NodeResolver`：进入节点时查询组织 API。
- `ApprovalTask`：维护审批人、允许动作和转交关系。
- `NodeEvaluator`：处理串行、会签和或签。
- `DeliveryReceipt`：保证只创建一条正式消息。

这些能力不能直接堆叠在现有发送 handler 中，否则后续无法独立演进或抽离。

## 7. 状态与一致性

```text
RUNNING
  -> BLOCKED / RETURNED
  -> REJECTED / WITHDRAWN
  -> APPROVED
  -> DELIVERING
  -> DELIVERED / DELIVERY_FAILED
```

- `APPROVED` 不等于消息已发送。
- 审批动作使用任务版本控制。
- 会签和或签在事务内完成节点收敛。
- 审批完成事件通过 outbox 发布。
- 正式投递使用唯一业务键，重复执行返回同一 `post_id`。
- 目标为空或组织查询失败时禁止写入空 `viewers` 或全员可见值。

## 8. 收益与成本

**收益**

- 消息团队可以独立排期。
- 审批状态和消息投递在同一服务，排障链路更短。
- 可以直接围绕消息 revision 和 `viewers` 设计。

**成本**

- 消息团队长期维护流程、任务权限、组织变化和审计。
- 公共审批能力反向依赖 IM。
- 其他业务仍可能重复建设。
- 后续抽成公共组件需要迁移合同、实例和运维责任。

## 9. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 公共能力绑定 IM | 独立领域模块和清晰端口，保留抽离条件 |
| 流程复杂度被低估 | 一期冻结范围，补齐并发和异常用例 |
| 组织数据不一致 | 只通过权威 API 和事件接入 |
| 重复或乱序导致多发 | outbox、状态回查和投递幂等 |
| 可见性旁路泄露 | 上线前统一审计所有 `viewers` 读取路径 |

## 10. 启用条件

以下条件需要同时成立：

1. 方案一无法在约定里程碑内形成最小组件合同。
2. 消息审批存在明确且不可后移的上线期限。
3. 评审明确接受公共能力进入 IM 的架构成本。
4. 消息团队获得长期维护授权，或双方明确后续抽离和接管责任。

条件未满足时，继续按方案一推进。方案二不能因为组织侧延期而自动生效。
