# 公司大群消息发送审批：方案决策稿

> 前置入口：[公司大群消息审批：立项前置说明](./00-消息审批立项前置说明.md)
>
> 本页仅在立项前置 Gate 通过，或管理层明确接受未满足项风险后进入。两份方案文档用于支撑本页结论，不要求评审人先阅读实现细节。

## 一、建议结论

**建议选择方案一。**

由组织架构部门建设和维护边界独立的通用审批组件，消息部门承担首个业务场景、验收用例、消息接入和最终投递。

双方并行建设：

- 组织架构部门不需要理解消息内部存储、Helix 或投递实现。
- 消息部门不实现通用流程引擎，也不复制组织关系。
- 审批组件只持业务引用、摘要和摘要哈希。
- 消息系统仍是正文、附件、最终 `viewers` 和正式消息的唯一 Owner。

若组织侧在双方约定的里程碑内无法提供最小组件合同，必须重新评审是否接受方案二的架构债务，不能自动转由消息团队承担。

## 二、本次需要拍板

1. 是否同意以方案一作为目标架构。
2. 是否同意组织架构部门负责通用审批组件的建设、发布和 SLA。
3. 是否同意消息部门负责首个场景、接入、验收和最终消息投递。
4. 是否同意方案二只能经过再次评审后启用。

本次不评审数据库表结构、具体接口字段和页面设计。

## 三、为什么是通用组件

逐级审批、会签、或签、任务权限、转交、退回、审计和状态回查都不属于消息特有能力。

消息场景特有的只有：

- 待审消息正文与附件。
- 目标部门和指定人员。
- 审批通过后的 `post.viewers`。
- 正式消息、消息事件和投递回执。

如果把完整审批能力放进 IM，其他业务未来只能依赖消息系统或重复建设。由组织架构部门维护独立组件，则可以复用组织关系，同时保持组件本身不依赖具体业务。

## 四、方案比较

| 维度 | 方案一：通用审批组件 | 方案二：消息系统内建 |
|---|---|---|
| 定位 | 推荐目标架构 | 风险兜底 |
| 建设方式 | 两部门并行 | 消息部门单方承担 |
| 组织一致性 | 组件直接复用组织能力 | 依赖跨部门 API |
| 公共复用 | 可供其他业务接入 | 绑定 IM |
| 短期协作成本 | 较高，需要冻结合同 | 较低，消息侧可独立推进 |
| 长期维护 | 责任边界清晰 | 消息团队维护非核心能力 |
| 重复建设风险 | 低 | 高 |
| 后续迁移 | 无额外抽离 | 可能需要抽成公共组件 |

## 五、双方交付物

### 组织架构部门

- 独立审批组件及运行责任。
- 审批实例、节点、任务和动作权限。
- 逐级 N、串行、会签、或签。
- 同意、拒绝、退回、撤回和当前任务转交。
- 多任职、多上级、部门负责人等动态解析。
- 组织变更后的当前节点重算。
- 完成事件、权威状态查询、幂等和审计。

### 消息部门

- 消息发送审批场景与验收用例。
- 待审正文、附件、revision 和摘要哈希。
- 提交审批、状态回查和事件消费 Adapter。
- 审批详情的任务授权读取接口。
- 投递时重新解析目标部门成员。
- 最终 `viewers`、正式消息和幂等投递。
- PC、Flutter、Web 的统一审批状态展示。

## 六、最小组件合同

双方先冻结能力合同，不先讨论内部表结构：

1. 幂等创建审批实例。
2. 查询审批实例、当前节点和允许动作。
3. 同意、拒绝、退回、撤回和转交。
4. 进入每个节点时重新解析组织关系。
5. 无审批人时默认阻塞，支持显式 fallback、继续上溯或跳过。
6. 发布可靠完成事件，并提供权威状态回查。
7. 支持消息系统回写 `DELIVERED / DELIVERY_FAILED`。
8. 组件只保存业务引用、摘要和摘要哈希。

以上任一核心项缺失，都不能把“未来可以支持”当作当前合同已经成立。

## 七、并行推进方式

| 阶段 | 组织架构部门 | 消息部门 | 共同完成 |
|---|---|---|---|
| 合同冻结 | 审批 API、事件、状态和组织解析 | 业务引用、摘要、回查和投递合同 | 场景及反向用例 |
| 并行建设 | 审批组件和组织 Adapter | 内容、审批 Adapter 和投递链 | Mock 合同对接 |
| 联调 | 节点推进、任务权限、事件 | 事件消费、成员解析、正式投递 | 全流程与异常恢复 |
| 验收 | 审批状态和组织审计 | 消息、`viewers` 和投递证据 | 多角色端到端证据 |

联调入口是双方冻结的合同，不要求任何一方理解另一方内部实现。

## 八、兜底切换闸门

出现以下情况时，只能发起重新评审，不能自动切换为消息侧自研：

- 最小组件合同在约定里程碑内无法冻结。
- 组织侧无法提供逐节点动态解析或任务权限。
- 可靠事件、状态回查或幂等无法满足。
- 双方无法形成可执行的联调计划。

重新评审需要同时确认：

- 是否接受公共审批能力绑定 IM。
- 消息团队是否被授权长期维护。
- 其他业务如何避免重复建设。
- 后续抽离条件、接管责任和迁移成本由谁承担。
