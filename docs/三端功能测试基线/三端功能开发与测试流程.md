# 三端功能开发与测试流程

## 1. 目标

PC、Mobile 和 Web/后续平台共享 Helix 业务语义时，功能必须先在 Helix 中形成可回放、可审计的
标准，再由各端机械消费。测试文件存在、Mock 通过、HTTP 200、Frame 到达、UI 截图和双用户真实链
是不同证据，不能互相替代。

本流程适用于新增 Gate、修改既有 Gate、升级 Surface schema、调整 Fixture inventory，以及任何会
改变 PC WDIO 或 Mobile QuickJS/Venus/GTest 断言的功能。

## 2. 职责边界

| 层 | 负责 | 不负责 |
|---|---|---|
| Helix | command/observation、状态机、权限、Persist barrier、Frame、Fixture、provenance | DOM、Flutter Widget、平台测试替身 |
| cses-client | Fixture parity、Angular codec/SurfaceRuntime、Mock、single-real、dual-real、DOM 与 artifact | 补算业务字段、手写 Helix 终态 |
| Mobile | C++ SurfaceRuntime、FFI batch、QuickJS typed view、Venus 产品绑定、GTest | raw event reducer、手工修正 Fixture |
| Reviewer | pin/hash、证据分面、失败分类和最大可声明结论 | 用低等级证据补高等级 Green |

依赖方向固定为：

```text
Helix ScenarioRunner
  -> ImModule::handle
  -> Effect::Emit
  -> canonical Frame + provenance
  -> PC/Mobile byte-exact mirror
  -> consumer unit/contract tests
  -> Mock
  -> single-real
  -> dual-real/multiremote
  -> UI render evidence
```

## 3. 测试先行顺序

1. 在 Helix 写失败的行为测试，覆盖成功、失败、重放/迟到、恢复和原子拒绝。
2. 通过公开 `ImModule::handle` 回放产生 Frame，禁止测试直接拼业务结果。
3. 显式更新 canonical Fixture，普通测试只能比较 Golden。
4. 生成 `provenance.json`，至少记录 producer revision、schema、raw/semantic hash、surface inventory、
   参数白名单和文件 inventory。
5. PC 与 Mobile 运行同步脚本，先验证 source，再删除退役镜像并 byte-exact 复制新 inventory。
6. PC 先跑 codec/loader/parity/Mock，再跑 single-real 和 dual-real；multiremote 必须使用独立
   Actor/Observer 身份、profile、SQLite、端口和 artifact。
7. Mobile 依次覆盖 C++ decode/apply、完整 DomainEvent batch、QuickJS `im.surface.view()` 和 Venus
   产品绑定；涉及 Venus 的 Gate 必须运行对应 Venus gate。
8. UI 只从 typed Surface 读取数据。PC 断言 DOM，Mobile 断言 QuickJS/Venus typed view；真实 Widget
   像素证据仍需独立宿主测试。

## 4. Fixture 合同

- Fixture 目录、文件名和版本由 provenance 决定，消费者不得把 `.frame-v2.json` 写死为通用规则。
- 一个 Gate 可以同时包含不同 schema，例如共享 Dialog Surface 使用 V2、Timeline 使用 V3。
- 同步脚本必须 fail-closed 校验 inventory、schema、producer revision、raw hash、semantic hash 和
  surface inventory；不一致时状态是 `CONTRACT_DRIFT`。
- 动态替换只能落在 `parameterizableFields`；revision/epoch rebase 还必须落在 `rebaseFields`。
- Fixture 是 producer 证据，不证明真实 SQLite、Go、PG、WS、双用户或 DOM。

## 6. 命令模板

命令从各自仓根执行，工作区位置通过环境变量传入，不在代码或文档固定机器路径：

```bash
# Helix：先比较；只有明确更新 canonical inventory 时才设置 UPDATE_*
cargo test -p helix-im --test <gate>_wdio_fixture_contract_test
UPDATE_<GATE>_WDIO_FIXTURES=1 cargo test -p helix-im --test <gate>_wdio_fixture_contract_test

# PC
HELIX_ROOT=<helix-root> node scripts/message-wdio/sync-helix-fixtures.mjs --gate=<gate>
npm run message:wdio:contracts
npm run message:wdio:<gate>:mock
npm run message:wdio:<gate>:single-real
npm run message:wdio:<gate>:dual-real

# Mobile
HELIX_ROOT=<helix-root> make <gate>-fixture-sync
HELIX_ROOT=<helix-root> make <gate>-fixture-gate
make surface-runtime-gtest
make venus-<gate>-frame-gate
```

仓库没有对应命令时，不复制 G01 命令冒充覆盖；先登记 runner、manifest、test target 和报告合同。

## 7. 完成判据

| 状态 | 判据 |
|---|---|
| `DONE` | 任务声明的所有必需 lane 在同一版本窗口真实通过，required fail/skip 为 0 |
| `PARTIAL` | 单元/Fixture/Mock 已过，但 real、dual-user、UI 或其他必需证据未执行 |
| `BLOCKED` | 环境、账号、Go/PG/WS、driver、端口或宿主前置阻断 |
| `CONTRACT_DRIFT` | producer、pin、schema、Fixture、loader 或 UI contract 不一致 |

最终报告必须列出分母、实际执行命令、各 lane 状态、首个可信失败、artifact、未验证证据面和解除
停止条件。未实际运行的 real/multiremote/Venus/UI 不得写成 Green。
