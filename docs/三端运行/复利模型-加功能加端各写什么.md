# 复利模型 —— 加功能 / 加端,每层各写什么（发送 vs 撤回 实算）

> 给团队 / 新人讲「为什么是这个架构」的材料。用**发送消息**(第一个功能)和**撤回消息**(第二个功能)实算一遍:business 写一次三端共享,driver/host 按平台一次性铺轨,**第 N 个功能 ≈ 只写 im 一段 handle**。
> 关联:[`发消息全链路-三端.md`](./发消息全链路-三端.md)(链路图)· [架构设计 §4.5 发送机制](../过会方案/helix-core-im-架构设计.md)· [ROADMAP-full §1 两轴正交](../ROADMAP-full.md)· 代码层走读见各 crate `src/`(module.rs / pending_send.rs / storage.rs)。

---

## §0 心法一句话

**core 定义"词汇"(Tick/Effect),im 写"业务"(handle 里 push Effect),driver 干"脏活"(把 Effect 翻成真 SQL/HTTP/WS)。** `handle` 签名里**没有任何 I/O 句柄** → 你物理上没法在 im 调数据库,只能 `out.push(Effect::…)`。这是 headless 的强制力,也是复利的根。

---

## §1 发送消息:三端分别写什么

关键认知:**business 写一次,只有 driver/host 按平台各一份——而且那份是「通用胶水」,不是「发消息逻辑」。**

| 层 | native(桌面) | wasm(浏览器) | ffi(移动) | 写几份 |
|---|---|---|---|---|
| **core** Tick/Effect/step | ←──── 同一份 ────→ | **1 份,三端共享** |
| **im** 发送业务（乐观/对账/15s 超时/cursor） | ←──── 同一份 ────→ | **1 份,三端共享(业务大头)** |
| driver **Storage** | sqlx+SQLite | sqlite-wasm+OPFS | rusqlite | per-platform **3 份** |
| driver **Http** | reqwest | fetch | host 回调 | per-platform **3 份** |
| driver **Transport** | tokio-tungstenite | web-sys WS | host 帧注入 | per-platform **3 份** |
| **host 薄桥** | Tauri invoke/emit | postMessage | C ABI/SendPort | per-platform **3 份(极薄)** |

> **最关键一点**:driver/host 那 3 份是**按「能力」写一次,不是按「功能」写**。native 的 `Storage::batch_upsert` 写好后——发消息用它、撤回用它、收消息用它、第二个模块也用它。**driver/host 是一次性「铺轨道」投资,不随功能数量增长。**

发送消息(第一个功能)付的成本:im 业务 1 份(~100 行)+ core 0 + **driver/host ×3(地基,一次性大头)**。

## §2 撤回消息:复用多少

第二个功能起,**地基全摊销**,只付增量。撤回 = 在 im 加一个新 `handle` 臂,吐两个**已有**的 Effect:

```rust
// im 里新增一臂(伪码,与 handle_send_message 同构)
fn handle_recall_message(&mut self, cmd, out) {
    out.push(Effect::Persist { corr, ops: vec![upsert("messages", status="revoked")] }); // 本地标已撤回
    out.push(Effect::Http   { corr, req: DELETE ".../posts/{id}" });                     // 通知服务端
    out.push(emit_post_revoked(channel_id, msg_id));                                      // UI 更新气泡
}
```

| 层 | 撤回要写什么 | 三端 |
|---|---|---|
| core | **0 改**(`Persist`/`Http`/`Emit` 词汇已有) | —— |
| **im** | **+1 handle 臂(~30–50 行)** | **写 1 份 → 3 端自动一致** |
| driver ×3 | **0 改**(复用 `batch_upsert` + `http`) | —— |
| host ×3 | **0 改**(复用同一条 Command→Emit 通道 + `im:__bus__`) | —— |
| db | **0 改**(messages 的 `send_status` 多一个取值 `revoked`) | —— |

## §3 复利账(对比「没有 helix、三端各写一遍」)

| | 传统三端 | helix | 省 |
|---|---|---|---|
| 撤回的**业务逻辑** | iOS Swift + Android Kotlin + Web TS **各写 1 遍** = 3 份 | im **1 份**覆盖三端 | **省 ~2/3 业务码 + 0 漂移** |
| 撤回用的**网络/存储** | 三端各自调一遍 | driver **0 改**(复用) | **100% 复用** |
| 三端**一致性** | 三份手写,必漂移(同一个「撤回规则」三端可能算得不一样) | 同一份 `handle`,**字节级一致 + 可回放测试** | 漂移归零 |

**复利模型(一句话)**:
> 第 1 个功能付「地基税」(core + driver×3 + host×3);从第 2 个功能起,**每个新功能 ≈ 只在 im 写一段 `handle`,三端 0 改、自动一致**。
> **N 个功能 × 3 端,本来要写 3N 份业务,helix 只写 N 份** —— 这就是 `M×P` 塌成 `M+P` 落到代码上的复利。功能越多,地基越摊薄。

## §4 加功能时每层各写什么(速查)

| 你要加 | core | im | driver | db |
|---|---|---|---|---|
| 发消息 | 0 改 | `handle_send_message` 吐 4 Effect + 记账 | 复用(0 改) | messages |
| 撤回消息 | 0 改 | +1 handle 臂(Persist revoked + Http DELETE) | **0 改** | 复用 messages |
| 第二个模块(会议) | 0 改 | 新 `MeetingModule` + `register()` | **0 改** | 新业务表 |
| 上新端(wasm) | 0 改 | **0 改** | 重写三个 trait 实现 | OPFS sqlite |

**规律**:横向加业务 = 只动 im;纵向加端 = 只动 driver;**core 在交叉点永远不动**。

---

## §5 唯一例外(诚实)

如果某个新功能需要一种 driver **还没有的能力**(如「语音消息」要流式上传,现有 `Http` 不够)——那要在三端 driver 各补一次那个能力(per-platform),补完后又变成所有功能共享。撤回用的是现成 `Http(DELETE)`,所以 driver 0 改。

另:本文算的是**业务①(收发/状态)**的复利。**展示态**(如撤回后气泡显示「已撤回」)目前(无 core-view)仍在各端 UI 各写;接 [方向 A core-view](../过会方案/helix-core-view-方向A设计.md) 后,展示态也进 im,复利扩到展示层。
