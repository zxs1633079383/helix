# Helix 分层性能压测指标与工具方案

> 日期：2026-07-14
> 状态：方案待实施，本文不包含当前 `main` 的新跑分
> 范围：`helix-core` + `helix-im` + `helix-driver-host/native/ffi` + 真实 Go K8s 联调
> 上游对照：Go G-01 热点/多频道报告与 UC1-16 六档全链路报告

## 1. 决策摘要

Helix 应当建立独立性能证据链，且必须同时覆盖 HTTP、WS、Effect、Storage、Event/Projection 与 PortReply。但这些不能混成一个总 P99，必须按 sans-IO 边界分层归因：

1. `helix-core` / `helix-im` 只测确定性状态机、解析、gate、Effect 生成和投影构造。
2. `helix-driver-host/native/ffi` 测队列、调度、SQLite、HTTP/WS adapter、EventSink 与 FFI 批量跨边界。
3. Go/K8s 真链测端到端容量、服务端与网络影响，不能反推 Helix core 是瓶颈。
4. 热点单 channel 与多 channel 并行必须分测。多 channel 100 RPS 不等于单 channel 100 RPS。
5. 先补可归因指标和证据包，再根据 profile 优化；不先猜 core、SQLite 或队列。

Go 两份报告目前能作为负载模型输入，不是 Helix 性能结论：

- 热点单频道只正式证明到 5 RPS。
- 25/50/75/100 RPS 是 50 频道并行总吞吐。
- 2026-07-14 六档报告只对 G-01@5 产生 `PARTIAL/LOAD_WS_CLEANUP_PASS`，且因 run-window DB/Pulsar/Hub/trace provider 不完整，未达 full-chain PASS。
- Helix 2026-06 历史报告能证明当时的性能方向，但不代表当前 `main`。

## 2. 真实调用链与归因边界

### 2.1 命令/HTTP 主链

```text
Tick::Command
  -> ExecutionShell::step
  -> ImModule command handler
  -> Effect::{Persist, Http, ScheduleTimer, Emit}
  -> consume_effects
  -> dispatch_effects
  -> SQLite / HTTP / EventSink
  -> Tick::PortReply 优先回灌
  -> ExecutionShell::step
  -> reconcile / Persist / Emit
```

关键实现：

- `crates/helix-core/src/engine.rs`
- `crates/helix-driver-host/src/engine.rs::run_engine_loop`
- `crates/helix-driver-host/src/dispatch.rs::dispatch_effects`
- `crates/helix-im/src/send/flow.rs`
- `crates/helix-im/src/port_reply.rs`

### 2.2 WS 入站主链

```text
SharedWsClient reader
  -> tick_tx.send(Tick::Inbound)
  -> ExecutionShell::step
  -> WS registry / handler
  -> channel gate: apply | duplicate-drop | buffer-gap
  -> Persist / Emit
  -> SQLite / Native broadcast / FFI batch callback
```

关键实现：

- `crates/helix-driver-host/src/network.rs`
- `crates/helix-im/src/ws/registry.rs`
- `crates/helix-im/src/ws/handlers/post.rs`
- `crates/helix-im/src/channel/gate.rs`
- `crates/helix-driver-native/src/event_sink.rs`
- `crates/helix-driver-ffi/src/event_sink.rs`

### 2.3 分层责任

| 层 | 要压的内容 | Helix 自身可归因 | 外部或平台条件 |
|---|---|---|---|
| HTTP | Command 到 Http Effect、排队、并发闸、request、reply 回灌 | Effect 构造、queue wait、PortReply 路由 | DNS/TLS/RTT、Go handler、Pulsar/DB |
| WS | socket 收帧到 Tick、parse/gate、Persist/Event | reader 转换、tick 队列、parse/gate、effect 产生 | Go 广播前、Pulsar、网络送达 |
| Effect | 每 Tick 数量、类型、字节、dispatch | 完全属于 Helix | 无 |
| Storage | Persist 排队、transaction、rows、cursor、WAL、读写混合 | HostStorage/SQLite adapter、写 worker | 文件系统、磁盘、OS |
| Event/Projection | Emit 构造、BatchSink flush、broadcast lag、FFI callback | helix-im 投影 + driver egress | Angular/Dart 真正渲染属产品壳 |
| PortReply | corr dispatch 到 I/O 完成、reply 被 step 消费 | 队列、优先回灌、reconcile | 中间 I/O 本身需按 port 再分段 |

## 3. 压测对象不按 UC 全量穷举

Helix 不应照搬服务端“23 条声明 x 6 档”。多个 UC 在客户端共用同一类 Command/HTTP/WS/Persist/Emit 管线，全穷举会把正确性矩阵误当成性能矩阵。

建议压 7 类工作负载，再用 strict matrix 保证各 UC 语义正确：

| 负载类 | 代表 UC | 核心风险 | 优先级 |
|---|---|---|---|
| 发送 + echo 对账 | G-01/G-02/G-03a | 乐观落库、HTTP、timer、temporaryId 对账 | P0 |
| 单端高聚合 WS 入站 | G-27 | Tick 队列、parse、gate、SQLite、EventSink | P0 |
| 离线/gap/backfill | G-S1/G-S2/G-S3/G-S4/G-04a | 500/5000 批量、cursor、too_long、续拉 | P0 |
| 本地查询 | G-10/G-11 local-first | SQLite scan、rows codec、结果投影 | P0 |
| 多频道批量操作 | G-05/G-15/G-15a | 多 channel 公平性、effect 放大、写竞争 | P1 |
| 读 HTTP + render-ready 投影 | G-10a/G-12/G-14 | HTTP reply parse、revision/dedupe、Event 体积 | P1 |
| 高频 mutation | G-04/G-06/G-07/G-08/G-09/G-13/G-14a/G-16 | WS mutation、小批写、终态覆盖 | P1 |

## 4. 负载形状

### 4.1 channel 形状

| 形状 | 含义 | 目的 |
|---|---|---|
| `hot-1` | 1 个 channel 承担全部事件 | 验证保序与单 key 上限 |
| `parallel-50` | 50 个 channel 均分总事件 | 验证跨 key 并行与公平性 |
| `fan-in-50-to-1-client` | 一个 Helix 实例加入 50 个 channel | 验证单设备最坏聚合入站 |
| `multi-module` | IM + 第二模块共享写路径 | 验证 SQLite 单写者竞争；当前仍是开放缺口 |

### 4.2 档位与窗口

- 与 Go 报告可比的 L3 档位：5/10/25/50/75/100 operations/s。
- L2 saturation 额外档位：200/500/1000 events/s，直到首个 SLO 失守。
- L1 不用业务 RPS 限制，用固定事件数和 Criterion 吞吐寻找状态机上限。
- 每个正式档必须分开：`load_duration` / `drain_duration` / `observation_duration`。
- L3 默认正式窗口：`120s load + 90s drain + 120s observation`。
- L2 nightly 使用同样三窗；PR smoke 可缩短，但不得把 drain 并入 load。

## 5. 指标合同

### 5.1 标签规则

指标只允许低基数维度：

- `layer`、`stage`、`action`、`tick_kind`、`effect_kind`、`storage_op`
- `platform`、`channel_shape`、`payload_bucket`、`rate`、`status`

以下高基数值禁止进 Prometheus label，只进 trace/JSONL：

- `corr_key`、`req_id`、`temporaryId`、`postId`、`channelId`、`userId`、`eventSeq`

### 5.2 延迟、吞吐与队列

| 指标 | 单位/统计 | 采集点 | 起步预算，非当前跑分 |
|---|---|---|---|
| `helix_core_step_cpu` | us; P50/P95/P99 | 紧包 `shell.step` | 普通 post 桌面 P99 <= 1ms；基线退化 >20% 告警 |
| `helix_tick_queue_wait` | ms; P50/P95/P99 | 入队时间到主循环取出 | 额定负载 P99 <10ms |
| `helix_tick_queue_depth` | count/max | Command/WS 入队处 | 稳态 <192，即 cap 256 的 75% |
| `helix_http_queue_wait` | ms; P95/P99 | Effect dispatch 到 worker 开始 | P99 <20ms，无持续增长 |
| `helix_http_request_duration` | ms; P50/P95/P99 | HTTP adapter request | 按 endpoint 建基线；不归咎 core |
| `helix_http_inflight` | count/max | HTTP worker pool | <= 配置并发，必达队列无丢弃 |
| `helix_persist_queue_wait` | ms; P95/P99 | dispatch 到 persist worker | 桌面 P99 <20ms；手机独立建基线 |
| `helix_storage_tx_duration` | ms; P50/P95/P99 | HostStorage 实际事务 | 普通 post 桌面 P99 <20ms；批量单列预算 |
| `helix_storage_rows` | rows/s + batch histogram | StorageOp 执行层 | 吞吐相对固定 runner 基线下降 >15% 判红 |
| `helix_port_roundtrip` | ms; P50/P95/P99 | corr dispatch 到 PortReply 被 step | storage/http/upload 必须分组 |
| `helix_ws_ingress_to_effect` | ms; P50/P95/P99 | reader 收帧到 effects 构造 | 桌面 100 RPS fan-in P99 <20ms |
| `helix_ws_ingress_to_event` | ms; P50/P95/P99 | reader 收帧到 EventSink 消费 | 桌面 P99 <50ms；手机起步 <100ms |
| `helix_command_to_projection` | ms; P50/P95/P99 | Command accept 到终态 projection | L3 总 SLO，必须能展开为各 hop |
| `helix_shutdown_drain` | ms + remaining jobs | shutdown 到必达任务收口 | Persist 零遗留；HTTP 按既定 timeout 语义 |

### 5.3 Effect、Event 与内存

| 指标 | 单位/统计 | 采集点 | 闸门建议 |
|---|---|---|---|
| `helix_effects_per_tick` | count/distribution | `consume_effects` 前 | 按 action 固定合同；无理由多 1 个即审查 |
| `helix_effect_bytes_per_tick` | bytes; P50/P95/P99 | OwnedEffect 转换后 | P99 相对基线增长 >25% 告警 |
| `helix_effect_amplification` | effects/input event | 每个工作负载 | 热点与多 channel 分开比较，防 O(N) 放大 |
| `helix_event_lagged_total` | count | Native `EventReceiver` | 验收负载下必须 0 |
| `helix_event_no_receiver_total` | count | Native emit 失败 | 正式场景必须 0 |
| `helix_event_batch_size` | events/batch + bytes/batch | `BatchSink::flush` | 非空 step 最多一次跨边界 callback |
| `helix_ffi_callback_duration` | ms; P95/P99 | C++ callback 外围 | P99 <4ms 作为起步预算 |
| `helix_ffi_busy_total` | count | FFI 拒绝/重入边界 | 额定负载必须 0 |
| `helix_alloc_count_per_op` | alloc/op | 基准 allocator | HX-C005 声明零分配的子路径必须 0 |
| `helix_alloc_bytes_per_op` | bytes/op | L1/L2 profiler | 稳态相对基线增长 >10% 告警 |
| `helix_rss_slope` | MiB/min | observation 窗 | 10 分钟增长 <5%；create/destroy 后回落 |

### 5.4 正确性指标

性能 PASS 必须同时满足：

- `lost = 0`
- `duplicate = 0`
- `order_violation = 0`
- `wrong_channel = 0`
- `cursor_regression = 0`
- `event_lagged = 0`
- Persist 必达任务 drain 后零遗留
- 相同 Tick 剧本产生 byte-identical 有序 Effect/Projection
- 每个 `temporaryId/req_id/corr_key` 必须与最终投影对应，不以 HTTP 200 代替完成

## 6. 工具矩阵

| 工具 | 使用层 | 用途 | 不适用边界 |
|---|---|---|---|
| Criterion / `cargo bench` | L1/L2 | core、gate、storage、engine pump 统计基准 | 不用于真网络/K8s/多分钟 soak |
| iai-callgrind | L1 | Linux 稳定检查 instructions/cache/branch 回归 | 不测 async/HTTP/WS/SQLite wall time |
| `perf` + cargo-flamegraph | L2/L3 Linux | CPU 热点定位 | 不能单独证明延迟和正确性 |
| samply / Instruments | L2 macOS | native CPU、Allocations、Time Profiler | 不作为跨平台 CI 闸门 |
| DHAT/dhat-rs | L1/L2 | Effect/Projection/FFI encode 分配定位 | 不开在长时真网络主压测中 |
| heaptrack | L2/L3 Linux | heap 增长和泄漏诊断 | 不进常规 PR CI |
| tokio-console | L2 | task wake、poll、blocking、假死诊断 | 禁止引入 sans-IO core；不是吞吐基准 |
| SQLite trace/profile/EXPLAIN | L2 | transaction、prepare、WAL、慢 SQL 定位 | 高档不全量打印 SQL 参数，防扰动 |
| k6 | L3 | Go HTTP 负载、fixture/provider 编排 | k6 不经 Helix Command/Effect，不能单独证明客户端闭环 |
| Rust harness + HDR Histogram | L2/L3 | 驱动 Helix、收集每 hop 时间、receiver/oracle | 指标/时钟不得反向注入 core 运行时依赖 |
| OTel + Jaeger | L2/L3 | 逐请求 correlation 与瓶颈归因 | trace 不代替 histogram/throughput 统计 |

## 7. 现有能力与盲点

### 7.1 已有资产

- `crates/helix-im/benches/step_inorder.rs`
- `crates/helix-im/benches/gate_bench.rs`
- `crates/helix-driver-host/benches/storage_bench.rs`
- `crates/helix-driver-native/benches/engine_bench.rs`
- `crates/helix-im/tests/stress_test.rs`
- `crates/helix-driver-native/tests/stress_storage.rs`
- `crates/helix-driver-native/tests/stress_engine.rs`
- `/helix-stress-verify` 技能的 stress 三件套 + Criterion 入口
- OTel spans：`helix.command.accept`、`helix.core.step`、`helix.ws.recv/send`、`helix.http.dispatch/request/response`、`helix.storage.persist`、`helix.storage.sqlite.query`、`helix.event.emit`

### 7.2 OTel 不能直接当性能指标

- 当前 `on_tick_start` 的 scope 活到整次 loop 收尾，`helix.core.step` 可能包含 effect dispatch/queue wait/flush，不是纯 core CPU。
- `helix.storage.persist` 和 `helix.http.dispatch` 偏向 dispatch 边界，不等于真实 SQLite transaction 或 HTTP wire 时间。
- trace 适合逐条归因；HDR/metrics 适合 P50/P95/P99 和吞吐。两者都需要。

### 7.3 当前最值得证伪的风险

1. Tick 入站队列容量 256，WS reader 使用 `send().await`，队满会反向阻塞 socket 继续读取。
2. Persist/HTTP 队列容量 1024，缺真实 queue depth/wait histogram。
3. SQLite 文件 WAL 单写路径及多模块共享写竞争未实测。
4. Native broadcast 慢消费者的 `lagged_total`、无 receiver emit 以及恢复动作需要纳入闸门。
5. FFI batch encode、scratch 扩容、callback 时间和 `FFI_BUSY` 缺基线。
6. Effect 数量/字节放大与 PortReply 回灌饥饿缺可见性。
7. Criterion 基线主要在本机 `target/criterion`，未形成固定 Linux runner 的持久趋势。

## 8. 三层实施方案

### 8.1 L1 纯 core/模块微基准

输入矩阵：

- 有序 post、duplicate、旧帧、gap=1/100/500/5000、too_long。
- sync batch=1/100/500/5000。
- send/echo/reply/read/query 的代表状态转移。
- payload=256B/2KiB/16KiB。
- channel=1/50/500，相同总事件数下比较 `hot-1` 与 `parallel-50`。

产出：

- core step CPU、events/s、effects/tick、effect bytes、alloc/op。
- byte-identical 确定性 hash。
- Criterion 趋势与 iai-callgrind instructions/cache/branch 硬回归。

### 8.2 L2 host driver 组合压测

测试拓扑：

- loopback HTTP/WS server 注入 0/10/100/500ms，超时、断连、乱序、重连。
- 真实文件 SQLite WAL，不用 `:memory:` 代替生产写特性。
- 同时灌 WS write + HTTP reply + local query + Event consumer。
- Native broadcast 和 FFI batch callback 分开压。
- 一组业务模块与两组模块共享 storage 分开压。

产出：

- queue wait/depth、storage transaction、PortReply roundtrip、Event lag、FFI callback、RSS slope。
- accepted load 与首个 SLO 失守点。
- CPU/alloc/sqlite profile 只在诊断档开启，不与主跑分混跑。

### 8.3 L3 Go K8s 真链

场景 A，入站容量：

```text
k6/Go sender -> cses-im-server -> WS -> Helix receiver
  -> Tick::Inbound -> gate -> SQLite -> Event/Projection
```

场景 B，完整发送闭环：

```text
Helix Command -> Persist optimistic -> Http Effect -> Go
  -> WS echo -> Helix gate -> Persist reconcile -> final Projection
```

正式模型：

- `hot-1@5`：与 Go 已证热点单频道基线对齐。
- `parallel-50@25/50/75/100`：与 Go 多频道报告对齐。
- `fan-in-50-to-1-client@25/50/75/100`：新增 Helix 单设备最坏入站模型。
- 未有 Go 服务端证据前，不将 `hot-1@10..100` 称为真链 PASS；可在 L1/L2 作客户端独立 saturation 实验。

证据必须串联：

`traceparent + req_id + temporaryId/postId + channelId/eventSeq`

fixture、receiver/oracle、DB/WS/trace provider、cleanup 任一缺失时 fail-closed，不生成假 PASS。

## 9. 零配置入口与文件布局

建议最小产物：

```text
tools/helix-perf/                  # Rust runner + HDR + receiver/oracle
perf/contracts/run.schema.json     # 证据包机器合同
perf/scenarios/default.toml         # 非敏感默认地址/档位/窗口
perf/baselines/<platform>.json      # 固定 runner 基线
perf/reports/.gitignore             # 本地原始证据默认不入库
scripts/perfctl                     # 统一入口
docs/perf/README.md                 # 用法与 PASS 语义
```

无手工 `export` 的标准命令：

```bash
scripts/perfctl smoke
scripts/perfctl l1
scripts/perfctl l2
scripts/perfctl l3 g01-hotspot-5
scripts/perfctl full
```

配置约束：

- 默认地址、namespace、档位、窗口写入 `default.toml`，环境变量只是可选覆盖层。
- Token/cookie/password 不入库，自动读 OS 凭据或 gitignored 本地文件。
- 缺凭据、真 fixture、provider 或 K8s 连接时 preflight 必须失败，不用假数据继续。

## 10. 证据包

每次 run 至少产生：

```text
manifest.json
summary.json
histograms.hdr
metrics.jsonl
trace-index.jsonl
sqlite.json
correctness.json
cleanup.json
profiles/                     # 只在 profile 模式存在
```

`manifest.json` 必须固化：

- Helix git SHA、branch、dirty state、rustc、profile。
- CPU/OS/内存/文件系统/SQLite PRAGMA。
- Go image digest、Pod 拓扑、HPA 冻结状态。
- channel shape、payload bucket、档位、精确 fixture 数。
- load/drain/observation 三窗开始、结束与持续时间。
- 完整性计数、首个 SLO 失守点、cleanup 零残留。

## 11. CI 与持续回归

### PR gate

- L1 正确性、确定性和 iai-callgrind 低噪指令数。
- Criterion 初期只告警，不在共享 runner 上用绝对墙钟阻断。
- lost/dup/order/wrong-channel/cursor regression/event lag 立即硬闸。

### Nightly 固定 Linux runner

- L1 Criterion + L2 loopback HTTP/WS + 真文件 SQLite。
- 校准 10-20 次后冻结绝对预算。
- 起步相对闸门：median >20%、P99 >30% 或吞吐下降 >15% 判红。
- 准确性闸门不等校准，始终硬阻断。

### 隔离环境手工/定时运行

- L3 Go K8s 真链，不进普通 PR。
- 固定 Go image digest、Pod 拓扑、Helix 客户端人格和 run-owned fixture。
- 每档原子写 progress，失败只阻断当前 workload 后续档。

## 12. 实施优先级

### P0：先建可归因证据

1. 建 `perfctl` + scenario config + run schema + 证据包。
2. 新增 tick/http/persist queue wait/depth、PortReply roundtrip、effects/tick/bytes、Event 最终交付 histogram。
3. 将纯 `shell.step` 时间从当前大 scope 中独立，但指标实现只落 host/harness，core 不读墙钟。
4. 建 L2 loopback HTTP/WS + SQLite + Event 闭环。
5. 建 L3 两场景：外部 sender -> Helix receiver；Helix Command -> Go -> WS echo -> local projection。
6. 将真实 Go `post` wire corpus 加入热点/多 channel 回放，不只用 synthetic `posted` fixture。

### P1：补平台和竞争基线

1. 多模块竞争同一 SQLite 写路径。
2. Linux 真盘基线。
3. Flutter 真机 FFI batch/callback/RSS 基线。
4. Native no-receiver/lag 恢复与 FFI busy 闸门。
5. accepted load 自动寻界和固定 runner 趋势对比。

### P2：自动诊断与长稳

1. 自动 flamegraph、DHAT/heaptrack、SQLite profile。
2. 30-60 分钟 soak、能耗与长期 RSS/queue slope。
3. 趋势 dashboard 与容量变更摘要。
4. 有证据后再评估 Effect 分配、WS 文本转换、写批形状或队列策略优化。

## 13. 停止规则

- 没有分 hop 时间，不说“Helix core 慢”。
- 只有 HTTP 200，不说“发送闭环 PASS”。
- 只有 WS 到达，没有 SQLite + Projection，不说“客户端 PASS”。
- 多 channel 过了，不说单 channel 上限相同。
- 没有固定 runner 和环境 manifest，不用本机墙钟数字作 CI 硬闸。
- 没有 run-owned fixture/provider/cleanup，L3 fail-closed。
- profile 与主跑分分开运行，不将 profiler 开销算入容量。
- `helix-core` 不引入 tokio、metrics、OTel 或墙钟依赖。

## 14. 验收定义

第一阶段不以“所有数字更快”为完成，而以以下事实为完成：

1. 一条命令能直接运行 L1/L2/L3，普通入口无必填环境变量。
2. 每个 run 都有可重放 manifest、histogram、trace index、正确性与 cleanup 证据。
3. 能回答延迟分别花在 core、queue、SQLite、HTTP、WS、EventSink 还是 Go/RTT。
4. `hot-1`、`parallel-50`、`fan-in-50-to-1-client` 有独立结论。
5. 正确性计数全部为 0，且闸门具备 HX-C011 要求的可证伪性。
6. 实测数据出来后，才将“队列/SQLite/FFI/core 哪个是第一瓶颈”升级为优化任务。
