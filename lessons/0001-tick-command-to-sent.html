第 1 课 · Helix MessageV3

一条消息，怎样从 Tick::Command 走到 sent？

今天只拿到一个胜利：以后看到“发送成功”，你能问出它到底停在了哪一跳；并且能从 G01a 测试入口顺着源码走完一次。

先打开一页式速查表 →

先记住：发送不是一个瞬间，而是一个小型状态机。用户点击发送只是“意图”；sending 是本地已经保存的乐观事实；sent 要等服务器的 WebSocket post echo，并且最终事实经过持久化与 read-back。

1. 先看总地图

1
Tick::Command：用户说“我要发”AppCommand { name: "im_send_message", payload: JSON bytes }
2
Helix-im：先建一条本地乐观消息message.send_status = "sending"，并记住 temporaryId 和 corr。
3
Persist 完成后才公开 im:post:sending数据库写成功的回灌叫 PortReply::Ok；源码里没有名为 PersistOk 的类型。
4
再发 HTTP POST /posts/create，并启动超时 timerHTTP 2xx 只表示 admission；状态仍然是 Sending。
5
WS post echo：服务器把事实送回来Helix 用 temporaryId 找回本地行，得到服务器 id。
6
MessageV3 原子提交 + read-back 后才 emit 终态im:post:received 的 data.sendStatus 是 "sent"。

2. G01a 测试类到底从哪里开始？

你给的文件不是“发送实现”，而是一个 测试入口。它把场景参数交给共享测试器：

#[tokio::test]
async fn mv3_g01a_real_chain() {
    shared::assert_isolated_send(...).await
        .unwrap_or_else(|error| panic!("MV3-G01a FAIL: {error}"));
}

读这个文件时先问三个问题：

  1. 谁注册它？ tests/message_v3_domain.rs 用 #[path] 把目录文件注册进 message_v3_domain target。
  2. 谁做事情？ shared::assert_isolated_send 负责建频道、跑发送链、关频道；具体装配在 shared::run_helix_send。
  3. 失败怎样出来？ helper 返回 Result<T, String>；? 会提前返回错误，最外层 unwrap_or_else 把错误变成测试失败。

建议先用这个聚焦命令运行一个测试（本轮没有执行它）：

cargo test -p helix-driver-native --test message_v3_domain \
  phase1_post_g01a::mv3_g01a_real_chain -- \
  --nocapture --test-threads=1

它需要真实 Go 8066、登录凭据和可用 WebSocket。没有这些前置，应该记录 BLOCKED_PRECONDITION 或 UNVERIFIED，不是把 health 200 当业务成功。

3. 从入口开始读 Rust

先不要被 Rust 语法吓到。把它当成“一个带标签的消息包”：

pub enum Tick {
    Command(AppCommand),
    PortReply { corr: Correlation, outcome: PortOutcome },
    Inbound(InboundBytes),
    // ...
}

enum 的意思是：Tick 只能是这些情况之一。match 就是“看它是哪一种，再走对应分支”。在 core engine 中，Command 会走模块的 accepts() 和 handle()；PortReply 不重新扫描模块，而是用 corr_map 找回原来的业务请求。

发送命令的模块分支很直白：

"im_send_message" => {
    self.handle_send_message(cmd.payload.as_ref(), now_ms, out)?;
}

这里的 out 是 EffectSink。你可以先把它理解成“待办清单”：业务层把 Persist、Http、Emit 放进去，真正执行 I/O 的是 driver。

4. 为什么先是 sending？

handle_send_message 做三件重要的事：

  1. 解析 payload，补上频道、身份、时间和 Helix 铸造的 temporaryId。
  2. 构造一条写入 message 表的 Persist，其中 send_status 是 "sending"。
  3. 注册 PendingSend，先标成内存状态 Local，等待这次 P1 写入完成。

关键顺序不是“代码恰好这样写”，而是一个不变量：P1 没有成功，就不能向 UI 宣布 sending，也不能抢跑 HTTP。测试 send_test.rs 明确断言了这一点。

Local

内存里有 pending，P1 还没确认。UI 不应把它当成已进入发送阶段。

Sending

P1 Ok 后，内存变为 Sending，并 emit im:post:sending。

Sent

WS echo 带服务器 id 后，按 temporaryId 写入 sent 并取消 timer。

UnSend

HTTP/持久化失败或超时会写 unsend，并 emit im:post:send-failed。

5. 为什么 HTTP 2xx 还不是 sent？

因为当前协议把“请求被接纳”和“服务器事实已经通过实时通道回来”分开。HTTP reply handler 对普通文本的 PortOutcome::Ok 不直接发布 sent；它只结束 HTTP 这一跳，消息仍是 Sending。

真正的确认是 WebSocket 的 action == "post"。这不是 posted。在 post handler 里，Helix 先做 echo 对账，再继续走 MessageV3 gate。

6. temporaryId 为什么不能被删？

服务器返回的是新的 id，但本地乐观行最初没有这个 id。temporaryId 就像快递单上的临时追踪号：

本地乐观行:  temporaryId = tmp-123, id = ""
WS echo:    temporaryId = tmp-123, id = srv-456
对账结果:   temporaryId = tmp-123, id = srv-456, send_status = "sent"

所以成功后两个字段都保留：id 是服务器主键，temporaryId 是本地对账锚点。echo settle 同时做三件事：写 sent、取消 timer、移除 pending_sends 和旧的 corr_map 路由。

7. 最后的收尾：为什么还要 PersistAtomic 和 read-back？

WS echo 只是把服务器事实送到 Helix。MessageV3 还要求：先把 message、channel、member、cursor 等相关事实作为一个原子批次提交；成功后，再按当前 viewer 做一次 read-back。只有 read-back 成功，才允许构造：

{
  "event": "im:post:received",
  "data": {
    "id": "srv-456",
    "temporaryId": "tmp-123",
    "sendStatus": "sent"
  }
}

这就是“可见成功”落后于“durable 事实”的原因：不能让 UI 先看到成功，而本地数据库还没提交。

9. driver 做什么？

Helix-im 只产出 Effect，不自己访问 SQLite、HTTP 或 WS。host engine 取出 Tick，调用 core 的 step()，再把 Effect 分发给对应 port：

Effectdriver 做的事回到 Helix 的形式
Persist写 SQLiteTick::PortReply { corr, Ok/Err }
PersistAtomic一个 SQLite transaction同样按 corr 回灌
Http调用 HttpRequesterHTTP envelope 包在 PortReply 里
Send调用 WS FrameSender不代表对方已送达
Emit调用 EventSink；native 再转 bus envelope事件 bytes 交给宿主
