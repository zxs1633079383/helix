Lesson 0003

Correlation：异步 I/O 的回执小票

上一课你学到：模块吐 Effect::Http，driver-host 真发 HTTP。那问题来了：HTTP 是异步回来的，core 又不能 await，那回包怎么准确回到原来的业务模块？答案就是 Correlation。

本课目标：能说清楚 Correlation、Tick::PortReply、core corr_map、IM CorrelationContext 四者各管什么。

先记一个比喻

你去窗口办事，拿到一张号码小票。窗口后台慢慢处理，处理完喊号。Correlation 就是这张小票。

在 Helix 里，Effect::Http { corr, req } 或 Effect::Persist { corr, ops } 发出去以后，driver 执行完会喊号：Tick::PortReply { corr, outcome }。core 看 corr，把回包送回当初发出这张小票的模块。

两张 map，不要混

core corr_map

位置：crates/helix-core/src/engine.rs 和 module_host.rs。它只记录 Correlation -> module_index，回答“回哪个模块”。

IM corr_map

位置：crates/helix-im/src/port_reply.rs、state 相关类型。它记录业务上下文，回答“这个回包代表哪件事”。

完整回路

helix-im handle(Command)
  -> alloc corr = 101
  -> state.corr_map[101] = OutboundSendHttp { temporary_id, channel_id }
  -> Effect::Http { corr: 101, req }

ExecutionShell
  -> core corr_map[101] = module_index(im)

driver-host
  -> 发 HTTP
  -> reply_tx.send(Tick::PortReply { corr: 101, outcome })

ExecutionShell.step(PortReply 101)
  -> core corr_map.consume(101) = module_index(im)
  -> 投递给 helix-im

helix-im handle_port_reply(101)
  -> state.corr_map.remove(101) = OutboundSendHttp
  -> 继续业务：对账 / 落库 / emit / 标失败

为什么不用 await

因为 helix-core 的铁律是 step() 同步、无 I/O、无 await、无 spawn。它不能卡在那里等 HTTP 或 SQLite。它只能先吐 Effect，下一次等 driver 把结果包装成新的 Tick 喂回来。

这就是 sans-IO 的关键：等待发生在 driver，决策发生在 module，连接两者的是 Correlation。

三个红线

红线 1

不要靠 Effect 顺序表达因果

同一批 Vec<Effect> 的兑现顺序没有保证。必须“发请求 -> 等 PortReply -> 再吐下一步”。

红线 2

必达请求不能用 Fire

需要回包推进状态机的 HTTP/存储必须用 Effect::Http 或 Effect::Persist。HttpFire / PersistFire 不会产生 PortReply。

红线 3

业务上下文不要塞进 core

core 只知道 module index，不知道 OutboundSendHttp、SyncPull、MessageQuery。这些业务语义留在 helix-im。
