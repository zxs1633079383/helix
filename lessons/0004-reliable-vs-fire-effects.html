Lesson 0004

必达 vs 可丢：别把状态机交给运气

上一课你学了 Correlation：需要回包的 I/O 会带一张小票。本课只解决一个判断：什么时候必须要小票，什么时候可以 fire-and-forget。

本课目标：看到 Persist、PersistFire、Http、HttpFire 时，能立刻判断它是不是 load-bearing。

核心分界线

Fire 不是“异步”。Helix 的 driver 本来就会异步兑现 I/O。Fire 的真正意思是：这件事没有 Correlation，不会产生 PortReply，core 和模块都不会等它回来继续业务。

所以判断标准很简单：如果结果要推进状态机、清 inflight gate、拿响应体、推进 cursor，不能 fire。

四种 Effect 怎么选

Persist

本地写成功后才能继续。带 corr，driver 必须回 PortReply。比如 sync 拉回一批消息，写成功后才推进 cursor。

PersistFire

幂等、可重算、丢了不破坏主流程的写。无 corr，无回包。比如主写确认后做单调 cursor 补写。

Http

默认 HTTP 选择。带 corr，响应会回来。发消息、同步、增量拉取都属于这里。

HttpFire

极少数 HTTP 才能用：不需要响应、丢失可自愈、没有 inflight 闸。当前 helix-im 基本没有真实生产者。

背压也是语义

helix-driver-host 里，必达请求用 Overflow::Block：队列满就等，慢一点，但不丢。因为它的 PortReply 承载了后续业务。

HttpFire 用 Overflow::DropNewest：队列满就丢当前这条。这个策略只有在“丢了也能靠 cursor-gate / 重连 / proactive resync 补回来”时才成立。

代码里的判断模板

if needs_response_body || clears_inflight || advances_cursor {
    Effect::Http { corr, req }      // 必达，慢而不丢
} else if idempotent && loss_self_heals {
    Effect::HttpFire { req }        // 可丢，显式 opt-in
} else {
    // 先别写 Effect：这个需求还没把可靠性讲清楚
}
例 1

发消息 posts/create

必须 Effect::Http。它需要服务端响应、失败处理、pending 状态对账。丢了不是“省事”，是把用户消息扔进黑洞。

例 2

sync/notify 增量同步

必须 Effect::Http。回包里有数据，且 PortReply 要清 inflight gate、决定是否续拉、推进游标。

例 3

单调 cursor 补写

可用 PersistFire，前提是主数据已经可靠落地，并且这个写是幂等的 monotonic upsert。重复写没事，漏了下次还能从旧 cursor 恢复。

练习

posts/create 需要响应体和失败对账，选哪个？

主写已成功，只推进幂等单调 cursor，选哪个？

必达 HTTP 队列满了，driver 正确行为是什么？

一个请求要靠 PortReply 清 inflight gate，可以用 Fire 吗？
