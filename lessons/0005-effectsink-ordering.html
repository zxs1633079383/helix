Lesson 0005

EffectSink：输出缓冲，不是因果队列

上一课你学会了“必达 vs 可丢”。这节补上一个很容易误判的点：模块在同一个 step 里 push 多个 Effect，并不等于 driver 会按这个顺序完成它们。

本课目标：能解释 EffectSink 的 Rust 形状、生命周期，以及为什么“先 push Persist 再 push Http”不能表达“写库成功后再发 HTTP”。

EffectSink 是什么

在 Helix core 里，模块不能直接调用 Storage / HTTP / WS。模块只有一个输出口：&mut EffectSink。

fn handle(&mut self, tick: &Tick, now_ms: u64, out: &mut EffectSink) {
    out.push(Effect::Persist { corr, ops });
    out.push(Effect::Emit { event });
}

这段 Rust 的意思很朴素：函数借用一个可变缓冲，把“想做的 I/O 声明”塞进去。它没有 await，没有线程，也没有真的写库。

ExecutionShell 如何用它

ExecutionShell 自己持有一个 scratch: EffectSink。每次 step() 开始先 clear()，然后把同一个缓冲传给模块，最后返回 &[Effect] 给 driver 消费。

step(tick):
  scratch.clear()
  module.handle(tick, now_ms, &mut scratch)
  register_effects_to_maps(module_index, 0)
  return scratch.as_slice()

这里有个 Rust 生命周期点：返回的是借用 self.scratch 的切片。driver 必须在下一次 step() 前消费完，或者自己 clone 成 owned effect。因为下一次 step 会清空并复用这块缓冲。

最大的坑：Vec 顺序不是兑现顺序

Vec<Effect> 的下标顺序只代表“本 step 输出时的排列”，不代表 driver 的完成顺序。driver-host 可能把 Persist 入队、Http 入队、Emit inline 发出；不同队列、不同 worker、不同网络延迟都会让完成顺序变化。

所以这个写法是错的：

// 错：以为同一批 Effect 会先写库成功，再发 HTTP
out.push(Effect::Persist { corr: save_corr, ops });
out.push(Effect::Http { corr: http_corr, req });

正确写法是拆成两个 step：

// step A: 只发需要确认的写
out.push(Effect::Persist { corr: save_corr, ops });

// step B: 等 Tick::PortReply(save_corr, Ok) 回来后
out.push(Effect::Http { corr: http_corr, req });

core 为什么还要扫描 Effect

模块吐出带 corr 的 Persist / Http / Request 后，core 会扫描本次新增的 Effect，把 Correlation -> module_index 放进 corr_map。这样未来 PortReply 回来，才能投回正确模块。

启动时更细一点：start() 会挨个模块调用 on_start，而且所有模块的初始 effects 会累积在同一个 sink 里返回。为了不把前一个模块的 corr 误注册到后一个模块，core 只扫描每个模块新增的 [start..] 区间。

判断

什么时候可以同 step 多 push？

当这些 effect 彼此没有因果依赖时。比如一个投影事件和一个可丢的幂等补写，可以同一批吐出；但“写成功后才能发”的关系必须等 PortReply。
