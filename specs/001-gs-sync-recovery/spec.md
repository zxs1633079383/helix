# Feature Specification: SPEC-IFV2-GS01-GS04-同步恢复

**Feature Branch**: `main (no feature branch created)`
**Created**: 2026-07-21
**Status**: Draft
**Input**: 用户描述：在 WebSocket 重连或重新登录建立连接后，比较本地已提交序列与远端权威序列；不一致时同步最新 message、channel、channel event、channel member，并以可审计证据证明本地状态与远端一致。

**相关合同**：[GS01-GS04 同步到 Frame 完整时序与数据](../../crates/helix-im/docs/interaction-v2/01-GS01-GS04-同步到Frame完整时序与数据.md)；[运行、证据与人工介入手册](../../crates/helix-im/docs/interaction-v2/flows/README.md)。本 Spec 以这些已拍板的 ActionBinding、HostObservation、Tick、Persist、Row/VM、SurfaceComposer 和 InteractionFrame 语义为边界，不重定义它们。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 重连后恢复到权威最新状态 (Priority: P1)

作为重新连上 WebSocket 的 IM 用户，我需要系统发现本地序列与远端序列不一致时自动补齐缺失数据，使我看到的频道、消息和成员状态与服务端一致，而不是看到过期列表或缺失消息。

**Why this priority**: 重连是离线、弱网和切后台后的基础恢复路径；若它不可靠，消息、未读、权限与后续发送都失去可信前提。

**Independent Test**: 在隔离频道人为准备一个落后于远端的本地同步水位，建立新连接，验证系统完成恢复并给出与远端一致的已提交本地状态和 UI Frame。

**Acceptance Scenarios**:

1. **Given** 同一用户的本地已提交序列低于远端权威序列，**When** WebSocket 重连完成并收到连接握手，**Then** 系统必须启动恢复、取得缺失事实、持久提交后才显示恢复完成。
2. **Given** 本地与远端序列相等，**When** WebSocket 重连完成，**Then** 系统不得重复制造消息、成员或频道变更，并可保持已提交的用户界面状态。
3. **Given** 恢复数据无法持久提交，**When** 系统尝试应用同步批次，**Then** 本地序列不得前进，且不得显示基于未提交数据的最终业务画面。

---

### User Story 2 - 重新登录后建立可信同步基线 (Priority: P1)

作为重新登录的用户，我需要新身份建立 WebSocket 连接时先完成与该身份匹配的同步判断，避免旧会话的进度、动作或频道数据泄漏到新会话。

**Why this priority**: 重新登录改变身份边界；错误复用旧会话会造成严重的数据与权限错误。

**Independent Test**: 使用两个隔离用户依次登录同一客户端，验证第二个用户只接收自己的同步结果、频道和动作能力。

**Acceptance Scenarios**:

1. **Given** 用户 A 的旧会话存在本地状态，**When** 用户 B 重新登录并建立连接，**Then** 旧会话的未完成动作、缓存作用域和动作地址必须失效。
2. **Given** 用户 B 本地序列与远端权威序列不一致，**When** 新连接握手后完成比较，**Then** 系统必须只为用户 B 同步、提交并呈现缺失事实。

---

### User Story 3 - 陌生频道安全 hydration (Priority: P2)

作为收到陌生频道事件或通过深链进入频道的用户，我需要系统先补齐频道和成员上下文，再显示频道并允许发送，避免出现无归属消息或可对未知频道发送的编辑器。

**Why this priority**: 这是同步链路进入可交互 UI 的关键边界，直接保护频道权限与发送正确性。

**Independent Test**: 让同步结果指向本地不存在的频道，验证频道上下文持久化后才出现频道摘要与编辑器能力。

**Acceptance Scenarios**:

1. **Given** 本地缺少频道或成员上下文，**When** 收到该频道的同步事实，**Then** 系统必须先补齐并提交频道、成员、消息和用户状态，再呈现该频道。
2. **Given** hydration 尚未完成，**When** 用户打开该频道，**Then** 用户不得获得可执行的发送动作。
3. **Given** hydration 提交成功，**When** 对应频道已打开，**Then** 频道摘要和编辑器能力必须作为一个一致的交互结果出现。

### Edge Cases

- 本地序列高于远端报告的权威序列时，系统不得假装同步完成；必须进入可诊断的恢复/失败状态，并请求权威重建或人工介入。
- 同一远端事件重复到达、乱序到达或在恢复过程中再次到达时，本地状态不得产生重复消息、重复成员或重复频道变更。
- 远端返回过长或不可连续的缺口时，系统必须放弃猜测式补洞，改走权威重载，并在完成前保持“同步中”可见。
- UI 收到不兼容、作用域错误或版本基线错误的交互结果时，必须拒绝整笔结果并请求该作用域的最新快照，不得退回 raw 事件拼装。
- 本地持久化中断、进程重启或会话身份改变时，未完整提交的同步批次不得提升本地同步水位。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在 WebSocket 重连成功或重新登录后建立 WebSocket 连接时，比较当前身份、频道作用域的本地已提交序列与远端权威序列。
- **FR-002**: 当任一可同步作用域的本地序列与远端权威序列不一致时，系统必须进入同步恢复；序列相等时不得重复制造业务事实。
- **FR-003**: 当本地序列落后于远端时，系统必须取得并应用缺失的 message、channel、channel member、用户频道状态及 channel event 应用记录，使本地状态前进到同一权威水位。
- **FR-004**: 同一同步批次中的业务事实、事件应用记录和同步水位必须作为一个可恢复的提交结果；提交失败时，水位不得前进，最终业务交互结果不得出现。
- **FR-005**: 系统必须在本地保留可查询的 channel event 应用账本或等价的持久化证据，使其能够证明从旧水位到新水位的远端事件已被完整、无重复地应用；仅保存一个无法解释覆盖范围的最大序列值不满足本要求。
- **FR-006**: 同步完成后，本地 message、channel、channel member 和 channel event 应用账本必须能够在限定频道与水位范围内，与远端权威数据进行可审计的一致性比较。
- **FR-007**: 系统必须只在同步事实已提交后产出受影响的频道、未读、消息窗口、成员和频道摘要交互状态；未附着的视图不得被强制创建。
- **FR-008**: 对已打开的陌生频道，系统必须先产出一致的频道摘要和编辑器能力；在该结果完成前不得授予可执行的发送动作。
- **FR-009**: 系统必须在恢复开始、恢复完成和恢复失败时向用户提供清晰的全局同步状态；恢复期间，其他已有效频道的现有操作不得被无理由冻结。
- **FR-010**: 系统必须对重复、乱序、缺口过长、身份切换和交互结果基线不匹配采取幂等、权威重载或作用域快照恢复，不得由客户端根据旧 raw 事件自行补算业务状态。
- **FR-011**: 所有验证查询必须使用受限、只读的 `mcp__helix_local_sqlite_ro__*` 与 `mcp__cses_pre_postgres_ro__*`；不得直接修改业务库、同步水位、事件账本或客户端缓存来制造通过结果。
- **FR-012**: 验收必须包含确定性 Helix 核心单元测试，覆盖正常同步、持久化失败、重复/乱序事件、序列差异与身份切换。
- **FR-013**: 验收必须包含 `cses-client` 的 DOM 验证，证明全局“同步中”状态、恢复后的频道/消息呈现，以及陌生频道在 hydration 完成前后编辑器能力的差异。
- **FR-014**: 每次可签收运行必须产出带 correlation 的证据包，关联连接/登录、序列比较、同步输入、提交结果、交互结果、客户端应用与数据库只读对账。
- **FR-015**: 连续实施或验证工作超过 30 分钟时，责任人必须每 30 分钟报告已完成工作、当前证据/阻塞和下一步操作；该报告是进度透明度要求，不替代完成证据。
- **FR-016**: 当远端与本地事实冲突无法通过一次权威恢复收敛、需要数据库写操作、涉及真实用户数据或需要改变已拍板交互语义时，系统必须停止自动处置并要求人工介入。

### Key Entities *(include if feature involves data)*

- **同步会话**: 某身份建立连接后的一次恢复上下文，包含会话身份、作用域、关联键和开始/完成状态。
- **频道同步水位**: 某频道在本地已完整提交的权威事件边界，用于决定是否需要恢复，不能脱离其已应用事实单独前进。
- **同步事实批次**: 从远端得到、准备作为一个恢复结果提交的频道、成员、消息、用户状态和事件应用记录集合。
- **本地事件应用账本**: 可查询地说明哪些 channel event 已被应用、对应哪个频道和水位范围的持久化证据；其具体物理布局留给实施计划决定。
- **交互结果**: 已提交同步事实投影出的、带作用域和版本边界的用户界面状态；它不是原始事件或客户端本地推测。
- **证据包**: 对某次运行的身份、序列、水位、数据库只读快照、跨端关联日志、测试结果和最终判定的可审计集合。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在全部定义的重连、重新登录、离线补事件、gap 恢复和陌生频道场景中，100% 的序列不一致样本都会进入恢复，100% 的序列相等样本不会产生重复业务记录。
- **SC-002**: 每个通过验收的同步运行中，选定频道范围内本地 message、channel、channel member 和本地事件应用账本与远端权威事实在最终水位前 100% 一致；不得存在未解释的缺失、重复或越过水位的记录。
- **SC-003**: 在所有故意注入的持久化失败案例中，0 个案例产生最终业务交互结果或推进同步水位。
- **SC-004**: 每个 GS01-GS04 验收场景都同时具有核心单元测试、客户端 DOM 验证和带 correlation 的只读数据库对账；缺任一证据面即不得标记通过。
- **SC-005**: 对持续超过 30 分钟的实施/验证窗口，100% 的窗口至少每 30 分钟产出一次包含“已完成、当前状态、下一步”的进度报告。
- **SC-006**: 每次无法自动收敛的数据库、身份、Frame/版本或权威事实冲突，100% 被标为 `BLOCKED` 或 `FAIL` 并附第一偏离点，不以手工改库方式转为通过。

## Assumptions

- 远端 PostgreSQL 保持 channel event 与其权威水位的可查询证据；本地和远端读取均经受限 MCP 的 bounded read 完成。
- 当前本地 Helix SQLite 已有 `channel`、`channel_member`、`message` 等投影表，但尚未发现物理 `channel_event` 表；因此在本 Spec 通过前，实施必须提供满足 FR-005 的本地事件应用账本或等价可查询持久化证据，不能把仅有的最大 cursor 当作完整对账。
- 同步使用隔离 tenant、频道和测试账户进行验证；真实用户数据、远端数据库写、DDL、全表导出或生产修复不在本 Feature 范围内。
- 本 Spec 定义 V2 的可实施目标；在 V2 producer、consumer、核心单测与客户端 DOM 验证实际完成前，状态始终是 Draft/Planned，不宣称运行时成功。
- 30 分钟报告仅适用于活跃实施或验证；它不要求建立无人值守定时器，也不替代由人工/系统完成的最终验收。
