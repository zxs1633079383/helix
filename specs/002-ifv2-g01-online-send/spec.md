# Feature Specification: SPEC-IFV2-G01-在线发送

**Feature Branch**: `002-ifv2-g01-online-send`

**Created**: 2026-07-21

**Status**: Planned - implementation blocked pending 001 T050 current-pin evidence

**Input**: 客户端发送普通文本消息时，G01 必须正确执行 ActionBinding、Effect、Persist、SurfaceComposer 和交互帧链路，形成可验证的 `Sending`、`Sent`、`Failed` 呈现状态。本地持久化事实与远端权威记录须可通过受限只读查询对账；发现实现问题可修复源码并重跑验证，但不得直接改数据库或伪造 UI 结果。

## Implementation Admission *(hard prerequisite)*

本 Spec 只消费 `SPEC-IFV2-GS01-GS04-同步恢复` 的最终 V2 基线。任何 G01 源码、fixture、
PC worktree、Cargo/Jest 或真实链执行，都必须等待 001 的 `T050` 已完成，并且该记录对当前 source pin
给出 Rust、PC DOM、mobile fixture、SQLite/PG readonly 四面证据的明确 `PASS`。在此之前，G01 只允许维护
本 Spec 的文档和只读审计，不得并行定义九 Surface、Frame Cache、通用 fixture grammar 或 composer hydration。

公共 JSON wire 由 001 固化为 camelCase（例如 `schemaVersion`、`transactionId`、`requestId`）。Rust 内部可
使用 snake_case 字段并通过 serde 映射；G01 不得另立 snake_case public wire。`message.create` 是 composer
capability；其 opaque binding 承载的实际 action kind 是 `im.send-message`，客户端只提交 `actionRef` 与
`im.message-content.v2` 输入，不能自造 action kind、频道、用户或 temporary id。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 发送者看到单一且可信的消息状态 (Priority: P1)

作为可发送频道的成员，我提交一条普通文本消息后，需要马上知道它在发送、已发送或失败，且同一条消息不会重复出现。

**Why this priority**: 消息状态是发送者判断是否需要重试的唯一可信用户界面依据。

**Independent Test**: 在隔离频道发送一条消息，验证从用户提交到“发送中”，再到权威确认后的“已发送”，始终只有一个逻辑消息行。

**Acceptance Scenarios**:

1. **Given** 用户已获得当前频道有效的发送能力，**When** 用户提交合法文本，**Then** 系统接受该请求，并在本地消息事实已提交后显示唯一的“发送中”行。
2. **Given** 消息显示“发送中”，**When** 系统收到匹配该请求的权威远端确认，**Then** 同一行收敛为“已发送”，并使用稳定的远端消息身份。
3. **Given** 传输请求已被接受但尚未得到权威确认，**When** 客户端收到传输成功结果，**Then** 该行继续显示“发送中”，不得提前显示“已发送”。

---

### User Story 2 - 失败不会丢失输入或误导用户 (Priority: P2)

作为发送者，当请求被拒绝、本地保存失败或远端超时时，我需要保留输入或看到同一条失败消息，并在允许时可以重试。

**Why this priority**: 用户不应因临时错误丢失内容，也不能被错误地告知消息已发送。

**Independent Test**: 分别触发无效发送能力、本地保存失败、远端失败/超时、重复或迟到确认，验证恢复、失败与幂等收敛。

**Acceptance Scenarios**:

1. **Given** 发送能力失效或输入不合法，**When** 用户提交，**Then** 系统拒绝、不创建消息行，并恢复该次输入。
2. **Given** 本地消息事实提交失败，**When** 系统报告失败，**Then** 不显示“发送中”行，并恢复该次输入。
3. **Given** 已提交消息的远端发送失败或超时，**When** 失败被确认，**Then** 同一逻辑行变为“失败”，并仅在允许时提供重试。
4. **Given** 系统收到重复或迟到的远端确认，**When** 处理该确认，**Then** 最终只存在一个正确的“已发送”行。

---

### User Story 3 - 接收者和验证者独立确认结果 (Priority: P3)

作为接收者，我只在自己的会话获得权威消息后看见新消息；作为验证者，我可以用同一关联标识核对本地、远端和桌面呈现的结果。

**Why this priority**: 发送者临时状态不能泄漏；可审计证据使修复依据事实而非猜测。

**Independent Test**: 两个隔离用户执行一次发送，验证接收者不会看见发送者的临时消息，并能以关联标识对齐双方的持久化和呈现结果。

**Acceptance Scenarios**:

1. **Given** 发送者消息仍为“发送中”，**When** 接收者尚未获得权威消息，**Then** 接收者不显示该临时消息。
2. **Given** 接收者获得权威消息，**When** 接收者完成自己的会话更新，**Then** 接收者看见消息、会话预览和适用未读变化。
3. **Given** 一个验证运行，**When** 验证者按其关联标识查询受限事实，**Then** 本地事实、远端权威记录和桌面可见状态不存在矛盾。

### Edge Cases

- 频道权限、成员资格或生命周期在用户取得发送能力后变化时，旧能力必须失效，不能继续发送。
- 应用重启、网络中断和恢复后，已提交的消息必须恢复正确状态，不得凭草稿把消息误标为已发送。
- 不一致、未知或版本不连续的呈现更新必须保留最后一个一致画面并触发恢复，不能由客户端补造消息行。
- 重复提交、重试、重复确认和迟到确认不得产生重复本地记录、远端记录或用户可见消息。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须只接受拥有当前有效发送能力的频道成员的普通文本消息提交，并拒绝无效、过期或作用域不匹配的请求。
- **FR-002**: 每次提交必须有唯一关联标识，可关联用户动作、临时消息、远端确认、可见更新和验证证据。
- **FR-003**: 对于被接受的提交，系统必须先形成可恢复的本地消息事实，之后才显示“发送中”。
- **FR-004**: 系统必须将“发送中”“已发送”“失败”作为互斥、用户可见的消息状态；一次发送在任一时刻只能处于其中一个状态。
- **FR-005**: 系统必须仅在收到匹配的权威远端确认后显示“已发送”；单独的传输受理不得改变消息状态。
- **FR-006**: 系统必须在权威确认后将临时消息身份收敛为规范远端身份，同时保持用户只看见一个逻辑消息行。
- **FR-007**: 系统必须在“发送中”形成前的拒绝或保存失败时恢复该次输入；在已形成后失败时显示同一消息的失败状态，并仅在允许时提供重试。
- **FR-008**: 系统必须幂等处理重复提交、重复确认和迟到确认，避免本地、远端或用户界面的重复逻辑消息。
- **FR-009**: 发送者和接收者必须在独立会话中形成可验证的可见更新；发送者的“发送中”状态不得对接收者可见。
- **FR-010**: 每次验证必须支持范围受限的本地 SQLite 与远端 PG 只读对账，并将结果关联至同一发送请求；验证不得直接更改真实持久化数据。
- **FR-011**: 验收必须包含 Helix Rust 行为单元测试、`cses-client` 桌面 DOM 呈现测试、双用户验证、SQLite/PG 对账及至少一个失败反证。
- **FR-012**: 发现实现缺陷时，授权维护者可以修复受影响源码或测试并重新执行同一验证；不得通过直接修改 SQLite/PG、伪造客户端状态或绕过正常发送链修复。
- **FR-013**: 持续超过 30 分钟的实施、修复或验证工作必须每 30 分钟报告已完成工作、当前证据、阻塞项和下一步；外部环境无进展时同样如实报告。
- **FR-014**: 被接受的发送必须遵守既定 G01 交互顺序：有效 ActionBinding 进入命令处理，产生必要 Effect，经本地 Persist 成功后由 SurfaceComposer 形成交互帧；任何阶段失败不得跳过前置阶段伪造后续状态。

### Key Entities *(include if feature involves data)*

- **发送请求**: 用户向一个频道提交普通文本的唯一操作，带有关联标识和当前结果。
- **发送能力**: 指定用户在指定频道、指定上下文中可发送消息的短生命周期授权。
- **临时消息**: 本地已提交但尚未由远端确认的逻辑消息，处于“发送中”或“失败”。
- **规范消息**: 已由远端权威确认、具有稳定身份并处于“已发送”的消息。
- **交互帧**: 一次完整、一致的用户界面状态变化，包含消息状态、受影响会话信息和一次性交互结果。
- **验证运行**: 以用户、频道和关联标识隔离的验证记录，用于收集本地、远端和桌面证据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在隔离频道的正常发送验证中，100% 的被接受消息从“发送中”收敛为一个“已发送”逻辑消息，且没有重复可见行。
- **SC-002**: 在拒绝、本地保存失败、远端超时、重复确认和迟到确认五类验证中，100% 的运行保持输入恢复或单一正确失败/已发送状态，不显示错误的“已发送”。
- **SC-003**: 每个通过的验证运行都能用一个关联标识串起用户提交、本地事实、远端权威记录及发送者/接收者可见结果；缺少任一必需证据时结果必须为阻塞或不确定，而非通过。
- **SC-004**: 所有要求的 Rust 行为单测和 `cses-client` DOM 测试通过，且至少一个故意破坏的呈现更新验证证明系统拒绝不一致状态。
- **SC-005**: 对于持续超过 30 分钟的实施、修复或验证活动，100% 的执行窗口都有间隔不超过 30 分钟的进度与下一步记录。

## Scope and Exclusions

- 仅覆盖普通文本的 G01 在线发送；附件、媒体、上传、定时、转发、群治理和其他 Gate 不在本次范围内。
- 不以 legacy raw emit 作为业务 UI 真源，也不以旧链路成功证明本功能完成。
- 不授权对真实 SQLite、远端 PG 或客户端缓存的直接写入、修复或清理。
- 本次实现优先级要求 `cses-client` 桌面 DOM 验证；移动端可复用语义，但不是本 Spec 的完成前置。
- 001 未完成或其 T050 证据不是当前 source pin 的 `PASS` 时，本 Spec 的任何实现任务均为 blocked；不得以
  仅有设计文档、旧 pin 或单端 fixture 代替该前置。

## Assumptions

- 用户已经通过 001 已验收的频道进入和同步恢复获得当前有效发送能力；陌生频道必须先完成必要恢复后才可发送。
- 用户所述“远端 PC 落库”按前文 SQLite/PG 语境解释为远端服务端的权威持久化记录；客户端侧由桌面 Frame Cache/DOM 证据独立验证。
- 验证环境提供两个隔离测试用户、一个可清理的测试频道以及本地 SQLite、远端 PG 的受限只读查询。
- 所有真实业务写入继续经过正常产品链；30 分钟报告是持续工作合同，不要求为本 Spec 启动无人值守定时任务。
