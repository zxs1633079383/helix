# Feature Specification: G15a PC 创建群聊

**Feature Branch**: `main (spec-only; no branch hook configured)`

**Created**: 2026-07-21

**Status**: Draft

**Loop Profile**: `helix-loop/v1`

**Input**: 基于 G15a 建群合同，为 PC 用户实现创建群聊；移动端不在本次范围内。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建者建立并进入可信群聊 (Priority: P1)

作为有建群权限的 PC 用户，我可以从会话列表发起创建群聊，填写群名称并选择至少一名其他成员；创建成功后，我只看到一个新群聊，并能在取得完整频道能力后进入交流。

**Why this priority**: 这是 G15a 的核心用户价值；如果创建结果不能形成唯一且可进入的群聊，其余邀请与恢复行为都没有可靠基础。

**Independent Test**: 使用一个创建者和至少一名候选成员提交合法建群请求，验证创建者的会话列表只新增一个群聊，并在进入后获得可用的频道摘要和消息输入能力。

**Acceptance Scenarios**:

1. **Given** 创建者已登录且当前会话列表提供有效的建群能力，**When** 创建者打开建群界面，**Then** 可以填写不超过 30 个字符的群名称并选择至少一名其他成员。
2. **Given** 建群草稿合法且未在提交中，**When** 创建者确认创建，**Then** 系统只接受一次规范化请求，并将该次操作标记为等待权威结果。
3. **Given** 服务端已确认新群聊且本地事实已完整提交，**When** 创建者收到用户界面更新，**Then** 会话列表中只出现一个对应群聊，名称和成员摘要与权威结果一致。
4. **Given** 新群聊已出现在创建者会话列表，**When** 创建者进入该群聊，**Then** 系统先提供同一群聊的频道摘要和消息输入能力，再允许发送消息；消息时间线按需加载。

---

### User Story 2 - 失败不会制造幽灵群聊 (Priority: P2)

作为创建者，当权限失效、输入无效、远端拒绝、冲突或本地提交失败时，我需要保留可修正的草稿并得到明确结果，而不是看到一个并不存在或不可进入的群聊。

**Why this priority**: 建群是跨用户且可持久化的操作，错误的成功提示会制造难以恢复的频道和成员状态。

**Independent Test**: 分别触发过期能力、空成员、重复成员、远端拒绝和本地提交失败，验证会话列表保持上一个一致状态，且不存在新群聊行。

**Acceptance Scenarios**:

1. **Given** 建群能力已过期或与当前用户不匹配，**When** 用户提交草稿，**Then** 系统拒绝请求、不创建群聊，并提示用户重新取得有效能力。
2. **Given** 群名称为空、超长或未选择其他成员，**When** 用户尝试提交，**Then** 系统保持草稿、说明不可提交原因，并且不产生远端操作。
3. **Given** 远端拒绝、发生冲突或返回无效结果，**When** 该结果到达，**Then** 系统保留上一个一致的会话列表，恢复草稿的可编辑状态，并显示与本次请求关联的失败结果。
4. **Given** 权威群聊事实已到达但本地事实提交失败，**When** 系统处理失败，**Then** 不发布新群聊的成功界面更新，并进入可恢复或需人工处理的状态。

---

### User Story 3 - 受邀成员与恢复链路独立收敛 (Priority: P3)

作为受邀成员，我只通过属于自己的会话范围收到新群聊；作为验证者，我能证明重复、乱序和断线恢复不会产生重复群聊或把创建者的界面状态复用给其他用户。

**Why this priority**: 群聊创建影响多个用户，但每个用户的权限、未读和已挂载界面都不同，必须独立形成结果。

**Independent Test**: 使用创建者和受邀成员两个隔离账号，重复投递并调整权威事实到达顺序，验证双方各自得到一个正确群聊，未参与用户不受影响。

**Acceptance Scenarios**:

1. **Given** 群聊已权威创建且用户 A 是受邀成员，**When** 用户 A 获得自己的频道事实，**Then** 用户 A 的会话列表和适用未读摘要独立更新，不复用创建者的界面更新。
2. **Given** 用户 B 未被邀请且没有访问权限，**When** 群聊创建完成，**Then** 用户 B 的会话列表、未读摘要和频道能力均不发生变化。
3. **Given** 同一群聊事实通过确认、实时推送或恢复同步重复到达，**When** 系统处理这些事实，**Then** 每个相关用户最终只存在一个群聊和一份规范成员关系。
4. **Given** 客户端在远端创建成功后、界面更新前中断，**When** 客户端恢复并重新同步，**Then** 群聊从权威事实重新形成，不依赖丢失的临时界面状态。

---

## Loop Contract *(mandatory)*

> 本节定义 G15a 的外置 UC 合同。成员选择、名称输入和提交中的视觉状态属于 PC 平台输入过程；只有规范化的最终建群请求进入共享业务链。

### Trigger

已登录 PC 用户在自己的会话列表中调用当前有效的“创建群聊”能力，并提交合法的群名称与成员集合。

### Goal

创建一个由服务端确认、在本地可恢复且对各相关用户独立可见的群聊；创建者能从唯一的新会话行进入频道，受邀成员只获得属于自身范围的群聊结果。

### Completion

仅当以下事实同时可被独立验证时完成：服务端存在唯一权威群聊及成员关系；创建者本地已提交对应频道与成员事实；创建者收到一次原子用户界面更新并看到唯一群聊行；进入频道时先获得可用的频道摘要与消息输入能力。单独的请求受理、传输成功或临时弹窗关闭都不算完成。

### Boundaries

本次只覆盖 PC 端的私有群聊创建，不覆盖移动端、私聊、开放频道、话题、群头像上传、成员治理、关闭或退出频道。相同请求的自动重试必须保持幂等；同一失败签名最多自动修复两次，第三次转入人工处理。不得通过直接修改本地或远端数据库制造成功结果。

### Human Gate

扩大到移动端或其他频道类型、改变服务端派生的创建者/成员/默认头像规则、引入不可逆数据迁移、绕过权威事实或降低完成标准，都必须由用户明确批准。

### Edge Cases

- 用户双击提交、网络重试或页面重复触发同一请求时，只能创建或显示一个逻辑群聊。
- 成员集合包含创建者、重复成员、空标识或已失效账号时，必须规范化或拒绝，不能形成不确定成员关系。
- 用户取得建群能力后权限发生变化时，旧能力必须失效。
- 权威确认、实时推送和恢复同步以任意顺序重复到达时，最终频道与成员事实必须一致。
- 远端已经创建成功但客户端在本地提交前退出时，恢复同步必须能补齐群聊，不得再次创建。
- 新群聊事实到达时会话列表尚未挂载，系统可以不立即渲染，但下次挂载必须得到完整且唯一的群聊结果。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须只向已登录且当前有建群权限的 PC 用户提供创建群聊能力，并拒绝过期、跨用户或作用域不匹配的调用。
- **FR-002**: 建群草稿必须包含去除首尾空白后 1 至 30 个字符的群名称，以及至少一名不同于创建者的有效成员。
- **FR-003**: 创建者身份必须来自当前可信会话；创建者不得作为普通受邀成员重复提交，重复成员必须在请求前归一化为唯一集合。
- **FR-004**: 每次被接受的建群提交必须具有可关联且可幂等处理的请求身份，重复提交不得产生重复群聊。
- **FR-005**: 系统必须将用户输入过程与共享业务请求分离；未完成的名称、成员选择和弹窗状态不得成为跨端业务事实。
- **FR-006**: 系统必须仅接受服务端确认的频道身份、成员关系和最终频道属性作为成功事实，不得以请求受理或传输成功推测建群完成。
- **FR-007**: 权威频道与成员事实必须在本地完整提交后，系统才可以向创建者发布成功的群聊界面更新。
- **FR-008**: 创建者的成功更新必须原子地形成唯一会话行，并同步更新适用的会话摘要；不得先显示无法进入的半成品群聊。
- **FR-009**: 创建者进入新群聊时，系统必须先提供该频道一致的摘要与消息输入能力；消息时间线加载是独立的后续行为。
- **FR-010**: 每名受邀成员必须基于自己的权限、会话范围和已挂载界面独立形成群聊结果，不得复用创建者的用户界面状态。
- **FR-011**: 未参与用户不得获得该群聊的会话行、未读变化、频道能力或可推断的成员信息。
- **FR-012**: 权限拒绝、输入错误、远端失败、冲突、无效权威结果或本地提交失败时，系统必须保留最后一个一致界面，不发布成功群聊，并给出与本次请求关联的可操作结果。
- **FR-013**: 重复、乱序或恢复得到的同一频道事实必须幂等收敛为一个频道、唯一成员关系和每用户一个群聊结果。
- **FR-014**: 验收必须覆盖创建者正常链路、受邀成员独立链路、未参与用户隔离、重复事实、过期能力、远端拒绝和本地提交失败。
- **FR-015**: 移动端界面、移动端集成和移动端验收不得成为本功能的实现任务或完成证据。

### Key Entities *(include if feature involves data)*

- **建群能力**: 当前用户在自己的会话列表范围内发起创建群聊的短生命周期授权。
- **建群草稿**: PC 平台暂存的群名称与成员选择；在提交前不是共享业务事实。
- **建群请求**: 由合法草稿规范化得到的单次幂等操作，关联创建者、成员集合和最终结果。
- **群聊**: 服务端确认的私有频道，具有唯一身份、名称、生命周期和创建者。
- **群成员关系**: 用户与群聊之间的权威成员关系，每个相关用户据此形成自己的可见结果。
- **用户范围群聊结果**: 某一用户的会话行、未读摘要和频道能力组成的一致可见状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在所有正常创建验证中，100% 的请求在权威确认和本地提交后只产生一个创建者可见群聊行，且该群聊可以取得频道摘要与消息输入能力。
- **SC-002**: 在双击、三次重复事实和断线恢复三类验证中，创建者和每名受邀成员最终都只有一个相同频道身份及一份规范成员关系。
- **SC-003**: 在过期能力、非法草稿、远端拒绝、无效结果和本地提交失败五类验证中，100% 不出现幽灵群聊或错误成功提示，且创建者得到明确的修正、重试或人工处理结果。
- **SC-004**: 双用户隔离验证中，创建者与受邀成员各自获得正确结果，未参与用户的会话列表、未读摘要和频道能力保持不变。
- **SC-005**: 100% 的通过运行能够用同一请求身份关联提交、权威频道事实、本地频道/成员事实和创建者可见结果；缺少任一必需证据时结论必须为阻塞或不确定。
- **SC-006**: PC 端的功能和验收可以在没有移动端构建、移动端 fixture 或移动端运行证据的情况下独立完成。

## Scope and Exclusions

- 范围包含共享 G15a 建群语义、PC 建群入口、PC 草稿提交、创建者会话结果、受邀成员独立结果及失败/恢复行为。
- 范围不包含移动端、Web 专属界面、私聊、开放频道、创建话题、修改头像、群资料治理、成员角色治理、退出或关闭频道。
- 范围不包含消息发送本身；创建后发送依赖既有的频道进入和发送能力。
- 不以旧的原始事件、传输响应、临时弹窗状态或直接数据库写入作为成功真源。

## Assumptions

- PC 用户已有可用身份和组织成员目录，候选成员的有效性由现有身份与权限系统提供。
- 本期群聊类型固定为私有群聊；创建者由可信会话派生，默认头像和成员角色由现有权威规则派生。
- 群名称长度按当前 PC 产品约束采用 1 至 30 个字符；本 Spec 不改变该产品规则。
- 新群聊创建后不会自动加载完整时间线；进入频道时只要求先取得一致的摘要与消息输入能力。
- Web 专属交互和移动端均不是本期完成前置；共享业务语义不得引入仅 PC 可解释的持久事实。
